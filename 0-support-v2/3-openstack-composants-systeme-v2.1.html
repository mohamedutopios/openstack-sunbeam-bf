Introduction

Objectif et déroulé

Objectif : connaître les trois logiciels sur lesquels reposent tous les services OpenStack, savoir ce que chacun expose sur le réseau, et savoir l'interroger quand le cloud se comporte mal.

À l'issue de ce module, vous saurez :

  • Expliquer ce que font RabbitMQ, MariaDB Galera et le serveur d'API, et ce qu'ils ne font pas.
  • Citer leurs ports, leurs comptes et les réseaux sur lesquels ils doivent — ou ne doivent pas — être joignables.
  • Relier chaque option de configuration d'un service au composant qu'elle pilote.
  • Lancer les commandes de diagnostic de chacun et interpréter leur sortie.
  • Reconnaître dans un journal le message qui désigne le composant fautif.
  • Conduire les reprises courantes : partition du bus, perte de quorum de la base, backend d'API hors service.

1 · La file de messages

Rôle : ce que le bus transporte, et pour qui

Trois services rendus

  • Appels RPC : un processus demande à un autre processus du même service d'exécuter une fonction (créer une instance, attacher un volume).
  • Notifications : un service annonce qu'un événement a eu lieu, pour qui voudra l'entendre (mesure d'usage, audit).
  • Découverte implicite : un nova-compute devient joignable dès qu'il s'abonne à sa file. Il n'existe aucun registre d'adresses des processus.

Ce qu'il n'est pas

  • Un stockage : un message consommé disparaît. L'état durable est en base.
  • Un canal entre services : Nova parle à Neutron en REST, jamais par le bus.
  • Un chemin de données : aucun paquet ni bloc d'instance n'y transite.
Découplage : l'émetteur ignore où tourne le destinataire et combien d'exemplaires existent. C'est ce qui permet d'ajouter un hyperviseur ou un scheduler sans rien reconfigurer.

Connexions et canaux : ce qu'un seul processus ouvre

  • Une connexion est une session TCP authentifiée ; un canal est un flux logique à l'intérieur. oslo.messaging ouvre plusieurs connexions par processus.
  • Chaque worker d'un service est un processus distinct, avec ses propres connexions.
  • Le total croît donc vite : nombre de nœuds × services × workers × quelques connexions.
Option (oslo.messaging)DéfautEffet
rpc_conn_pool_size30Taille maximale du pool d'émission

À vérifier côté RabbitMQ : la limite de descripteurs de fichiers du processus (une connexion = un descripteur). Un cluster qui refuse de nouvelles connexions alors que la mémoire est saine a souvent atteint cette limite.
Un pare-feu ou un répartiteur qui ferme les connexions inactives entre un nœud et RabbitMQ provoque des reconnexions en boucle : les battements servent précisément à garder ces sessions vivantes.

Durée de vie

  • Les files RPC d'un rôle (scheduler, conductor) sont durables : elles attendent leurs consommateurs.
  • Les files de réponse et de diffusion appartiennent à un processus : sans consommateur, elles expirent au bout de rabbit_transient_queues_ttl (1800 s par défaut).
  • Un service arrêté longtemps laisse donc des ordres en attente dans sa file ciblée : ils seront exécutés à son retour.
Changer de type n'est pas transparent. Une file existe avec ses arguments ; un service qui la redéclare autrement est refusé : PRECONDITION_FAILED - inequivalent arg 'x-queue-type'. Le passage aux files à quorum impose d'arrêter les services, de supprimer les anciennes files, puis de redémarrer.

Le cluster : trois nœuds, un cookie, une majorité

Réaction à une partitionComportementUsage
pause_minorityLe côté minoritaire se met en pause et refuse les clientsRecommandé à trois nœuds
autohealLes deux côtés continuent, puis le perdant est redémarréPrivilégie la disponibilité, au prix de pertes
ignoreRien : les deux côtés divergentÀ éviter
  • Les leaders des files à quorum se répartissent sur les trois nœuds : aucun n'est « le maître ».
  • Une file à quorum reste utilisable tant que deux de ses trois répliques se voient.
  • Le cluster se forme par nom : un nœud dont le nom d'hôte change est vu comme un inconnu.
  • Les services listent les trois nœuds et se reconnectent seuls : pas de VIP devant RabbitMQ.

1 · La file de messages

Partition réseau : symptômes et reprise

Ce que l'on observe

  • Dans les journaux des services : vagues de « AMQP server … is unreachable », puis reconnexions.
  • cluster_status : section « Network Partitions » non vide, ou un nœud absent des « Running Nodes ».

Reprise après retour du lien

  • Avec pause_minority, le nœud isolé rejoint seul le cluster.
  • S'il reste à l'écart : rabbitmqctl stop_app puis start_app sur ce nœud.

Arrêt complet du cluster

  • Le dernier nœud arrêté doit redémarrer en premier : lui seul connaît le dernier état.
  • Si cet ordre est inconnu ou impossible : rabbitmqctl force_boot sur un nœud, puis démarrage des autres.
Après toute reprise, contrôler les services eux-mêmes : certains processus restent connectés à une file qui n'existe plus et ne s'en aperçoivent pas. Vérifier la colonne consumers, redémarrer ceux qui manquent.

Ce qu'un message perdu laisse derrière lui : une instance en BUILD, un volume en « attaching », une migration à mi-chemin. Le bus ne rejoue rien de lui-même ; il faut remettre l'état en cohérence avec les commandes d'administration du service.
Bonne pratique : avant une opération de maintenance sur le bus, s'assurer qu'aucune opération longue n'est en cours — migrations, créations en masse, sauvegardes de volumes.

2 · La base de données

Rôle : la mémoire du cloud

Ce qu'elle contient

  • L'inventaire : instances, ports, réseaux, volumes, images, utilisateurs, projets.
  • L'état de chaque ressource et de chaque opération en cours (vm_state, task_state, status).
  • Les affectations : quelle instance sur quel hôte, quel volume attaché où, quelles allocations dans Placement.
  • Les battements des services et la configuration dynamique : quotas, gabarits, agrégats, rôles.

Ce qu'elle ne contient pas

  • Les données des utilisateurs : disques, objets et images vivent dans le stockage.
  • Les jetons Keystone : au format Fernet, ils ne sont pas enregistrés.
  • L'état réel des hyperviseurs : la base dit ce qui devrait être, pas ce qui est.
La base est la référence. En cas de divergence avec la réalité (instance disparue de l'hyperviseur, port orphelin), ce sont les services qui se resynchronisent sur elle — ou l'administrateur qui la corrige par les API, jamais par SQL.

  • Les services ne connaissent que la VIP : ils ignorent quel nœud est actif.
  • HAProxy envoie tout vers un seul nœud ; les deux autres ne servent qu'en cas de panne du premier.
  • Une bascule coupe toutes les connexions ouvertes : oslo.db les rouvre et rejoue la requête en cours.
  • Chaque connexion occupe un thread et de la mémoire côté MariaDB : la somme de tous les pools doit rester sous max_connections.
2 · La base de données

Galera : la réplication par certification

  • Synchrone à la validation : quand le service reçoit « OK », la transaction est connue et acceptée par la majorité. Aucune écriture validée ne se perd à la panne d'un nœud.
  • Appliquée ensuite : les autres nœuds l'écrivent avec un léger décalage. Lire sur un autre nœud juste après peut renvoyer l'ancienne valeur.
  • Tous les nœuds acceptent les écritures, mais deux transactions concurrentes sur les mêmes lignes via deux nœuds se heurtent à la certification. D'où le nœud d'écriture unique.
  • Contrôle de flux : un nœud trop lent à appliquer freine tout le cluster. Les trois nœuds doivent avoir des disques équivalents.
Contraintes de Galera : tables InnoDB uniquement, clé primaire sur chaque table, grosses transactions à éviter. Les schémas d'OpenStack les respectent.

Quorum et états d'un nœud Galera

TransfertPrincipeQuandDurée
IST (incrémental)Rejoue les transactions manquantes depuis le cache d'un donneurAbsence courte : le retard tient dans le cache (gcache)Secondes à minutes
SST (complet)Copie intégrale des données depuis un donneur (mariabackup)Nœud neuf, absence longue, données corrompuesProportionnelle à la taille de la base
  • Majorité stricte : à trois nœuds, deux doivent se voir. À deux, la moindre coupure entre eux arrête tout.
  • Nombre pair : ajouter un arbitre (garbd) qui vote sans stocker de données.
  • Arrêt propre d'un nœud : il quitte le groupe et la majorité se recalcule sur les nœuds restants.
  • Arrêt brutal des trois : plus de composant primaire, aucun nœud ne redémarre seul en service — il faut réamorcer le cluster.
  • Pendant un SST, le donneur est mis à l'écart : à trois nœuds, un seul reste pleinement disponible.

Étendre, puis contracter

Erreurs « Unknown column », « Table doesn't exist » ou refus de démarrer du service juste après une mise à jour : le schéma est en retard sur le code. Jamais de modification manuelle du schéma.

3 · Le serveur d'API

La pile : du répartiteur au code du service

HAProxy

Reçoit toutes les connexions, déchiffre, choisit un contrôleur sain. Ne connaît rien d'OpenStack : il ne voit que du HTTP.

Serveur WSGI

Fait tourner le code Python : gère les processus, les threads, les redémarrages. C'est lui qui fixe la capacité de traitement.

Application

Le service lui-même. Une requête n'aboutit que si toutes ses dépendances répondent : la disponibilité de l'API est le produit des leurs.

Workers : la capacité, et ce qu'elle coûte en aval

  • Un worker traite une requête à la fois par thread. Trop peu de workers : les requêtes attendent, HAProxy renvoie des 504.
  • Trop de workers : mémoire épuisée sur les contrôleurs et plafond de connexions de la base dépassé.
  • La bonne valeur se mesure : temps de réponse, file d'attente HAProxy, Threads_connected.
Où se règle le nombre de workers
uWSGI : processes et threads
mod_wsgi : directive WSGIDaemonProcess
Kolla-Ansible : variable openstack_service_workers
Piège du défaut « un worker par cœur » : sur un contrôleur de 64 cœurs, dix services à 64 workers font 640 processus et des dizaines de milliers de connexions potentielles. Toujours borner.

  • Le premier délai qui expire décide de ce que voit le client ; les étages suivants continuent de travailler.
  • Un 504 signifie « pas de réponse à temps », pas « opération échouée ». Relancer aveuglément crée des doublons.
  • Après un 504, vérifier l'état de la ressource avant toute nouvelle tentative.
  • Allonger les délais repousse le symptôme sans traiter la lenteur. La bonne question : pourquoi 80 s ?
C'est aussi pourquoi les opérations longues sont des « cast » : l'API répond 202 tout de suite et n'attend rien.

La requête n'a pas été traitée normalement. Le journal du service peut être vide : commencer par HAProxy.
