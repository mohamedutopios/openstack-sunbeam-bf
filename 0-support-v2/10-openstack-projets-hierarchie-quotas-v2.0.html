Introduction

Objectif et déroulé

Objectif : savoir découper un cloud en projets, les ranger dans une hiérarchie, borner leur consommation par des quotas, et choisir un modèle d'organisation qui cloisonne réellement équipes, applications et environnements.

À l'issue de ce module, vous saurez :

  • Dire ce qu'un projet isole, service par service, et ce qu'il laisse partagé.
  • Construire un arbre de projets et y poser des rôles hérités.
  • Lire, fixer et dimensionner des quotas pour le calcul, le stockage et le réseau.
  • Expliquer les limites unifiées et leurs deux modèles d'application.
  • Comparer plusieurs modèles d'organisation et en choisir un.
  • Compléter le cloisonnement par le réseau et le matériel.

1 · Le projet

Ce qu'est un projet

Vocabulaire : « projet » et « tenant » désignent la même chose ; le second est l'ancien nom, encore présent dans certaines commandes, options et messages d'erreur.
Un projet n'est pas un groupe de personnes. C'est un conteneur de ressources ; les personnes y accèdent par des rôles, et une même personne peut travailler dans plusieurs projets.

Chaque service tient ses propres comptes : il n'existe pas de « quota global du projet ». Un projet a un jeu de quotas dans Nova, un autre dans Cinder, un autre dans Neutron.
1 · Le projet

Ce qui est étanche, ce qui est partagé

  • Réseau : deux réseaux de deux projets ne communiquent pas, sauf par un routeur et une adresse externe, comme deux réseaux d'entreprises distinctes.
  • API : lister les instances ne renvoie que celles du projet du jeton ; demander celle d'un autre renvoie « introuvable ».
  • Matériel : la cloison est logique. Les instances de deux projets partagent hyperviseurs et disques ; l'étanchéité repose sur la virtualisation.
  • Entre membres d'un même projet : aucune cloison. Tout membre voit et peut modifier toutes les ressources du projet.

1 · Le projet

Cycle de vie d'un projet

# Prérequis : jeton d'administrateur ou de gestionnaire de domaine
openstack project create --domain nord \
  --description "Site vitrine" vitrine
openstack project show vitrine --domain nord

# Suspendre, reprendre
openstack project set --disable vitrine --domain nord
openstack project set --enable  vitrine --domain nord

# Retirer : purger d'abord, supprimer ensuite
openstack project purge --dry-run --project <id>
openstack project purge --project <id>
openstack project delete <id>
  • Désactiver n'arrête rien : c'est l'accès par l'API qui est coupé. Pour libérer de la capacité, il faut arrêter ou supprimer les instances.
  • project purge supprime instances, volumes, instantanés et images du projet ; l'option --dry-run liste sans agir. Réseaux, routeurs, adresses flottantes, répartiteurs et secrets sont à vérifier à part.
  • Ordre de nettoyage réseau : ports et adresses flottantes, interfaces de routeur, routeurs, sous-réseaux, réseaux.
Un projet supprimé sans purge laisse des instances qui tournent et consomment, mais que plus personne ne peut atteindre sans droits d'administration.

Les étiquettes compensent ce que la hiérarchie ne dit pas : environnement, centre de coût, niveau de sensibilité, application. Elles servent ensuite à filtrer et à produire des rapports.
# Poser des étiquettes
openstack project set vitrine --domain nord \
  --tag env:prod --tag cout:cc-4410 --tag sens:interne

# Filtrer : tous les projets de production du domaine
openstack project list --domain nord --tags env:prod

# Ceux qui portent l'une OU l'autre étiquette
openstack project list --tags-any env:prod,env:rec

# Ceux qui n'en portent aucune : à corriger
openstack project list --domain nord --not-tags-any \
  env:prod,env:rec,env:dev

# Protéger un projet critique contre l'erreur de manipulation
openstack project set socle --domain nord --immutable
  • Convention à fixer une fois : des préfixes — env:, cout:, sens:, app: — évitent les variantes d'écriture.
  • Une étiquette n'a aucun effet technique : elle ne donne ni droit ni quota. C'est un classement.
  • Les services peuvent lire les étiquettes par l'API de Keystone ; un outil de facturation s'en sert pour ventiler les coûts.

2 · La hiérarchie

L'arbre de projets

Lecture : le domaine est la racine ; chaque projet a exactement un parent ; les projets sans enfant — les feuilles — sont en général ceux qui portent les ressources.
Rien n'oblige à mettre des ressources dans un nœud intermédiaire : « production » peut n'être qu'un dossier, qui sert à ranger et à porter des rôles hérités.

2 · La hiérarchieHéritage depuis le domaine : module 9

Les rôles hérités

  • Un rôle hérité se pose sur un nœud et s'applique en dessous : à tous ses descendants, présents et futurs — mais pas au nœud lui-même.
  • Pour avoir aussi le rôle sur le nœud, on ajoute une affectation directe : les deux se cumulent.
  • Posé sur le domaine, un rôle hérité couvre tous les projets du domaine.
  • Un nouveau sous-projet reçoit les droits sans rien faire : c'est tout l'intérêt, et aussi le risque — il faut savoir ce qui descend avant de créer.
2 · La hiérarchie

Direct ou hérité : commandes et lecture

# Hérité : les exploitants lisent toute la production
openstack role add --group exploitants --group-domain nord \
  --project production --project-domain nord \
  --inherited reader

# Direct : l'équipe web agit dans son projet seulement
openstack role add --group web-dev --group-domain nord \
  --project prod-web --project-domain nord member

# Hérité sur le domaine : l'audit lit tous les projets
openstack role add --group audit --group-domain nord \
  --domain nord --inherited reader
# Ce qui a été saisi sur un nœud
openstack role assignment list --names \
  --project production --project-domain nord
openstack role assignment list --names \
  --project production --project-domain nord --inherited

# Ce qui s'applique réellement sur une feuille
openstack role assignment list --names --effective \
  --project prod-web --project-domain nord
Affectation directeAffectation héritée
S'applique àla cible elle-mêmeles descendants de la cible
Nouveaux sous-projetsrien : à refairecouverts automatiquement
Lisibilitéévidenteexige --effective pour voir le résultat
Retrait d'un droit sur un seul enfantsimpleimpossible : l'héritage ne se « coupe » pas
Usage typeéquipes applicativesfonctions transverses : exploitation, audit, sécurité
Pas d'exception possible : on ne peut pas dire « hérité partout sauf ici ». Si une feuille doit échapper à un droit, elle n'est pas sous la bonne branche.
Règle simple : lecture en hérité, large ; écriture en direct, ciblée.
2 · La hiérarchie

Ce que la hiérarchie ne fait pas

On pourrait croire que…En réalité
un membre du parent voit les instances des enfantsnon : il lui faut un rôle hérité, ou direct, sur chaque enfant
le quota du parent borne les enfantsnon avec les quotas classiques ; oui seulement avec les limites unifiées en mode strict
les réseaux du parent sont accessibles aux enfantsnon : il faut un partage explicite
supprimer le parent supprime la branchenon : feuilles d'abord, et les ressources à part
la facture se cumule vers le hautà faire par l'outil de facturation, en lisant l'arbre
À retenir : la hiérarchie est un outil d'organisation des droits. Pour tout le reste — réseau, capacité, facturation — elle n'est qu'une information que d'autres mécanismes peuvent exploiter.

Consulter et manipuler l'arbre

# Prérequis : jeton d'administrateur ou de gestionnaire du domaine

# Construire une branche
openstack project create --domain nord production
openstack project create --domain nord \
  --parent production prod-web
openstack project create --domain nord \
  --parent production prod-bases

# Voir la position d'un projet
openstack project show prod-web --domain nord \
  -c id -c parent_id -c domain_id

# Ses ancêtres, sa descendance
openstack project show prod-web --domain nord --parents
openstack project show production --domain nord --children

# Les enfants directs d'un nœud
openstack project list --parent production --domain nord
# Tout l'arbre d'un domaine, sous forme lisible
openstack project list --domain nord --long \
  -c ID -c Name -c "Parent ID" -c Enabled

# Retirer une branche : feuilles d'abord
openstack project purge --project <id de prod-web>
openstack project delete <id de prod-web>
openstack project purge --project <id de prod-bases>
openstack project delete <id de prod-bases>
openstack project delete <id de production>
  • L'option --parent ne s'utilise qu'à la création : il n'existe pas de commande pour déplacer un projet.
  • Colonnes affichées : elles varient selon la version du client ; -f json donne toujours parent_id.
  • Pour un vrai dessin de l'arbre, exporter en JSON et le reconstruire avec un petit script : c'est un bon exercice de travaux pratiques.
Dans les commandes de suppression, préférer les identifiants : un nom se trompe plus facilement de domaine qu'un identifiant.
2 · La hiérarchie

Quand se servir de la hiérarchie

Elle apporte quelque chose quand…

  • Des fonctions transverses — exploitation, sécurité, audit — doivent avoir le même droit sur un ensemble de projets qui grandit.
  • Des projets naissent souvent : un rôle hérité évite d'oublier une affectation à chaque création.
  • Une capacité doit être partagée entre projets d'une même équipe, avec les limites unifiées en mode à deux niveaux.
  • Une branche doit pouvoir être suspendue ensemble — un environnement, une application en fin de vie : l'arbre donne la liste, on désactive les feuilles puis le nœud.
  • Les rapports se font par regroupement : coût par application, par environnement.

Elle complique sans rien apporter quand…

  • Il y a peu de projets, stables : des affectations directes se lisent mieux.
  • Chaque projet a sa propre équipe, sans fonction transverse.
  • L'arbre voudrait refléter l'organigramme : il change plus vite que les projets, et un projet ne se déplace pas.
  • On attend d'elle une isolation qu'elle ne fournit pas.
  • Les étiquettes suffisent au classement dont on a besoin.
BesoinHiérarchieÉtiquettesDomaines
Faire descendre un droitoui : rôles héritésnonoui, sur tout le domaine
Classer selon plusieurs axesun seul axe : l'arbreoui, autant d'axes que voulunon

3 · Les quotas

À quoi servent les quotas

Protéger la capacité

Aucun projet ne peut, par erreur ou par excès, épuiser les hyperviseurs, le stockage ou les adresses.

Répartir équitablement

La capacité achetée ou allouée à chaque équipe est matérialisée et opposable.

Borner les erreurs

Une boucle dans un script d'automatisation s'arrête au quota, pas à la saturation du cloud.

Maîtriser les coûts

Le plafond de consommation est aussi un plafond de dépense, connu d'avance.
Deux réglages distincts : le quota dit ce qu'un projet a le droit de demander ; la capacité dit ce que le cloud peut fournir. Les deux refus n'ont pas le même message d'erreur.
Chiffres d'illustration. Le rapport entre somme des quotas et capacité est un choix d'exploitation, à suivre dans le temps.

Quotas de calcul — Nova

QuotaCe qu'il plafonneDéfaut amont

  • Les trois premiers font tout le travail : une instance est refusée dès que l'un d'eux serait dépassé.
  • Le gabarit décide de la consommation : une instance « 4 cœurs, 8 Gio » retire 1, 4 et 8192 des trois compteurs.
  • Instance arrêtée : elle compte toujours. Seule une instance « remisée et déchargée » ne consomme plus cœurs ni mémoire.
# Quotas de calcul d'un projet
openstack quota show --compute prod-web

# Fixer
openstack quota set prod-web \
  --instances 40 --cores 160 --ram 327680
Cohérence à vérifier : 40 instances, 160 cœurs, 320 Gio correspondent à un gabarit moyen de 4 cœurs et 8 Gio. Des quotas incohérents entre eux rendent l'un des trois inutile.
Ce qui n'est pas plafonné ici : le disque éphémère des instances — sauf avec les limites unifiées — et les cartes graphiques ou autres ressources spéciales, qui se bornent par gabarits privés.
Valeurs par défaut du code amont, données de mémoire : celles de votre cloud se lisent avec openstack quota show --default.

Quotas réseau — Neutron

QuotaCe qu'il plafonneDéfaut amont

  • Le quota qui compte vraiment : les adresses flottantes. Elles puisent dans la plage du réseau externe, ressource rare et commune à tous.
  • Le quota qui bloque sans prévenir : les ports. Une instance sans port disponible échoue à la création avec une erreur réseau, pas une erreur de calcul.
openstack quota show --network prod-web
openstack quota set prod-web \
  --networks 10 --subnets 20 --routers 3 \
  --ports 300 --floating-ips 8 \
  --secgroups 30 --secgroup-rules 300
Règle de cohérence : prévoir au moins un port par instance autorisée, plus une marge pour routeurs, DHCP et répartiteurs. Avec 40 instances, 300 ports sont confortables ; 40 seraient un piège.
Somme des adresses flottantes : la somme des quotas de tous les projets ne devrait pas dépasser de beaucoup la taille de la plage externe ; c'est le seul quota que l'on évite de surallouer.
L'équilibrage de charge a ses propres quotas, dans son propre service, lorsqu'il est activé.
3 · Les quotas

Comment un quota est vérifié

  • La vérification se fait à l'entrée, dans l'API du service, avant toute planification : un refus de quota ne laisse aucune trace d'instance.
  • Le service compte lui-même la consommation à chaque demande — dans ses bases, ou auprès de Placement pour les cœurs et la mémoire.
  • Deux refus à distinguer : « Quota exceeded », code 403, vient du quota ; « No valid host », instance en erreur, vient de la capacité.
  • Opération composée : créer une instance avec un volume et une adresse flottante interroge trois quotas, dans trois services.

Quatre niveaux de cloisonnement

Les niveaux se cumulent, ils ne se remplacent pas. Deux projets d'un même domaine sont isolés pour les ressources, mais partagent un annuaire ; deux projets isolés partagent les mêmes hyperviseurs tant qu'on ne dit rien de plus.
Le projet est le niveau obligatoire : toute ressource appartient à un projet. Les trois autres se décident selon l'exigence — séparation d'annuaires, de flux, ou de machines physiques.

5 · Mise en œuvre

Pas à pas (1) : l'arbre et les rôles

# Étape 0 — prérequis : cloud Sunbeam déployé,
# client openstack installé, domaine « nord » créé
sunbeam openrc > admin-openrc
source admin-openrc
openstack domain show nord -c id -c enabled

# Étape 1 — les nœuds de l'arbre
for n in prod horsprod; do
  openstack project create $n --domain nord \
    --description "Branche $n" --tag role:noeud
done
openstack project create socle --domain nord \
  --tag env:commun

# Étape 2 — les feuilles : projet:parent:env:application
for f in prod-web:prod:prod:web prod-bases:prod:prod:bases \
  prod-data:prod:prod:data rec-web:horsprod:rec:web \
  dev-web:horsprod:dev:web dev-data:horsprod:dev:data; do
  IFS=: read p par env app <<< "$f"
  openstack project create $p --domain nord \
    --parent $par --tag env:$env --tag app:$app
done
# Étape 3 — les groupes
for g in exploitation-prod audit developpeurs \
         equipe-web equipe-data dba; do
  openstack group create $g --domain nord
done

# Étape 4 — rôles hérités sur les nœuds : groupe:rôle:nœud
for a in exploitation-prod:member:prod developpeurs:reader:prod \
  audit:reader:prod audit:reader:horsprod \
  exploitation-prod:reader:horsprod; do
  IFS=: read g r n <<< "$a"
  openstack role add $r --inherited --group $g \
    --group-domain nord --project $n --project-domain nord
done

# Étape 5 — rôles directs sur les feuilles : groupe:projet
for a in equipe-web:rec-web equipe-web:dev-web \
  equipe-data:dev-data dba:prod-bases; do
  IFS=: read g p <<< "$a"
  openstack role add member --group $g --group-domain nord \
    --project $p --project-domain nord
done

# Contrôle : l'arbre, puis les droits effectifs
openstack project show prod --domain nord --children
openstack role assignment list --effective \
  --project prod-web --project-domain nord --names
Si le domaine est raccordé à un annuaire (sunbeam ldap add-domain), les groupes viennent de l'annuaire : on saute l'étape 3 et l'on affecte les rôles aux groupes existants. Les automates de prod-web et prod-data reçoivent un identifiant d'application (module 8), pas un groupe.

Pas à pas (2) : quotas, réseau, vérification

# Étape 6 — quotas nuls sur les nœuds
for n in prod horsprod; do
  ID=$(openstack project show $n --domain nord -f value -c id)
  openstack quota set $ID --instances 0 --cores 0 \
    --ram 0 --volumes 0 --gigabytes 0 \
    --networks 0 --routers 0 --floating-ips 0
done

# Étape 7 — quotas des feuilles
ID=$(openstack project show prod-web --domain nord -f value -c id)
openstack quota set $ID \
  --instances 30 --cores 120 --ram 245760 \
  --volumes 60 --gigabytes 3000 --snapshots 60 \
  --networks 4 --subnets 8 --routers 1 --ports 100 \
  --floating-ips 4 --secgroups 20 --secgroup-rules 200

ID=$(openstack project show prod-bases --domain nord -f value -c id)
openstack quota set $ID \
  --instances 8 --cores 64 --ram 262144 \
  --volumes 32 --gigabytes 6000 \
  --networks 2 --routers 1 --ports 40 --floating-ips 0
Même schéma pour chaque feuille : les valeurs viennent du tableau de dimensionnement, jamais d'une copie du projet voisin.
# Étape 8 — réseau commun du socle, partagé au cas par cas
openstack network rbac create --type network \
  --action access_as_shared \
  --target-project prod-web  commun

# Étape 9 — vérifier les plafonds posés
openstack quota show --usage $ID

# Étape 10 — vérifier la cloison avec le compte de dana,
# membre de developpeurs et d'equipe-web (pas d'admin-openrc)
export OS_USERNAME=dana OS_USER_DOMAIN_NAME=nord \

read -s OS_PASSWORD && export OS_PASSWORD

  server create --flavor m1.small --image ubuntu essai
# attendu : 403 — la politique refuse la création

Revue et suivi de consommation

# Consommation et plafonds de chaque projet de production
for p in $(openstack project list --tags env:prod \
            -f value -c ID); do
  openstack quota show --usage $p
done

# Heures consommées sur une période, par projet
openstack usage list --start 2026-09-01 --end 2026-10-01

# Capacité réelle, côté hyperviseurs
openstack hypervisor list --long

# Qui a quoi : toutes les affectations d'une branche
openstack role assignment list --names \
  --project prod --project-domain nord --inherited

  • Deux regards : la plateforme vérifie la capacité, le propriétaire du projet confirme les droits.
  • Avant de supprimer un projet : vider ses ressources dans chaque service — Keystone ne le fait pas.

Bonnes pratiques et erreurs fréquentes

À faire

  • Dessiner l'arbre avant de créer : le parent est définitif.
  • Un projet par application et par environnement, même pour une petite application.
  • Baisser les quotas par défaut avant d'ouvrir le cloud : un projet neuf ne doit rien pouvoir consommer d'important.
  • Affecter les rôles à des groupes, jamais à des personnes.
  • Réserver l'héritage aux populations transversales ; les équipes applicatives reçoivent des rôles directs.
  • Décrire l'organisation en code — Terraform ou scripts versionnés : l'arbre, les rôles et les quotas se relisent et se rejouent.
  • Tester la cloison avec un compte ordinaire après chaque changement.
  • Garder un projet de démonstration à part : celui que crée sunbeam configure n'a rien à faire en production.

Règle d'or : chaque projet a un propriétaire, un usage et un plafond connus.
Synthèse

Ce qu'il faut retenir

Le projet et l'arbre

  • Toute ressource appartient à un projet ; l'isolation est faite par chaque service.
  • L'arbre range et fait descendre des rôles ; il ne donne aucune visibilité du parent sur l'enfant.
  • Parent définitif, noms uniques dans le domaine.
  • Rôle hérité : s'applique en dessous, pas au nœud.

Les quotas

  • Un plafond par projet, par ressource, par service.
  • Vérifiés à l'entrée de l'API ; ils ne réservent rien.
  • Les valeurs par défaut sont le réglage le plus important.
  • Limites unifiées : valeurs dans Keystone, modèle plat ou à deux niveaux.

L'organisation

  • Quatre niveaux : domaine, projet, réseau, matériel.
  • Croiser application et environnement.
  • Arbre par environnement ou par application, selon qui a besoin du droit transversal.
  • Un socle pour le commun ; rien d'écrit des deux côtés de la cloison.
QuestionRéponse courte
Quand créer un projet ?dès qu'une application, un environnement ou un niveau de sensibilité diffère
Quand créer un sous-projet ?quand un même droit doit couvrir plusieurs projets, ou qu'un plafond commun doit les coiffer
Comment fixer un quota ?besoin en pointe, plus 20 à 30 % ; cohérent entre calcul, stockage et réseau ; revu chaque mois
Sur Sunbeam ?sunbeam openrc pour les identifiants d'administration ; tout le reste par l'API d'OpenStack, de préférence en code versionné
