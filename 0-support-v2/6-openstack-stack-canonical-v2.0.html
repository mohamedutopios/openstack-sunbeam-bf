Les formats de livraison de Canonical

Paquet deb

Le format historique d'Ubuntu. Dépendances partagées avec le système, mises à jour par apt. Les services OpenStack sont d'abord empaquetés ainsi dans l'archive Ubuntu.Où : à l'intérieur des rocks et des snaps

Snap

Application confinée, livrée avec ses dépendances, mise à jour de façon transactionnelle par canaux avec retour arrière. Indépendante de la version du système.Où : MAAS, Juju, Sunbeam, hyperviseur, MicroCeph, MicroOVN, Kubernetes

Rock

Image de conteneur au format OCI, construite par Canonical à partir de paquets Ubuntu, avec le gestionnaire de processus Pebble.Où : chaque service du plan de contrôle, dans un pod

Charm

Un opérateur : du code Python qui sait installer, configurer, relier, mettre à l'échelle et mettre à jour une application. Publié sur Charmhub.Où : un charm par rock et par snap à piloter

Des opérations pilotées par un modèle

Le point commun des trois briques : on ne décrit pas les étapes à exécuter, on décrit l'état voulu, et un contrôleur se charge d'y arriver puis de s'y maintenir.

BriqueCe que l'on déclareQui réalise
MAAS« cette machine doit être déployée en Ubuntu 24.04, avec ce partitionnement et ces interfaces »les contrôleurs de région et de rack
Juju« le modèle contient Keystone en trois unités, relié à MySQL »le contrôleur Juju et les charms
Sunbeam« ce cloud a ces nœuds, ces rôles, ces fonctionnalités »Sunbeam, qui pilote Juju
  • Ce que cela change : pas de fichier de configuration édité à la main sur un serveur ; toute modification passe par le modèle.
  • Ce que cela exige : faire confiance aux choix intégrés dans les charms, et savoir lire l'état du modèle pour diagnostiquer.

2 · MAAS

MAAS : rôle et principe

Le problème résolu : installer un système sur cent serveurs, à l'identique, sans clé USB ni console, et pouvoir recommencer à volonté.

  • Découvre les serveurs qui démarrent sur le réseau et dresse leur inventaire matériel : processeurs, mémoire, disques, cartes réseau, micrologiciels.
  • Pilote l'alimentation par la carte de gestion de chaque serveur (IPMI, Redfish).
  • Installe un système d'exploitation en quelques minutes : Ubuntu, mais aussi CentOS, RHEL, Oracle Linux, Windows, VMware ESXi.
  • Configure le stockage (partitions, LVM, RAID logiciel) et le réseau (agrégats, VLAN, ponts) avant l'installation.
  • Fournit les services réseau nécessaires : DHCP, DNS, NTP, amorçage, mandataire de paquets.
  • Expose tout par API : interface web, ligne de commande, Juju, Terraform.
Ce que MAAS n'est pas : un outil de configuration d'applications. Il s'arrête au système installé et joignable en SSH.

Prérequis à vérifier avant tout : un réseau où MAAS est le seul serveur DHCP, l'amorçage réseau activé dans chaque serveur, et un accès aux cartes de gestion.

Enrôlement et inventaire, pas à pas

Deux façons d'enrôler : laisser le serveur démarrer sur le réseau, MAAS le découvre seul ; ou le déclarer à la main avec l'adresse de sa carte de gestion, ce qui lance directement l'inventaire.
Premier diagnostic quand rien ne se passe : le serveur a-t-il reçu une adresse ? Un autre serveur DHCP répond-il sur ce VLAN ? L'amorçage réseau est-il en tête dans le micrologiciel ?
2 · MAAS

Déploiement : de « Ready » à un système en service

Ce qu'il faut retenir

  • Une copie d'image, pas une installation paquet par paquet : c'est ce qui rend le déploiement rapide et identique d'une machine à l'autre.
  • Le réseau et les disques se décident dans MAAS, avant le déploiement ; le système arrive déjà configuré.
  • cloud-init est le point d'entrée de la personnalisation : c'est par lui que Juju installe son agent.
  • Variantes : déploiement en mémoire seule, sans toucher aux disques (depuis 3.5) ; enregistrement d'une machine déjà installée, sans la réinstaller.

Le modèle réseau de MAAS

La plage dynamique sert à l'enrôlement et à l'inventaire. Une machine déployée reçoit en général une adresse fixe, choisie par MAAS hors de cette plage et inscrite dans le DNS.
Les espaces sont la clé de l'intégration : Juju et Sunbeam ne manipulent pas des VLAN mais des espaces. « Place ce service sur l'espace interne » fonctionne quel que soit l'adressage du site.

2 · MAAS

MAAS en pratique : installation et commandes

Prérequis : une machine Ubuntu Server 24.04 dédiée, une interface sur le réseau d'amorçage, aucun autre serveur DHCP sur ce réseau.

# 1 · Installer (maquette : base de test intégrée)
sudo snap install maas --channel=3.7/stable
sudo snap install maas-test-db
sudo maas init region+rack \
  --database-uri maas-test-db:///
sudo maas createadmin

# 2 · Ouvrir une session en ligne de commande
sudo maas apikey --username admin > cle.txt
maas login admin \
  http://10.10.0.2:5240/MAAS/api/2.0/ $(cat cle.txt)

# 3 · Dans l'interface web : importer les images,
#     activer le DHCP sur le VLAN d'amorçage,
#     définir la plage dynamique
En production, la base de test est remplacée par un PostgreSQL externe : version 16 recommandée, la 14 étant le minimum, déjà dépréciée.
# Inventaire
maas admin machines read | jq '.[].hostname'

# Étiqueter
maas admin tags create name=compute
maas admin tag update-nodes compute add=$ID

# Relancer l'inventaire d'une machine
maas admin machine commission $ID

# Réserver puis déployer
maas admin machines allocate tags=compute
maas admin machine deploy $ID \
  distro_series=noble

# Rendre au parc en effaçant les disques
maas admin machine release $ID erase=true
  • $ID est l'identifiant système de la machine (system_id), visible dans l'inventaire.
  • Tout ce que fait l'interface web passe par la même API : ce qui se clique se scripte.

2 · MAAS

MAAS : avantages et limites

Avantages

  • Complet : découverte, inventaire, tests, réseau, stockage et installation dans un seul outil, avec DHCP et DNS intégrés.
  • Rapide : une machine passe de « Ready » à « Deployed » en quelques minutes.
  • Piloté par API, donc par Juju, Terraform, Ansible ou vos scripts.
  • Multi-systèmes : Ubuntu d'abord, mais aussi d'autres Linux, Windows et ESXi.
  • Indépendant du reste : utile même sans OpenStack, pour un parc Kubernetes ou des serveurs de calcul.
  • Libre, sans limite de nombre de machines.

Limites

  • Exige la maîtrise du réseau d'amorçage : cohabiter avec un DHCP d'entreprise demande un relais et de la rigueur.
  • Dépend de la qualité des cartes de gestion : micrologiciels anciens ou exotiques sont la première source d'échecs.
  • Un service de plus à rendre redondant et à sauvegarder, avec sa base PostgreSQL.
  • Images non Ubuntu : à construire soi-même ; certaines relèvent de l'abonnement.
  • Ne configure pas les commutateurs : VLAN et agrégats doivent exister côté réseau avant.

Quand l'utiliser

Dès que le parc dépasse une dizaine de machines, ou que l'on veut pouvoir reconstruire un nœud sans intervention manuelle.

Quand s'en passer

Maquette sur une à trois machines, ou parc déjà géré par un autre outil de provisionnement que l'on ne veut pas remplacer.

Choix irréversible dans Sunbeam

Le fournisseur de machines — manuel ou MAAS — se décide à la conception : on ne peut pas en changer une fois le cloud déployé.

3 · Juju

Juju : rôle et principe

Le problème résolu : installer un logiciel est facile ; le relier aux autres, le faire évoluer et le maintenir pendant des années ne l'est pas.

  • Un charm par application : il contient tout ce qu'un spécialiste saurait faire — installer, configurer, initialiser la base, mettre à jour, sauvegarder.
  • Des relations entre applications : « Keystone a besoin d'une base » se dit en une commande ; les deux charms échangent adresses et identifiants sans intervention.
  • Un modèle, plusieurs substrats : la même commande déploie sur MAAS, sur LXD, sur un cloud public ou sur Kubernetes.
  • Tout le cycle de vie : mise à l'échelle, changement d'option, montée de version, actions ponctuelles.
Idée centrale : Juju ne sait rien d'OpenStack ni de PostgreSQL. Il transmet des événements ; c'est le charm qui sait quoi faire.

class DemoCharm(ops.CharmBase):
  def __init__(self, framework):
    super().__init__(framework)
    framework.observe(self.on.config_changed,

3 · Juju

Les relations : le cœur de Juju

  • Une relation n'est possible qu'entre interfaces identiques : un demandeur mysql_client ne se branche que sur un fournisseur mysql_client. C'est un contrat.
  • Elle vit dans le temps : si l'adresse de la base change ou si une unité s'ajoute, l'autre côté est prévenu et se reconfigure seul.
  • La retirer (juju remove-relation) déclenche le nettoyage : compte supprimé, service reconfiguré.
  • Relation entre modèles : une application peut être offerte à un autre modèle, voire à un autre contrôleur — la supervision ou un Vault partagé, par exemple.
  • Relation « pair » : entre les unités d'une même application, pour former une grappe.
  • Dans Canonical OpenStack : plusieurs dizaines de relations sont créées pour vous ; juju status --relations les montre toutes.

3 · Juju

Charmhub : pistes, canaux, révisions

  • Piste (track) : une ligne de versions du logiciel. Pour les charms d'OpenStack, la piste porte le nom de la version : 2024.1, 2026.1.
  • Risque : stable pour la production, candidate et beta pour valider, edge pour le dernier état du développement.
  • Canal = piste + risque : 2026.1/stable.
  • juju refresh fait passer une application à la dernière révision de son canal, ou vers un autre canal.

Prérequis : un poste Ubuntu, un cloud joignable (ici MAAS) et sa clé d'API.

Juju au-dessus de MAAS : ce que déclenche « juju deploy »

Les contraintes font le lien : tags=, mem=, cores=, zones=, spaces= sont traduites en critères de sélection dans l'inventaire de MAAS.

  • Les « séries » (remplacées par les bases), les charms Kubernetes d'ancienne génération, le fournisseur KVM.

Politique de versions

  • Une version mineure environ tous les trois mois, des correctifs mensuels.
  • Une version mineure reçoit des correctifs pendant quatre mois, puis deux mois de correctifs de sécurité seulement.
  • À chaque version majeure, la dernière mineure de la série précédente devient version à long terme, avec des correctifs de sécurité annoncés sur quinze ans.

  • Pas de mise à jour en place du contrôleur : on crée un contrôleur 4.0 et on y migre les modèles.
  • Un guide « 3.6 vers 4.0 » est publié (4.0.15 en octobre 2026). Il liste surtout les ruptures à traiter avant : enable-ha et upgrade-machine retirés, espaces MAAS explicites. À dérouler d'abord en maquette.

3 · Juju

Juju : avantages et limites

Avantages

  • Le savoir-faire est dans le charm : une petite équipe exploite des logiciels complexes sans en maîtriser chaque détail.
  • Les relations suppriment toute une classe d'erreurs : adresses, comptes et secrets ne sont plus recopiés à la main.
  • Un seul outil pour les machines et pour Kubernetes, et pour tout le cycle de vie.
  • État lisible : juju status donne une vue complète et homogène, quelle que soit l'application.
  • Catalogue de charms maintenus par Canonical : bases de données, supervision, identité, stockage.

Limites

  • Boîte noire relative : comprendre pourquoi un charm est bloqué demande parfois de lire son code.
  • Options limitées à ce que le charm expose : un réglage non prévu ne se fait pas proprement.
  • Compétence rare sur le marché, comparée à Ansible ou Kubernetes.
  • Le contrôleur est critique : à rendre redondant, à sauvegarder, à mettre à jour avec soin.
  • Écosystème centré sur Ubuntu : peu de charms pour d'autres systèmes.
  • Transition 3.x vers 4.0 à planifier : changement de base d'état, commandes retirées.

À retenir sur le modèle

Contrôleur, modèle, application, unité, relation : cinq mots suffisent à lire n'importe quel déploiement.

À retenir sur les charms

Un charm réagit à des événements. Son état — active, waiting, blocked — dit où regarder.

À retenir pour la suite

Canonical OpenStack est un ensemble de charms. Savoir lire Juju, c'est savoir diagnostiquer le cloud.

  • Pose les questions de configuration, ou lit un manifeste.
  • Active les fonctionnalités optionnelles, met à jour, ajoute et retire des nœuds.

Réseaux : deux réseaux physiques, six réseaux « cloud »

Le minimum : deux réseaux physiques

  • Générique : provisionnement, gestion et accès aux API.
  • Externe : adresses flottantes et sortie des instances vers l'extérieur.

Avec MAAS : une isolation plus fine

  • Chaque sous-réseau est rangé dans un espace ; chaque espace est associé à un réseau « cloud » par sunbeam deployment space map.
  • Un seul espace pour tout : aucune isolation. Six espaces : séparation complète.
  • Plages d'adresses à réserver dans MAAS, nommées <nom>-internal-api et <nom>-public-api : dix à vingt adresses chacune, pour les points d'accès.
Réseau externe : sur l'interface qui y est branchée, laisser le sous-réseau « non configuré » dans MAAS et poser l'étiquette réseau neutron:physnet1. C'est OVN qui s'en servira, pas le système hôte.

Installation avec le fournisseur manuel

Prérequis, avant toute commande

  • Une machine physique dédiée, Ubuntu Server 24.04 LTS fraîchement installé, architecture amd64.
  • Deux réseaux physiques avec accès à Internet (ou un mandataire).
  • Un nom de machine pleinement qualifié qui se résout.
  • Pour le stockage : au moins un disque vierge, sans partition.
  • Une plage d'adresses libre pour les points d'accès.
# Première machine
snap info openstack                  # canaux disponibles
sudo snap install openstack --channel 2026.1/stable
sunbeam prepare-node-script --bootstrap \
  | bash -x && newgrp snap_daemon
sunbeam cluster bootstrap \
  --role control,compute,storage
sunbeam configure --openrc demo-openrc
Succès du bootstrap : le message « Node has been bootstrapped with roles: storage, compute, control ».
# Ajouter une machine — sur la première :
sunbeam cluster add cloud-2.exemple.lan \
  --output cloud-2.asc
# copier cloud-2.asc sur la nouvelle machine, puis, sur celle-ci :
sudo snap install openstack --channel 2026.1/stable
sunbeam prepare-node-script | bash -x \
  && newgrp snap_daemon
cat cloud-2.asc | sunbeam cluster join \
  --role control,compute,storage -

# Après l'ajout de nœuds « control » :
sunbeam cluster resize

Disponibilité, zones, régions

Ce qui est redondé dans un cloud à trois nœuds de contrôle

5 · Avantages, limites, support

Avantages de la stack Canonical

Du serveur nu au cloud, un seul fournisseur

MAAS, Juju, Kubernetes, Ceph, OVN, OpenStack et le système viennent du même éditeur, sont testés ensemble et suivent le même calendrier.

Démarrage très court

Un cloud fonctionnel sur une machine en quelques commandes, puis extension par ajout de nœuds, sans réinstallation.

Le même outil à toutes les tailles

De la maquette sur un poste au cloud de plusieurs baies : mêmes commandes, mêmes charms, mêmes procédures.

Peu de décisions à prendre

Hyperviseur, réseau virtuel, stockage, base, bus : les choix sont faits et intégrés. L'équipe se concentre sur l'usage du cloud.

Gratuit sans contrat, supportable ensuite

Le logiciel est le même avec ou sans abonnement. On peut démarrer seul et souscrire plus tard, sans migration.

Versions à très long terme

Une version LTS tous les deux ans : cinq ans de maintenance, jusqu'à douze avec Ubuntu Pro et Legacy Support. Peu de montées de version imposées.

Avantages techniques

  • Plan de contrôle en pods : redémarrage, répartition et mises à jour progressives assurés par Kubernetes.
  • Services découplés du système hôte : rocks et snaps embarquent leurs dépendances.
  • Mises à jour transactionnelles des snaps, avec retour arrière.
  • Relations Juju : aucune adresse ni mot de passe recopié à la main entre services.

Avantages d'organisation

  • Petite équipe possible : le savoir-faire d'exploitation est dans les charms.
  • Code ouvert et gouverné en amont : Sunbeam est un projet officiel d'OpenStack.
  • Tarification par nœud pour l'abonnement, lisible et prévisible.
  • Briques réutilisables pour d'autres usages : MAAS et Juju servent aussi pour Kubernetes ou des bases de données.

Cycle de vie des versions de Canonical OpenStack

  • Deux versions par an, en général en avril et en octobre, alignées sur le calendrier d'OpenStack.
  • Versions LTS de Sunbeam : 2024.1 et 2026.1 ; la prochaine est 2028.1, 2027.1 étant une version intermédiaire.
  • Système hôte : 2024.1 et 2025.1 sur Ubuntu 24.04 ; 2026.1 sur Ubuntu 24.04 ou 26.04.
  • Maintenance standard : cinq ans sur une LTS, sans abonnement.
  • Ubuntu Pro : cinq ans de plus ; Legacy Support : deux ans encore, soit douze au total.
  • Versions intermédiaires : quelques mois seulement. Une production se pose sur une LTS.
Dates relevées dans la page « Release cycle and supported versions » de la documentation 2026.1 ; la page commerciale de Canonical évoque jusqu'à quinze ans de correctifs de sécurité. Vérifier la disponibilité d'un canal avec snap info openstack.
5 · Avantages, limites, support

Modèle de support : quatre niveaux d'engagement

  • Deux périmètres d'abonnement : « Infra-only », qui couvre le système et l'infrastructure, ou complet, qui ajoute les applications. Les deux ouvrent droit au support de Canonical OpenStack.
  • Entre support et cloud géré : une formule intermédiaire d'astreinte, où les ingénieurs de Canonical interviennent sur vos incidents critiques pendant que votre équipe exploite.
  • Ce que l'abonnement ne remplace pas : une équipe qui connaît le cloud. Le support traite les anomalies, pas l'exploitation courante.
  • Hors support : les paquets OpenStack installés à la main depuis les archives reçoivent des correctifs de sécurité, pas d'assistance complète.
Tarifs et contenu exact des formules : non reproduits ici, ils changent. Demander un devis ; la tarification se fait par nœud.

Quand choisir cette stack — et quand l'éviter

Elle convient bien si…

  • Vos serveurs tournent déjà sous Ubuntu, ou rien n'impose un autre système.
  • Vous partez de zéro : pas de réseau virtuel à réutiliser, stockage Ceph ou baie prise en charge.
  • L'équipe est réduite et veut un résultat rapide avec peu de décisions.
  • Vous voulez démarrer sans budget logiciel et garder la possibilité de souscrire plus tard.
  • Vous cherchez des versions à très long terme.
  • Le cloud doit pouvoir commencer petit : trois nœuds, puis grandir.
  • Vous exploitez déjà MAAS ou Juju pour autre chose.

Mieux vaut regarder ailleurs si…

  • Une des limites listées slide 51 est bloquante : baie non prise en charge, autre réseau virtuel, matériel hors amd64, réseau strictement isolé.
  • La politique impose RHEL, OpenShift ou un Kubernetes déjà en place.
  • L'équipe, experte en Ansible, veut régler chaque service et embarquer ses propres correctifs.
  • Vous cherchez la plus grande liberté de choix techniques : Kolla-Ansible ou OpenStack-Ansible s'y prêtent mieux (module 5).

Points d'attention sur un poste de travail

  • Virtualisation imbriquée : à activer sur l'hyperviseur du poste pour que les instances utilisent KVM ; sinon elles tournent en émulation, très lentement.
  • Réseau d'amorçage pour MAAS : un réseau interne sans le serveur DHCP de l'outil de virtualisation ; les machines virtuelles démarrent sur le réseau en premier.
  • Pilotage de l'alimentation : sans carte de gestion, déclarer le type « manuel » dans MAAS et démarrer les machines virtuelles à la main.
  • Disques pour Ceph : ajouter un second disque virtuel, vierge, à chaque nœud de stockage.
  • Accès à Internet : indispensable pendant l'installation — snaps, charms et images sont téléchargés.
  • Nom de machine : pleinement qualifié, résolu localement, fixé avant l'installation.
Ne pas extrapoler : une maquette prouve le fonctionnement et les procédures, pas les performances ni la tenue à la panne.
