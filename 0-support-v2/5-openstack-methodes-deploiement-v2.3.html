Introduction

Objectif et déroulé

Objectif : savoir situer chaque méthode de déploiement d'OpenStack — ce qu'elle automatise, sur quoi elle s'appuie, ce qu'elle exige de l'équipe — et disposer d'une démarche pour choisir.

À l'issue de ce module, vous saurez :

  • Décomposer un déploiement en couches et dire quel outil couvre laquelle.
  • Classer les méthodes selon trois axes : forme de livraison, orchestrateur, socle d'exécution.
  • Décrire le fonctionnement de DevStack, Kolla-Ansible, OpenStack-Ansible, OpenStack-Helm, Sunbeam, RHOSO et MOSK.
  • Distinguer outil communautaire, distribution supportée et offre gérée.
  • Comparer les méthodes sur l'exploitation : montée de version, personnalisation, fonctionnement déconnecté.
  • Appliquer une grille de critères et un arbre de décision à un contexte donné.

1 · Ce que « déployer » veut dire

Avant, pendant, après : le déploiement est un cycle

Ce que cela change dans le choix

  • Une démonstration juge le jour 1 ; l'exploitation se joue au jour 2. Une installation en vingt minutes ne dit rien de la montée de version dans deux ans.
  • L'outil choisi au départ devient le seul chemin pour modifier le cloud : toute intervention manuelle hors outil sera écrasée à la prochaine exécution.
  • Changer de méthode en cours de vie revient presque toujours à reconstruire un cloud à côté et à migrer les charges.

2 · Apprendre et développer

DevStack : le cloud du développeur

Principe : un ensemble de scripts shell qui clone les dépôts de chaque service, installe leurs dépendances et lance tout sur une seule machine, à partir des sources.

  • Pour qui : contributeurs au code d'OpenStack, tests d'intégration, découverte des API.
  • Ce qu'il installe : Keystone, Glance, Placement, Nova, Neutron (OVN), Cinder (LVM sur fichier), Horizon ; d'autres services par greffons.
  • Comment : chaque service devient une unité systemd devstack@<service> ; les journaux se lisent avec journalctl.
  • Atout : n'importe quelle branche, n'importe quel correctif en cours de revue, en une variable.
Jamais en production : pas de haute disponibilité, mots de passe simples, système hôte profondément modifié, aucune procédure de montée de version. Un redémarrage de la machine peut laisser le cloud inutilisable.
À lancer sur une machine jetable : une machine virtuelle dédiée, jamais son poste de travail.

DevStack en pratique

# 0. Prérequis : une VM Ubuntu 24.04 neuve, 8 Go de RAM,
#    4 vCPU, 60 Go de disque, accès à Internet

# 1. Créer l'utilisateur dédié
sudo useradd -s /bin/bash -d /opt/stack -m stack
sudo chmod +x /opt/stack
echo "stack ALL=(ALL) NOPASSWD: ALL" | sudo tee /etc/sudoers.d/stack
sudo -u stack -i

# 2. Récupérer DevStack sur la branche voulue
git clone https://opendev.org/openstack/devstack -b stable/2026.2
cd devstack

# 3. Écrire local.conf (ci-contre), puis lancer
./stack.sh

# 4. Utiliser
source openrc admin admin
openstack service list
# local.conf
[[local|localrc]]
ADMIN_PASSWORD=secret
DATABASE_PASSWORD=$ADMIN_PASSWORD
RABBIT_PASSWORD=$ADMIN_PASSWORD
SERVICE_PASSWORD=$ADMIN_PASSWORD
HOST_IP=192.168.56.10

# Ajouter un service par greffon
enable_plugin heat https://opendev.org/openstack/heat stable/2026.2

Les installations tout-en-un

La plupart des outils de production proposent un mode « une seule machine ». On y retrouve les mêmes conteneurs, les mêmes fichiers et les mêmes commandes qu'en production : c'est le meilleur terrain d'apprentissage d'un outil donné.

Limite commune : aucune haute disponibilité, un seul hyperviseur, stockage sur fichier ou sur disque local. On y apprend l'outil et les API, pas le comportement en panne.
Pour aller plus loin sans matériel : trois à cinq machines virtuelles avec virtualisation imbriquée permettent de monter un vrai plan de contrôle redondant et de simuler la perte d'un nœud.
2 · Apprendre et développer

L'installation manuelle : comprendre avant d'automatiser

Le même enchaînement pour chaque service

1Créer la base de données et son compte
2Créer l'utilisateur de service dans Keystone, lui donner le rôle admin sur le projet service
3Enregistrer le service et ses points d'accès dans le catalogue
4Installer les paquets
5Renseigner le fichier de configuration : base, bus, Keystone
6Initialiser le schéma (<service>-manage db sync)
7Démarrer et activer les services, puis vérifier
  • Valeur pédagogique irremplaçable : on voit de ses yeux ce que tout outil automatise — et où chercher quand il échoue.
  • Source : le guide d'installation officiel, décliné pour Ubuntu, Debian et les distributions de la famille Red Hat.
  • Résultat : un contrôleur et un nœud de calcul, sans redondance ni chiffrement.
Pas une méthode de production : non reproductible, sans haute disponibilité, et chaque montée de version serait à refaire à la main, service par service, sur chaque machine.

Kolla-Ansible : un conteneur par processus

À retenir : les images sont construites à l'avance par le projet Kolla ; Kolla-Ansible se contente de générer la configuration, de tirer les images et de démarrer les conteneurs. Mettre à jour un service, c'est remplacer son image.
3 · Outils communautaires

Kolla-Ansible : déroulé d'un déploiement

Prérequis, avant toute commande

  • Hôtes en CentOS Stream 10, Debian 13, Rocky Linux 10 ou Ubuntu 24.04 (série 2026.1 ; pas d'images Kolla pour CentOS Stream 10), accessibles en SSH par clé avec élévation de privilèges.
  • Par nœud de test : 8 Go de mémoire, 40 Go de disque, deux interfaces réseau.
  • Une adresse virtuelle libre sur le réseau interne, pour HAProxy.
  • Une interface sans adresse IP pour le réseau externe de Neutron.

python3 -m venv ~/kolla-venv

prechecks avant chaque deploy : il détecte un port déjà occupé, une adresse virtuelle déjà utilisée ou une interface absente avant qu'un conteneur ne soit lancé.

Kolla-Ansible : le modèle de configuration

# /etc/kolla/globals.yml — extrait
kolla_base_distro: "rocky"
kolla_internal_vip_address: "10.20.0.10"
network_interface: "bond0.20"

Trois niveaux de réglage

  • globals.yml — les choix d'architecture : interfaces, adresse virtuelle, services activés. Quelques dizaines de lignes suffisent.
  • /etc/kolla/config/ — n'importe quelle option d'un service. Un fichier nova.conf déposé ici est fusionné avec celui que génère l'outil ; un sous-dossier au nom d'un hôte limite la surcharge à cet hôte.
  • Images — pour un correctif de code ou un pilote tiers, on reconstruit l'image avec kolla-build et on la pousse dans son registre.

Kayobe : Kolla-Ansible depuis la machine nue

kayobe control host bootstrap
kayobe seed host configure
kayobe seed service deploy          # lance Bifrost
kayobe overcloud inventory discover
kayobe overcloud provision          # installe le système
kayobe overcloud host configure     # réseau, disques, noyau
kayobe overcloud service deploy     # Kolla-Ansible
  • Ce que Kayobe ajoute : les couches 2 et 3 — installation du système par PXE, liaisons réseau agrégées, VLAN, partitionnement, pare-feu, utilisateurs.
  • Ce qu'il ne change pas : les services restent ceux de Kolla-Ansible, avec les mêmes images et les mêmes fichiers de surcharge.
  • Intérêt : toute l'infrastructure décrite dans un seul dépôt git, de la configuration du commutateur d'un port jusqu'à une option de Nova.
  • Livré par le projet Kolla, donc versionné avec lui.

OpenStack-Ansible : des services isolés dans des conteneurs LXC

À retenir : OpenStack-Ansible ne télécharge pas d'images. Il construit les services depuis les sources au moment du déploiement, dans des conteneurs système qui se comportent comme de petites machines ; un mode sans conteneur (« metal ») existe aussi.

3 · Outils communautaires

OpenStack-Helm : déroulé et points d'attention

Prérequis, avant toute commande

  • Un cluster Kubernetes 1.33 à 1.35 sur Ubuntu 24.04 : la combinaison testée par le projet pour OpenStack 2025.1 à 2026.1.
  • Réseau de pods, contrôleur d'entrée, classe de stockage par défaut, adresses de service.
  • helm et kubectl sur le poste d'administration.

Ordre d'installation des charts

  • Socle : RabbitMQ, MariaDB, Memcached.
  • Cœur : Keystone, Heat, Glance, Cinder.
  • Calcul et réseau : Open vSwitch, libvirt, Placement, Nova, Neutron.
  • Interface : Horizon.
OpenStack-Helm est une boîte de charts, pas un produit : le cluster, son stockage, ses sauvegardes et l'enchaînement des charts restent à assembler et à maintenir.
# Dépôt de charts et greffon d'aide
helm repo add openstack-helm \
  https://tarballs.opendev.org/openstack/openstack-helm
helm plugin install \
  https://opendev.org/openstack/openstack-helm-plugin

# Répartition des rôles par étiquettes
kubectl label --overwrite nodes --all \
  openstack-control-plane=enabled
kubectl label --overwrite nodes --all \
  openstack-compute-node=enabled

# Un service = une installation de chart
helm upgrade --install keystone openstack-helm/keystone \
  --namespace=openstack \
  $(helm osh get-values-overrides -c keystone ${FEATURES})
helm osh wait-for-pods openstack

Sur Kubernetes : les assemblages construits au-dessus des charts

Kolla-Ansible

  • Images prêtes, un conteneur par processus.
  • Déploiement et montée de version rapides et reproductibles.

Communautaire ou éditeur : ce que l'on achète vraiment

Une souscription n'achète pas le logiciel — il est libre. Elle achète quatre services, qu'il faut sinon produire en interne.

Correctifs rétroportés

Les failles et anomalies sont corrigées dans votre version, pendant des années, sans vous imposer de monter de version pour un correctif.

Combinaisons certifiées

Matériel, pilotes de stockage et de réseau, systèmes invités : une matrice testée, et un engagement de l'éditeur si elle ne fonctionne pas.

Durée de vie longue

Une version amont est maintenue environ dix-huit mois. Un éditeur la maintient plusieurs années : moins de montées de version, mieux préparées.

Un responsable à appeler

Délai d'intervention contractuel, escalade jusqu'aux développeurs, et un seul interlocuteur pour le système, Ceph et OpenStack.

Ce que l'on cède en échange

  • Le rythme : les nouveautés arrivent quand l'éditeur les intègre, parfois plusieurs versions après l'amont.
  • Les choix techniques : système hôte, réseau virtuel et stockage sont ceux que l'éditeur supporte.
  • La liberté de modifier : un correctif maison ou un pilote non certifié peut faire sortir du support.
  • Le budget : coût récurrent, généralement par nœud ou par processeur.

Trois questions pour trancher

  • Avez-vous, en interne, quelqu'un capable de lire le code d'un service et de proposer un correctif en amont ?
  • Pouvez-vous tenir un rythme d'une montée de version par an au minimum ?
  • Une réglementation ou un client vous impose-t-il un support contractuel ?
Deux « non » puis un « oui » : une distribution supportée ou une offre gérée s'impose. La voie intermédiaire existe : outil communautaire, plus un contrat avec un intégrateur.

Montées de version : le vrai test d'une méthode

Ce que fait toute montée de version

  • Plan de contrôle d'abord : nouveau code, migration du schéma des bases, redémarrage des API une à une.
  • Nœuds de calcul ensuite, par lots : les agents acceptent de dialoguer avec un contrôleur plus récent qu'eux.
  • Les machines virtuelles continuent de tourner : seule l'API est brièvement perturbée, pas le trafic des instances.
  • Pas de retour en arrière simple : une fois le schéma migré, revenir exige de restaurer la sauvegarde.

Stockage : trois façons d'intégrer Ceph

Ce que l'outil doit toujours faire, quel que soit le mode

  • Distribuer ceph.conf et les clés à Glance, Cinder et Nova.
  • Déclarer le secret libvirt sur chaque hyperviseur, pour que QEMU ouvre les volumes.
  • Configurer les pools attendus : images, volumes, sauvegardes, disques éphémères.

Et quand le stockage n'est pas Ceph

  • Baie du commerce : vérifier que le pilote Cinder est dans l'image ou le paquet livré, et que l'éditeur le supporte.
  • LVM local : suffisant pour une maquette ; un seul nœud porte les volumes, sans redondance.
  • Réseau de stockage : à dimensionner et à isoler quelle que soit la méthode.

Tailles et topologies : du nœud unique au multi-site

  • La méthode doit couvrir la taille visée, pas seulement la taille de départ. Passer de trois à trente nœuds ne doit pas imposer de changer d'outil.
  • Ce qui limite en premier : la durée d'une exécution complète de l'outil, qui croît avec le nombre d'hôtes ; puis la base de données et le bus de messages.
  • Sites distants : vérifier si l'outil sait déployer des nœuds de calcul éloignés du plan de contrôle, et ce qui se passe quand le lien tombe.
  • Plusieurs clouds : un dépôt de configuration par cloud, un tronc commun partagé — possible avec tous les outils pilotés par fichiers.

Critères liés à l'organisation (1 à 5)

  • Ils servent surtout à éliminer : une contrainte non satisfaite écarte une méthode, quelle que soit sa note par ailleurs.
  • Ils se vérifient par la documentation, puis par une maquette.
  • Ils évoluent : les réévaluer à chaque étape importante du projet.
6 · Critères de choix

Le critère dominant : ce que l'équipe sait dépanner

Le test décisif : un incident survient en pleine nuit. La personne d'astreinte sait-elle où regarder sans ouvrir la documentation de l'outil ?
  • L'outil devient une compétence à part entière. On ne dépanne pas Nova dans Kubernetes comme Nova sur un serveur : il faut d'abord trouver le pod, son journal, sa configuration.
  • Deux technologies à apprendre en même temps — OpenStack et son orchestrateur — est le premier facteur d'échec des projets.
  • Compter les personnes, pas l'équipe : si une seule personne connaît l'outil, le cloud dépend de ses congés.
  • Recruter : les profils Ansible et Kubernetes sont nombreux ; les profils Juju ou spécialistes d'un outil précis sont plus rares.
Former l'équipe à l'orchestrateur avant le projet, pas pendant la mise en production.
6 · Critères de choix

Durée de vie et support : combien de temps une version tient-elle ?

Suivre l'amont

Une montée de version tous les six mois, ou une par an en ne prenant que les versions SLURP. Exige une chaîne de test et une équipe rodée. En retour : les nouveautés tout de suite, aucun coût de licence.

S'appuyer sur un éditeur

Une version garde ses correctifs de sécurité pendant des années. Les montées de version deviennent rares, mais chacune franchit plusieurs versions amont : à préparer comme un projet.

Le piège : ne rien faire

Un cloud communautaire laissé trois ans sans mise à jour n'a plus de correctifs et ne peut plus monter que version par version. Rattraper le retard coûte plus cher que de le prévenir.
Question à poser en comité : « Qui, nommément, fera la prochaine montée de version, et quand ? » Sans réponse, privilégier une version à long terme sous contrat.

Ce que le graphique veut montrer

  • Le matériel ne dépend pas de la méthode. Il représente pourtant souvent le premier poste : la méthode se joue sur le reste.

6 · Critères de choix

Huit erreurs fréquentes

Choisir sur la démonstration

Juger l'outil sur l'installation du premier jour, alors que le coût se joue sur les années d'exploitation.

Mettre DevStack en production

Ou tout autre outil de maquette « parce qu'il fonctionne déjà ». Aucune montée de version n'est prévue.

Suivre la mode

Adopter Kubernetes pour OpenStack sans équipe Kubernetes : deux plateformes à apprendre en même temps.

Modifier hors de l'outil

Corriger un fichier à la main sur un nœud. Le changement disparaît à la prochaine exécution, souvent au pire moment.

Oublier la machine nue

Choisir un outil qui commence « au système installé » sans avoir de moyen de réinstaller un serveur à l'identique.

Reporter les montées de version

Chaque version sautée rend la suivante plus risquée, jusqu'à imposer une reconstruction complète.

Ne pas avoir de préproduction

Répéter la montée de version directement en production. La maquette du projet doit devenir un environnement permanent.

Dépendre d'une seule personne

Un outil connu d'un seul ingénieur est un risque d'exploitation, quel que soit l'outil.

Les signes d'un bon choix

  • Toute la configuration tient dans un dépôt git, relu et versionné.
  • Un nouveau venu redéploie la préproduction en suivant le dépôt, sans aide.
  • La dernière montée de version date de moins d'un an.
Changer d'avis coûte cher. Passer d'une méthode à une autre revient à construire un second cloud et à migrer les charges. Mieux vaut trois semaines de maquette que trois ans avec le mauvais outil.
