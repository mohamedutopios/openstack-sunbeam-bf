Introduction

Objectif et déroulé

Objectif : confier l'authentification des personnes à une autorité externe, raccordée à Keystone par fédération, et appliquer une politique de mots de passe conforme aux recommandations de l'ANSSI — là où elle doit s'appliquer, sans mettre en panne les comptes de service.

À l'issue de ce module, vous saurez :

  • Expliquer pourquoi et comment déléguer l'authentification à une autorité externe.

  • Écrire et tester des règles de correspondance.
  • Raccorder un fournisseur d'identité à un cloud Sunbeam, pas à pas.
  • Traduire le guide de l'ANSSI en règles : longueur, complexité, expiration, verrouillage.
  • Appliquer ces règles dans Keystone sans casser les comptes de service.

01

Pourquoi une autorité d'authentification externe

Un cloud ne devrait pas être un annuaire de plus. Les personnes ont déjà une identité dans l'entreprise, avec sa politique, son multifacteur et sa procédure de départ : Keystone doit s'y fier, pas la recopier.

Ce qui reste local : les comptes des services OpenStack, un ou deux comptes d'administration de secours, et les comptes techniques des automates. Ils sont l'objet de la dernière partie.
1 · Autorité externe

Trois façons de raccorder des identités

  • Annuaire LDAP : Keystone lit l'annuaire et vérifie lui-même le mot de passe. Il le voit passer — et la politique de verrouillage ou d'expiration est celle de l'annuaire.
  • Fédération : Keystone ne voit ni mot de passe ni second facteur. Il reçoit une attestation signée par l'autorité, et en tire utilisateur et groupes.
  • Les trois coexistent, un domaine par source : comptes techniques en local, salariés par l'annuaire ou la fédération, partenaires par une autre fédération.
  • Sur Sunbeam : sunbeam ldap add-domain pour un annuaire, sunbeam identity provider add pour une fédération.

Le vocabulaire de la fédération

TermeSens
Fournisseur d'identité (IdP)l'autorité : authentifie la personne et atteste son identité
Fournisseur de service (SP)l'application qui fait confiance à l'attestation — ici Keystone
Attestationjeton d'identité signé (OIDC) ou assertion signée (SAML)
Attribut, revendicationune information de l'attestation : identifiant, courriel, groupes
Client, client secretl'enregistrement du SP chez l'IdP (OIDC) et son secret
URL de redirectionadresse du SP où l'IdP renvoie le navigateur après authentification
Émetteur, identifiant distantnom unique de l'IdP ; Keystone le compare à ce qu'il a enregistré
Règles de correspondancetraduisent les attributs reçus en utilisateur, groupes, projets

Ce qui se passe, en une phrase : Keystone renvoie le navigateur vers l'autorité ; l'autorité authentifie ; elle renvoie une attestation signée ; Keystone la vérifie, applique ses règles et délivre un jeton OpenStack.

  • La confiance est configurée, pas négociée : Keystone connaît d'avance l'émetteur, ses clés de signature et l'identifiant de client.
  • L'autorité ne connaît pas OpenStack : elle ne sait rien des projets ni des rôles. Elle fournit des attributs ; les règles de Keystone en tirent des droits.
  • Le jeton OpenStack reste un jeton Keystone : les services ne voient jamais l'attestation. Pour eux, un utilisateur fédéré est un utilisateur comme un autre.
Le module 8 présente la fédération dans les grandes lignes ; ce module en détaille le fonctionnement, la sécurité et la mise en œuvre.

Critère n° 1 : là où sont déjà les personnes

Le meilleur fournisseur est celui que l'entreprise exploite déjà, avec ses procédures d'arrivée et de départ.

Critère n° 2 : la maîtrise

Un cloud privé souverain s'accommode mal d'une authentification hébergée hors de l'Union : l'autorité devient un point de dépendance.

Critère n° 3 : la disponibilité

Autorité indisponible = plus aucune connexion humaine : d'où le compte de secours (partie 6).

2 · Fédération dans Keystone

Architecture

  • Le module web fait le protocole — redirections, échange du code, vérification de la signature — et transmet les attributs à Keystone sous forme de variables d'environnement.
  • Keystone fait l'autorisation : il vérifie l'émetteur, applique les règles, crée ou retrouve l'utilisateur et émet un jeton.
  • Le préfixe des attributs dépend de la configuration du module : OIDC-email, HTTP_OIDC_EMAIL… Les règles de correspondance doivent utiliser exactement ces noms.
  • Horizon propose le fournisseur dans sa liste de connexion et reçoit le jeton en retour.
2 · Fédération dans Keystone

Les trois objets de Keystone

# Prérequis : identifiants d'administrateur
source admin-openrc
openstack identity provider create entreprise-idp \
  --remote-id https://sso.exemple.fr/realms/entreprise \
  --domain entreprise
openstack mapping create entreprise-mapping --rules rules.json
openstack federation protocol create openid \
  --identity-provider entreprise-idp --mapping entreprise-mapping
  • Identifiant distant : doit être égal, caractère pour caractère, à l'émetteur présenté par l'attestation — barre oblique finale comprise.
  • Domaine du fournisseur : les utilisateurs fédérés y sont créés ; un domaine par fournisseur.
  • Le nom du protocole fait partie des adresses de connexion : …/identity_providers/entreprise-idp/protocols/openid/auth.
2 · Fédération dans Keystone

Connexion par le navigateur (WebSSO)

  • Le mot de passe et le second facteur ne sont saisis que chez l'autorité (étape 4) : ni Horizon ni Keystone ne les voient.
  • Le premier jeton est sans portée : il dit qui est l'utilisateur. Horizon en demande ensuite un pour un projet.
  • Tableau de bord de confiance : Keystone ne renvoie le jeton qu'à une adresse d'Horizon déclarée d'avance — protection contre le vol de jeton par redirection.
  • Aucun rôle, aucun projet ? La connexion réussit chez l'autorité, puis échoue dans Horizon : la règle n'a donné aucun groupe utile.

# ~/.config/openstack/clouds.yaml
clouds:
  entreprise:
    auth_type: v3oidcdeviceauthz
    auth:
      auth_url: https://keystone.exemple.fr/v3
      identity_provider: entreprise-idp
      protocol: openid
      client_id: openstack-cli
      discovery_endpoint: >-
        https://sso.exemple.fr/realms/ent/.well-known/openid-configuration
      project_name: prod-web
      project_domain_name: nord

# Le client affiche une adresse et un code à valider
openstack --os-cloud entreprise token issue
  • Le client OIDC de la ligne de commande doit être déclaré chez l'autorité, avec le flux correspondant autorisé.
  • Méthode disponible selon la version de keystoneauth installée : vérifier avant de la proposer aux équipes.

Les règles de correspondance : anatomie

[
  {
    "local": [
      { "user":  { "name": "{0}", "email": "{1}" } },
      { "group": { "name": "exploitation-prod",
                   "domain": { "name": "entreprise" } } }
    ],
    "remote": [
      { "type": "OIDC-preferred_username" },
      { "type": "OIDC-email" },
      { "type": "OIDC-groups",
        "any_one_of": [ "openstack-exploitation" ] }
    ]
  },
  {
    "local": [
      { "user":  { "name": "{0}", "email": "{1}" } },
      { "group": { "name": "developpeurs",
                   "domain": { "name": "entreprise" } } }
    ],
    "remote": [
      { "type": "OIDC-preferred_username" },
      { "type": "OIDC-email" },
      { "type": "OIDC-groups",
        "any_one_of": [ "openstack-dev" ] }
    ]
  }
]
PartieRôle
remotece que l'attestation doit contenir ; toutes les conditions doivent être vraies
localce que Keystone en tire : utilisateur, groupes, éventuellement projets
{0}, {1}valeur du 1er, du 2e attribut de remote, dans l'ordre
Groupe localdoit exister dans Keystone et porter les rôles
  • Les droits ne sont pas dans la règle : elle ne fait que placer la personne dans un groupe Keystone ; les rôles sont affectés au groupe, comme pour tout autre utilisateur.
  • Les règles se cumulent : une personne présente dans les deux groupes de l'autorité reçoit les deux groupes Keystone.
  • Aucune règle ne correspond : refus de la connexion (401). C'est le comportement par défaut voulu — n'entre que qui est prévu.
Noms d'attributs d'exemple ; leur forme exacte dépend du module web et de l'autorité.

Les conditions sur les attributs

ConditionEffetUsage
any_one_ofvraie si l'une des valeurs est présenteappartenance à un groupe de l'autorité
not_any_offausse si l'une des valeurs est présenteexclure les comptes externes, les comptes suspendus
whitelistne garde que les valeurs listéestransmettre seulement certains groupes
blacklistretire les valeurs listéesécarter des groupes sensibles
regex: trueles valeurs sont des expressions régulièresdomaine de courriel, préfixe de groupe
Ordre et cumul : chaque règle qui réussit ajoute ses groupes. Une règle d'exclusion doit donc être portée par chaque règle d'accès — par une condition not_any_of — et non par une règle séparée.
# Seuls les salariés du domaine de courriel de l'entreprise,
# et jamais les comptes marqués « suspendu »
"remote": [
  { "type": "OIDC-preferred_username" },
  { "type": "OIDC-email",
    "any_one_of": [ ".*@exemple\\.fr$" ], "regex": true },
  { "type": "OIDC-groups",
    "not_any_of": [ "comptes-suspendus" ] },
  { "type": "OIDC-groups",
    "any_one_of": [ "openstack-dev" ] }
]

# Transmettre tels quels tous les groupes « os-* »
"local": [
  { "user": { "name": "{0}" } },
  { "groups": "{1}", "domain": { "name": "entreprise" } }
],
"remote": [
  { "type": "OIDC-preferred_username" },
  { "type": "OIDC-groups",
    "any_one_of": [ "^os-.*" ], "regex": true }
]
Transmettre des groupes en masse est pratique mais délègue à l'autorité le pouvoir d'ouvrir des droits : quiconque peut créer un groupe « os-… » chez elle en devient maître.
2 · Fédération dans Keystone

Utilisateurs et groupes fédérés

Type d'utilisateurComportement
éphémère (par défaut)créé à la première connexion dans le domaine du fournisseur ; attributs venus de l'autorité
localdoit exister déjà dans Keystone ; la fédération ne sert qu'à l'authentifier ; ses groupes et rôles locaux s'appliquent
  • Appartenance aux groupes : recalculée à chaque connexion à partir de l'attestation. Quitter le groupe chez l'autorité retire le droit à la connexion suivante.
  • Utilisateur « fantôme » : Keystone garde une trace de chaque utilisateur fédéré — identifiant stable, dernière connexion — ce qui permet audit et affectations directes.
  • Appartenance persistante : pour qu'un identifiant d'application ou une délégation d'un utilisateur fédéré reste valable entre deux connexions, Keystone peut conserver l'appartenance pendant une durée réglée sur le fournisseur (authorization_ttl) — à vérifier sur votre version.

Départ d'un salarié

MomentEffet
Compte désactivé chez l'autoritéplus de nouvelle connexion

Créer les projets automatiquement ?

"local": [
  { "user": { "name": "{0}" } },
  { "projects": [
      { "name": "bac-a-sable-{0}",
        "roles": [ { "name": "member" } ] }
  ] }
],

  { "type": "OIDC-preferred_username" },
  { "type": "OIDC-groups",
    "any_one_of": [ "openstack-bac-a-sable" ] }
]
  • Effet : à la première connexion, Keystone crée le projet s'il n'existe pas et y affecte le rôle à l'utilisateur.
  • Ces affectations persistent dans Keystone, même si la règle change ensuite : il faut les retirer à la main.
  • Les projets ainsi créés reçoivent les quotas par défaut : ceux-ci deviennent la seule protection.
PourContre

Recommandation : en production, les projets se créent par la plateforme ou le gestionnaire du domaine ; la fédération ne fait que placer les personnes dans des groupes existants.
Si l'on garde l'auto-création : quotas par défaut très bas, étiquette d'échéance, et revue mensuelle des projets créés ainsi.

Ce que la fédération apporte

  • une seule politique de mot de passe, celle de l'entreprise ;
  • le multifacteur sans rien développer ;
  • des départs traités une fois ;
  • aucun mot de passe humain dans Keystone.

Ce qu'elle n'apporte pas

  • les droits OpenStack : ils restent à concevoir dans Keystone ;
  • l'authentification des services et des automates ;
  • une révocation instantanée des sessions ouvertes.
C'est la dernière ligne du tableau qui fait le lien avec la suite : une fois les personnes fédérées, la politique de mots de passe de Keystone ne concerne plus que les comptes locaux.

Le guide et ses principes

Référence : ANSSI, Recommandations relatives à l'authentification multifacteur et aux mots de passe, version 2.0, 8 octobre 2021. Recommandations numérotées R1 à R38.
N°Principe
R1privilégier l'authentification multifacteur
R2privilégier des mécanismes robustes, conformes au RGS
R3choisir les moyens d'authentification après une analyse de risque
R10limiter le nombre de tentatives dans le temps
R13protéger les données d'authentification stockées
R31fournir un gestionnaire de mots de passe et former à son usage

Trois idées à retenir

Adapter à l'enjeu

Il n'y a pas une politique, mais des politiques : un compte d'administration du cloud n'a pas le même niveau d'exigence qu'un compte de lecture d'un projet d'essai.

La longueur d'abord

Un mot de passe long résiste mieux qu'un mot de passe court et « complexe », que les utilisateurs construisent selon des schémas prévisibles.

Le mot de passe seul ne suffit pas

Pour les accès sensibles — l'administration en tête — le guide recommande un second facteur, de préférence de possession.
4 · Référentiel ANSSI

Longueur et entropie (R21)

Calcul : longueur × log2(taille de l'alphabet). Valable seulement pour un tirage aléatoire uniforme — ce que n'est presque jamais un mot de passe choisi par une personne.

Tableau du guide — alphabet de 90 caractères

SensibilitéLongueur minimaleÉquivalent
Faible à moyenne9 à 11≈ 65 bits
Moyenne à forte12 à 14≈ 85 bits
Forte à très forte15 et plus≥ 100 bits
  • Forte à très forte sensibilité : le guide recommande en plus le multifacteur.
  • Mots de passe non mémorisés — ceux d'un gestionnaire, d'un compte technique — : au moins 20 caractères.
  • Code court acceptable seulement avec des mesures fortes : blocage définitif après trois échecs, comme une carte à puce.
Pour un cloud : les comptes d'administration relèvent de la sensibilité forte ; un compte de travail ordinaire, au minimum de la moyenne à forte.

4 · Référentiel ANSSI

Expiration (R24, R25, R26)

R24 — Comptes ordinaires

Si la robustesse est imposée et que le système le permet : pas d'expiration par défaut. Le guide note qu'une expiration courte, de 3 à 6 mois, peut être contre-productive : les utilisateurs incrémentent un chiffre.

R25 — Comptes à privilèges

Imposer une expiration, par exemple entre 1 et 3 ans. Le guide préfère, pour ces comptes, une authentification à deux facteurs.

R26 — Compromission suspectée

Renouveler sans délai — dans la journée — tous les mots de passe concernés ; à défaut, désactiver les comptes et prévoir une procédure de réactivation.
Habitude ancienneProblèmePratique conforme au guide
Expiration à 90 jours pour tousmots de passe prévisibles : « Printemps2026! »pas d'expiration pour les comptes ordinaires robustes
Jamais d'expiration pour l'administrationun mot de passe ancien a eu le temps de fuiter1 à 3 ans, plus multifacteur
Attendre l'expiration après une fuitefenêtre d'exploitation ouverterenouvellement immédiat, procédure prête
Dans Keystone, l'expiration est une option globale : elle ne distingue pas comptes ordinaires et privilégiés. On la module compte par compte avec une option d'exemption — partie 5.
4 · Référentiel ANSSI

Verrouillage et temporisation (R10)

  • R10 : limiter le nombre de tentatives sur une période — blocage temporaire de quelques secondes ou minutes après plusieurs échecs, linéaire ou exponentiel.
  • Un blocage définitif n'est envisagé par le guide que pour des codes courts protégés autrement — une carte à puce, par exemple.
  • Le revers du verrouillage : quiconque connaît un identifiant peut le bloquer en tapant de faux mots de passe. Sur un compte de service, c'est une panne du cloud.
  • R14 : en multifacteur, un échec ne doit pas révéler quel facteur a échoué.

Qu'est-ce qu'un compte à privilèges sur un cloud OpenStack ?

La dernière ligne est souvent oubliée : avec la fédération, l'administrateur de l'autorité est un administrateur du cloud par procuration.

Exigences renforcées

  • Multifacteur obligatoire pour toute personne détenant un de ces droits.
  • Mot de passe d'au moins 15 caractères, expiration entre 1 et 3 ans (R25).
  • Comptes dédiés : le compte d'administration n'est pas le compte de messagerie.
  • Nombre minimal et revue mensuelle.
  • Poste d'administration maîtrisé : le guide de l'ANSSI sur l'administration sécurisée des systèmes d'information le développe.
Pour les comptes de service, l'enjeu est le même mais les moyens diffèrent : pas de multifacteur possible, donc des secrets très longs, jamais saisis par une personne, et un accès restreint à leur stockage.

Où s'applique chaque règle

Règle d'architecture : la politique des personnes se règle à un seul endroit — l'autorité. Keystone n'applique sa propre politique qu'aux quelques comptes locaux qui lui restent.

La stratégie sur Sunbeam

5 · Appliquer dans Keystone

Le multifacteur des comptes locaux

# Prérequis : identifiants d'administrateur ; méthode
# totp acceptée par Keystone (à vérifier : [auth] methods)
source admin-openrc
SID=$(openstack user show secours \
  --domain "$OS_USER_DOMAIN_NAME" -f value -c id)

# 1 · Secret TOTP : 20 octets aléatoires, en base32
SECRET=$(head -c 20 /dev/urandom | base32 | tr -d '=')

# 2 · L'enregistrer comme justificatif du compte
openstack credential create --type totp "$SID" "$SECRET"

# 3 · Imposer mot de passe + totp
openstack user set "$SID" \
  --enable-multi-factor-auth \
  --multi-factor-auth-rule password,totp

# 4 · QR code pour l'application d'authentification
qrencode -t ansiutf8 \
  "otpauth://totp/OpenStack:secours?secret=$SECRET&issuer=OpenStack"

# 5 · Se connecter avec les deux méthodes
export OS_AUTH_TYPE=v3multifactor
export OS_AUTH_METHODS=v3password,v3totp
read -rs OS_PASSCODE; export OS_PASSCODE
openstack token issue
  • Règles de méthodes : une liste de combinaisons acceptées ; password,totp exige les deux. Plusieurs règles peuvent coexister.
  • Le secret TOTP est stocké dans Keystone : il fait partie de ce que R13 demande de protéger, comme les empreintes de mots de passe.
  • Horizon doit savoir demander le code : à vérifier sur votre version avant de compter dessus pour le compte de secours.
  • Ne jamais activer le multifacteur sur un compte de service : les services s'authentifient par mot de passe seul.

L'impact sur les comptes de service

Une politique de mots de passe pensée pour des personnes, appliquée sans précaution à des comptes de machines, produit des pannes : verrouillage à distance, expiration un dimanche, changement imposé qu'aucun programme ne sait faire.

6 · Comptes de service

Quatre risques

Le plus grave est le verrouillage : il transforme une simple connaissance du nom d'un compte — nova, neutron — en moyen de mettre le cloud hors service, sans aucun mot de passe.
Ces risques concernent aussi les comptes techniques des automates qui s'authentifient par mot de passe. Les identifiants d'application, eux, ne passent pas par le mot de passe du compte.

Les exemptions

# Prérequis : identifiants d'administrateur
source admin-openrc

# Le domaine des services : son nom se lit, il ne se suppose pas
SVC=$(openstack domain list -f value -c Name | grep -i service)

# Exempter chaque compte de service
for u in $(openstack user list --domain "$SVC" \
            -f value -c ID); do
  openstack user set "$u" \
    --ignore-lockout-failure-attempts \
    --ignore-password-expiry \
    --ignore-change-password-upon-first-use
done

# Inactivité, pour le compte de secours : par l'API
# (option sans équivalent dans le client selon les versions)
SID=$(openstack user show secours \
  --domain "$OS_USER_DOMAIN_NAME" -f value -c id)
TOKEN=$(openstack token issue -f value -c id)
curl -s -X PATCH "$OS_AUTH_URL/users/$SID" \
  -H "X-Auth-Token: $TOKEN" -H "Content-Type: application/json" \
  -d '{"user":{"options":{"ignore_user_inactivity":true}}}'

# Contrôle
openstack user show nova --domain "$SVC" -c options

Synthèse

Ce qu'il faut retenir

La fédération

  • L'autorité authentifie ; Keystone traduit des attributs en groupes.
  • Trois objets : fournisseur, règles, protocole.
  • Règles testées hors ligne, versionnées, fermées par défaut.
  • Sur Sunbeam : sunbeam identity provider add, puis les objets Keystone.

Le référentiel ANSSI

  • Longueur d'abord : 12, 15, au moins 20 selon l'enjeu.
  • Pas d'expiration systématique ; 1 à 3 ans pour les privilégiés.
  • Temporisation plutôt que blocage définitif.
  • Multifacteur pour tout accès sensible.

Les comptes de service

  • Verrouillage, expiration, premier usage, inactivité : quatre pannes possibles.
  • Exemptions posées avant d'activer.
  • Secrets longs, aléatoires, stockés et tournés.
  • Échec d'authentification = alerte.
