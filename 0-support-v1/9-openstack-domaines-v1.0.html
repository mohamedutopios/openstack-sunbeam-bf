Introduction

Objectif et déroulé

Objectif : savoir découper un cloud en domaines, comprendre ce que ce découpage isole réellement, et répartir l'administration entre une équipe plateforme — globale — et des responsables de domaine — délégués — sans ouvrir de brèche.

À l'issue de ce module, vous saurez :

  • Expliquer en quoi un domaine est un espace d'identité indépendant.
  • Dire ce qui appartient à un domaine et ce qui reste global.
  • Créer, raccorder, désactiver et supprimer un domaine sur Sunbeam.
  • Distinguer administrateur global, administrateur de domaine et gestionnaire de domaine.
  • Mettre en place une délégation et en vérifier les limites.
  • Choisir un découpage adapté à une organisation.

Pourquoi des domaines

Tant que le cloud ne sert qu'une équipe, un seul espace suffit. Dès qu'il en sert plusieurs — filiales, clients, annuaires — il faut des cloisons dans l'identité elle-même.

1 · Pourquoi des domaines

Le problème d'un espace unique

Collision de noms

Dans un espace unique, deux équipes ne peuvent pas avoir chacune un projet « web » ni un utilisateur « alice ».

Administration tout ou rien

Pour créer un utilisateur, il faut être administrateur du cloud. Impossible de confier « seulement mon périmètre ».

Une seule source d'identité

Tous les comptes viennent du même endroit : pas d'annuaire par filiale, pas de fournisseur d'identité par client.
1 · Pourquoi des domaines

Les trois fonctions d'un domaine

Définition à retenir : un domaine est un conteneur d'utilisateurs, de groupes et de projets, qui délimite à la fois leurs noms, leur administration et leur origine.
Un peu d'histoire : les domaines sont arrivés avec la version 3 de l'API d'identité. Avant, il n'existait que des « tenants », tous au même niveau ; le domaine Default a été créé pour les accueillir.

1 · Pourquoi des domaines

Ce qu'un domaine n'isole pas

Point le plus mal compris : le domaine est une notion de Keystone. Nova, Neutron, Cinder et Glance ne raisonnent qu'en projets ; ils ignorent à quel domaine un projet appartient.
SujetRéalité
Isolation réseaupar projet, pas par domaine : deux projets d'un même domaine sont aussi étanches que deux projets de domaines différents
Quotashistoriquement par projet ; pas de plafond « pour tout le domaine » dans les quotas classiques
Images publiques, gabaritsvisibles de tous les domaines
Réseaux partagés, réseau externecommuns à tout le cloud
Hyperviseurs, stockagemutualisés : les instances de deux domaines cohabitent sur les mêmes hôtes
Catalogue, régionsidentiques pour tous
  • Pour isoler du matériel par organisation : agrégats d'hôtes, gabarits privés, zones de disponibilité — pas les domaines.
  • Pour plafonner une organisation entière : les limites unifiées de Keystone, ou une somme de quotas par projet gérée par la plateforme — module suivant.
  • Pour restreindre le partage : images et gabarits en accès par projet ; réseaux partagés par règles d'accès ciblées.

# Deux « alice », deux « web » : aucun conflit
openstack user create --domain nord --password-prompt alice
openstack user create --domain sud  --password-prompt alice
openstack project create --domain nord web
openstack project create --domain sud  web

openstack user list --domain nord
openstack user list --domain sud
  • Les deux « alice » sont deux personnes distinctes pour le cloud : identifiants différents, mots de passe différents, droits différents.
  • Les identifiants sont opaques et attribués par Keystone ; ce sont eux que portent les jetons et les ressources.
  • Renommer un projet ou un utilisateur ne change pas son identifiant : ses ressources et ses droits le suivent.
Dans un journal ou une facture, toujours conserver l'identifiant : c'est la seule référence qui ne soit jamais ambiguë.

# Les options de la ligne de commande suivent la même logique
openstack role add \
  --user alice    --user-domain nord \
  --project web   --project-domain nord \
  member

openstack group add user \
  --group-domain nord --user-domain nord \
  developpeurs alice

# Ou, sans ambiguïté possible, par identifiants
openstack role add --user 3f1c… --project 9a7e… member
  • Oublier le domaine est l'erreur la plus fréquente : la commande cherche alors dans le domaine du jeton courant, ou échoue par ambiguïté.
  • Dans Horizon, la page de connexion demande le domaine en plus du nom et du mot de passe.
  • Dans les scripts, préférer les identifiants : ils survivent aux renommages.
2 · Espaces d'identité

Ce qui appartient à un domaine, ce qui est global

Appartenance exclusive : un utilisateur, un groupe ou un projet appartient à un seul domaine, pour toujours. On ne « déplace » pas un utilisateur d'un domaine à l'autre : on en crée un nouveau.
Les affectations de rôles n'appartiennent à aucun domaine : elles relient un acteur et une cible, qui peuvent être de domaines différents. C'est ce qui permet le travail entre organisations.
2 · Espaces d'identité

Le domaine, racine d'un arbre de projets

  • Tout projet a un domaine, et un seul ; un sous-projet est dans le domaine de son parent.
  • Le domaine est le sommet de l'arbre : un projet de premier niveau a pour parent le domaine lui-même.
  • Deux façons de poser un rôle sur un domaine :
AffectationDonne des droits sur
sur le domaine, directele domaine lui-même : gérer ses utilisateurs, groupes, projets
sur le domaine, héritéetous les projets du domaine — mais pas le domaine lui-même
# Gérer le domaine
openstack role add --user bob --user-domain nord \
  --domain nord manager

# Lire tous les projets du domaine
openstack role add --group exploitants \
  --group-domain nord --domain nord --inherited reader
Les deux se cumulent souvent : un responsable de domaine reçoit manager en direct, pour administrer, et member hérité, pour agir dans les projets.
2 · Espaces d'identité

Une source d'identité par domaine

  • L'aiguillage se fait sur le domaine : « alice » du domaine « siege » est cherchée dans l'annuaire du siège, et nulle part ailleurs.
  • Les domaines ne se voient pas : la panne de l'annuaire d'une filiale n'empêche pas les autres domaines de se connecter.
  • Une seule source par domaine. Deux annuaires, deux domaines.
  • Projets et rôles restent dans Keystone, quelle que soit la source : l'annuaire fournit des personnes et des groupes, jamais des droits.
2 · Espaces d'identité

Configuration propre à un domaine

Le mécanisme, dans Keystone

# keystone.conf — activer les réglages par domaine
[identity]
domain_specific_drivers_enabled = true
domain_config_dir = /etc/keystone/domains

# /etc/keystone/domains/keystone.siege.conf
[identity]
driver = ldap
[ldap]
url = ldaps://ldap.siege.exemple
suffix = dc=siege,dc=exemple
user_tree_dn = ou=personnes,dc=siege,dc=exemple
  • Un fichier par domaine, nommé d'après lui ; il ne surcharge que les sections liées à l'identité.
  • Variante : les mêmes réglages stockés en base et gérés par l'API, plutôt que dans des fichiers.
  • Un domaine sans réglage propre utilise le pilote par défaut : la base locale.

Sur Sunbeam : on ne touche pas à ces fichiers

sunbeam enable ldap
sunbeam ldap add-domain \
  --domain-config-file ./siege.yaml \
  --ca-cert-file ./ca-siege.pem siege
sunbeam ldap list-domains
Un appel par domaine raccordé. Le fichier YAML porte les mêmes clés que la section [ldap] : url, user, password, suffix au minimum.
Noms des charms et emplacement des fichiers décrits d'après le fonctionnement général de Sunbeam : à confirmer avec juju status.
2 · Espaces d'identité

Affectations entre domaines

openstack role add \
  --user carla --user-domain prestataires \
  --project web --project-domain nord member

openstack role add \
  --group audit-externe --group-domain prestataires \
  --domain nord --inherited reader

# Carla s'authentifie avec deux domaines différents
export OS_USER_DOMAIN_NAME=prestataires
export OS_PROJECT_DOMAIN_NAME=nord
  • L'indépendance porte sur l'identité, pas sur l'accès : rien n'interdit de donner à un acteur d'un domaine un rôle sur une cible d'un autre.
  • Usage type : un domaine « prestataires » ou « exploitation », dont les membres interviennent chez plusieurs organisations.
  • Qui peut créer une telle affectation ? Il faut des droits sur la cible ; un gestionnaire de domaine peut, selon la politique en vigueur, être limité aux acteurs de son propre domaine — à tester avant de s'y fier.
  • Revue : ces affectations sont celles qui échappent le plus facilement aux contrôles ; les lister régulièrement.
2 · Espaces d'identité

Cycle de vie d'un domaine

# Créer
openstack domain create --description "Filiale Nord" nord

# Suspendre un locataire : effet immédiat
openstack domain set --disable nord
openstack domain set --enable nord

# Supprimer : nettoyer les ressources d'abord
openstack project list --domain nord -f value -c ID
openstack project purge --project <id>   # par projet
openstack domain set --disable nord
openstack domain delete nord
  • Keystone ne prévient pas les autres services : il efface ses propres objets. Les ressources des projets disparus continuent de consommer capacité et adresses.
  • Ordre de retrait d'un locataire : désactiver le domaine, inventorier ses projets, purger leurs ressources, puis seulement supprimer.
  • project purge ne couvre pas tous les services : vérifier réseaux, répartiteurs, images et objets à la main.
Le domaine par défaut et les domaines techniques ne se suppriment pas : le cloud en dépend.

2 · Espaces d'identité

Les domaines dans Horizon

  • Champ « Domaine » à la connexion : présent dès que Horizon est configuré pour plusieurs domaines — c'est le cas à attendre sur un cloud qui en a plusieurs.
  • Fournisseurs fédérés : une liste de choix s'ajoute ; le domaine est alors déduit du fournisseur.
  • Contexte de domaine : un administrateur du cloud peut « se placer » dans un domaine pour y créer projets et utilisateurs.
  • Limites de l'interface : le panneau Identité s'appuie sur ses propres règles d'affichage ; il arrive qu'il masque une action que l'API autoriserait, ou l'inverse.
# Adresse du tableau de bord sur Sunbeam
sunbeam dashboard-url
En cas de doute, la ligne de commande fait foi : c'est l'API de Keystone, et non l'interface, qui applique réellement les règles de délégation.
Schéma de principe : la disposition exacte dépend de la version et du thème de Horizon.

3 · Administration globale

Qui est l'administrateur global

  • Il est au-dessus des domaines, pas dans l'un d'eux : son compte vit dans un domaine technique, mais ses droits portent sur le système.
  • Il peut tout faire dans tous les domaines — y compris ce qu'il a délégué. Déléguer n'est pas renoncer.
  • Sur Sunbeam : c'est le compte fourni par sunbeam openrc. Il s'ajoute à lui l'accès à Juju et aux nœuds, qui est un pouvoir d'un autre ordre encore.
  • Lecteur global : le profil à donner au support et aux outils de supervision, plutôt qu'un accès d'administration.

Les plafonds sont le vrai levier de la plateforme : un gestionnaire de domaine crée autant de projets qu'il veut, mais ne peut pas s'accorder plus de capacité.

En pratique sur Sunbeam : le fichier produit par sunbeam openrc vise le projet d'administration. C'est ce jeton qui sert au quotidien ; la portée système s'obtient à la demande.
# Jeton du projet d'administration — ce que donne admin-openrc
source admin-openrc
openstack token issue -c project_id -c user_id

# Jeton de portée système : retirer le projet, demander « all »
unset OS_PROJECT_NAME OS_PROJECT_DOMAIN_NAME
export OS_SYSTEM_SCOPE=all
openstack token issue -c system
openstack domain list

# Prérequis : détenir un rôle sur le système
openstack role assignment list --system all --names
openstack role add --user admin \
  --user-domain <domaine d'administration> \
  --system all admin
  • Les deux portées s'excluent : un jeton vise le système ou un projet, jamais les deux.
  • Si une commande d'administration renvoie 403 avec l'un, essayer l'autre : c'est le signe d'une règle qui déclare ses portées.
3 · Administration globale

Le piège du rôle admin

  • Héritage historique : pendant des années, « admin quelque part » a signifié « admin partout ». Les règles récentes corrigent cela opération par opération, mais pas encore partout ni dans tous les services.
  • Conséquence : considérer toute attribution du rôle admin — sur un projet, sur un domaine — comme une attribution potentiellement globale.
  • Le rôle manager a été introduit précisément pour offrir une délégation sans ce risque.
# Inventaire : qui détient admin, et sur quoi ?
openstack role assignment list --names --role admin

# Tester ce qu'un « admin de domaine » peut réellement faire
# (avec un jeton de bob, portée domaine nord)
openstack user list --domain sud      # doit échouer
openstack domain create essai         # doit échouer
Ne pas supposer, tester : le comportement dépend de la version de Keystone et des options de politique. Les deux commandes ci-dessus tranchent en une minute sur votre cloud.

4 · Administration déléguée

Le principe : trois étages

La plateforme décide du cadre

Combien de domaines, quelle source d'identité, quelle capacité. Elle n'intervient plus dans le quotidien d'un domaine.

Le gestionnaire organise son domaine

Il découpe en projets, compose les équipes, attribue les droits. Il répond aux demandes de ses propres utilisateurs.

Les membres consomment

Ils créent leurs instances, réseaux et volumes dans les projets où ils ont un rôle, sans connaître l'étage du dessus.

# Gestionnaire
openstack role add --user bob --user-domain nord \
  --domain nord manager

# Lecteur de domaine
openstack role add --group audit --group-domain nord \
  --domain nord reader

# Exploitants : member sur tous les projets, présents et futurs
openstack role add --group exploitants --group-domain nord \
  --domain nord --inherited member
  • manager implique member, qui implique reader : le gestionnaire est donc aussi lecteur de son domaine.
  • Gérer n'est pas utiliser : le rôle manager sur le domaine ne donne aucun accès aux instances des projets. Pour cela, il lui faut aussi un rôle dans les projets — direct ou hérité.
  • Le rôle manager existe depuis la version 2023.2 ; son usage pour la gestion de domaine a été complété dans les versions suivantes.

5 · Global ou délégué

Combien de domaines ? Arbre de décision

Règle de sobriété : un domaine se justifie par une frontière d'administration ou de source d'identité. Pour séparer des ressources, des budgets ou des environnements, les projets suffisent.
Erreur fréquente : un domaine par environnement — production, recette, développement. Ce sont les mêmes personnes et le même annuaire : trois projets, ou trois arbres de projets, dans un seul domaine.

Automatiser la création d'un domaine

# domaine.tf — fournisseur Terraform « openstack »
variable "nom"            { type = string }
variable "gestionnaires"  { type = list(string) }

resource "openstack_identity_project_v3" "domaine" {
  name        = var.nom
  description = "Domaine ${var.nom}"
  is_domain   = true
}

resource "openstack_identity_group_v3" "gestionnaires" {
  name      = "gestionnaires"
  domain_id = openstack_identity_project_v3.domaine.id
}

data "openstack_identity_role_v3" "manager" { name = "manager" }
data "openstack_identity_role_v3" "member"  { name = "member" }

resource "openstack_identity_role_assignment_v3" "gestion" {
  group_id  = openstack_identity_group_v3.gestionnaires.id
  domain_id = openstack_identity_project_v3.domaine.id
  role_id   = data.openstack_identity_role_v3.manager.id
}

resource "openstack_identity_project_v3" "socle" {
  name      = "socle"
  domain_id = openstack_identity_project_v3.domaine.id
}
  • Un module par domaine : domaine, groupe des gestionnaires, rôle manager, premier projet et son quota — toujours les mêmes étapes, donc à décrire une fois.
  • Le domaine est créé comme un projet marqué is_domain : c'est ce qu'il est, en interne.
  • Ce que la plateforme y gagne : revue par un pair avant application, historique, et un état de référence auquel comparer la réalité.
  • Ce qu'il ne faut pas y mettre : les comptes des personnes et les projets du quotidien — ils relèvent du gestionnaire, pas du code de la plateforme.

Bonnes pratiques

Peu de domaines, bien justifiés

Un domaine par frontière d'administration ou de source d'identité. Le reste se règle par projets.

Ne rien mettre dans les domaines techniques

Administration et services restent tels que Sunbeam les a créés.

manager, jamais admin

Le rôle admin ne se délègue pas, ni sur un domaine, ni sur un projet.

Deux gestionnaires au moins

Par domaine, nominatifs, attribués à un groupe plutôt qu'à des personnes.

Quota par défaut bas, quotas explicites par projet, plafond par domaine quand c'est possible.

Les dix tests, après chaque montée de version et chaque changement de politique.

Désactiver, inventorier, nettoyer les ressources, puis seulement supprimer le domaine.

Revoir les affectations croisées

Tout rôle accordé à un acteur d'un autre domaine a une raison écrite et une échéance.

Synthèse

Ce qu'il faut retenir

Le domaine

  • Espace de noms, frontière d'administration, point de raccordement d'une source d'identité.
  • Contient utilisateurs, groupes, projets — exclusivement.
  • Isole les identités, pas les ressources ni le matériel.
  • Désactiver suspend ; supprimer n'efface pas les ressources.

L'administration globale

  • Portée système ou projet d'administration, rôle admin.
  • Garde les domaines, les sources d'identité, les rôles, la capacité, le partagé, l'infrastructure.
  • Très peu de personnes.
  • admin ne se cantonne pas : ne pas le déléguer.

L'administration déléguée

  • Rôle manager sur le domaine, jeton de portée domaine.
  • Gère utilisateurs, groupes, projets, rôles courants.
  • Ne voit ni ne touche les autres domaines.
  • Ne peut pas attribuer admin ni changer les quotas.
