Schéma d'architecture

Canonical OpenStack (Sunbeam) — services, nœuds et flux

Déploiement multi-nœuds à haute disponibilité : trois nœuds par rôle. Le plan de contrôle tourne en pods sur Canonical Kubernetes, pilotés par des charms Juju ; le calcul et le stockage tournent en snaps directement sur les machines.

Vue d'ensemble

Cliquez sur une famille de flux, sur une pastille numérotée du schéma ou sur une ligne du tableau pour isoler un flux. Chaque numéro renvoie au tableau des flux.

Variante minimale : trois machines seulement, chacune cumulant les rôles control, compute et storage (architecture hyperconvergée). Les composants et les flux sont identiques ; seules les frontières entre nœuds disparaissent.

Scénario : créer une instance sur volume

Cliquez sur une étape pour allumer les flux qu'elle emprunte.

  1. L'utilisateur envoie POST /servers au point d'accès public. flux 1, 2
  2. nova-api valide le jeton auprès de Keystone, lit l'image dans Glance, vérifie réseaux et quotas, enregistre l'instance. flux 3, 9
  3. nova-conductor et nova-scheduler se coordonnent par RPC ; le scheduler interroge Placement et réserve un hôte. flux 6, 3
  4. cinder-scheduler confie la création du volume à cinder-volume, qui le crée dans Ceph à partir de l'image. flux 8, 5, 15
  5. L'ordre de construction arrive sur l'hyperviseur ; nova-compute demande le port à Neutron et la connexion du volume à Cinder. flux 7, 4
  6. Neutron inscrit le port dans OVN ; ovn-controller l'apprend par le relais et installe les flux Open vSwitch. flux 10, 11, 12
  7. libvirt démarre la machine ; QEMU ouvre le volume directement dans Ceph. flux 14
  8. Au premier démarrage, cloud-init lit ses métadonnées sur l'hôte. flux 18
  9. Une IP flottante est associée : le trafic entre et sort par br-ex ; entre hôtes, il passe par les tunnels Geneve. flux 16, 17

Vérifier sur un déploiement réel

sunbeam cluster list                    # nœuds et rôles
juju status -m admin/controller         # k8s, microceph, openstack-hypervisor…
juju status -m openstack                # charms du plan de contrôle
sudo k8s kubectl get pods,svc -n openstack   # pods et adresses LoadBalancer
sudo systemctl status 'snap.openstack-hypervisor.*'
sudo microceph status ; sudo ceph -s
sunbeam plans list                      # plans Terraform et verrous

Hypothèses et limites du schéma

  • Topologie OVN : le schéma montre OVN central et son relais dans Kubernetes, et le rôle compute comme passerelle vers l'extérieur. Les versions récentes ajoutent un rôle network (MicroOVN) qui reprend cette fonction de passerelle ; la branche de développement permet aussi de sortir OVN central du modèle openstack.
  • Cinder : cinder-volume est représenté en snap sur les nœuds de stockage. Les versions plus anciennes l'exécutaient dans Kubernetes (charm cinder-ceph-k8s).
  • Noms de nœuds et nombre de nœuds (sunbeam-ctl01…) : illustratifs. La haute disponibilité demande au moins trois nœuds ; au-delà, on ajoute surtout des nœuds compute et storage.
  • Ports : 5672, 3306, 6641, 6642, 6443, 17070, 6081 et les ports Ceph sont les valeurs par défaut des logiciels ; le port 7000 de clusterd et les ports exposés par Traefik (80 ou 443 selon l'activation de TLS) sont à confirmer sur votre version.
  • Flux non dessinés : console SPICE (navigateur → traefik-public → nova-spiceproxy → hyperviseur), accès objet (traefik-rgw → RGW), réplication interne de MySQL, RabbitMQ, OVN et Ceph, synchronisation entre démons clusterd.
  • Métadonnées : servies localement par le snap de l'hyperviseur ; selon la version, la requête peut être relayée vers nova dans Kubernetes.
