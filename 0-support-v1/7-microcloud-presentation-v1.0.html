  • Dérouler une initialisation et les opérations courantes.
  • Dire ce qui se passe lors d'une panne d'un membre, d'un disque, d'un lien.
  • Énoncer les cas d'usage, les avantages et les limitations.
  • Positionner MicroCloud face à Canonical OpenStack et choisir.

1 · Vue d'ensemble

MicroCloud en une image

À retenir : chaque membre porte les trois fonctions. Il n'y a ni nœud de contrôle séparé, ni base de données externe, ni bus de messages : l'état est répliqué entre les membres eux-mêmes.

SnapRôleCe qu'il apporteCe que l'on manipule au quotidien

MicroCloud n'est pas une couche de plus

Une fois le cluster formé, il s'efface : on administre un cluster LXD. MicroCloud revient pour ajouter ou retirer un membre et vérifier l'état d'ensemble.

Chaque service se répare lui-même

MicroCloud ne supervise pas les services après le déploiement. Un membre LXD hors ligne se traite avec les procédures de LXD, un disque avec celles de MicroCeph.

Les composants existent sans lui

LXD, MicroCeph et MicroOVN s'utilisent séparément. Canonical OpenStack réutilise d'ailleurs MicroCeph et MicroOVN.
1 · Vue d'ensemble

Les principes de conception

Hyperconvergé par construction

Calcul, stockage et réseau sur les mêmes machines. On ajoute de la capacité en ajoutant un membre identique aux autres.

Automatisé de bout en bout

Une commande pose les questions, puis forme trois grappes et les relie. Un fichier de préconfiguration rend l'opération reproductible.

Petit d'abord

Un membre pour essayer, trois pour la haute disponibilité, cinquante au maximum. La cible est le petit cloud, pas le très grand.

Sans plan de contrôle séparé

Chaque service réplique son état entre les membres. N'importe quel membre répond aux requêtes.

Conteneurs et machines virtuelles

Les deux types d'instances, avec les mêmes commandes, les mêmes réseaux et les mêmes volumes.

Libre, support en option

Les quatre snaps sont libres et gratuits. Ubuntu Pro ajoute durée de maintenance et assistance.

Ce que cela donne en pratique

  • Un cluster opérationnel en quelques dizaines de minutes, par une personne.
  • Très peu de concepts à apprendre : instance, image, profil, projet, pool, réseau.
  • Une exploitation proche de celle d'un hyperviseur classique, pas de celle d'un cloud à services multiples.

Ce que cela implique

  • Des choix imposés : LXD, Ceph, OVN, Ubuntu, snaps.
  • Pas de catalogue de services au-dessus des instances.
  • Une taille maximale connue à l'avance.

2 · Virtualisation : LXD

Le cluster LXD

  • Pas de nœud maître : chaque membre expose la même API et peut traiter n'importe quelle requête.
  • L'état du cluster — instances, profils, réseaux, pools, droits — vit dans une base Dqlite (SQLite répliqué) portée par les membres eux-mêmes.
  • La configuration est commune : un pool ou un réseau se définit une fois pour tout le cluster, avec des valeurs propres à chaque membre quand il le faut (quel disque, quelle interface).
  • Les instances, elles, tournent sur un membre précis ; leur disponibilité dépend du stockage choisi.
BesoinCommande

Détail d'un membrelxc cluster show micro02

Perte de la majorité (deux membres sur trois) : les instances en marche continuent, mais l'API n'accepte plus aucun changement tant que le quorum n'est pas revenu.

Vie d'une instance : les commandes

# Créer
lxc launch ubuntu:24.04 web1               # conteneur
lxc launch ubuntu:24.04 db1 --vm \
  -c limits.cpu=4 -c limits.memory=8GiB    # machine virtuelle
lxc launch ubuntu:24.04 app1 --target micro02

# Observer
lxc list
lxc info web1
lxc console db1                         # console série

# Entrer, copier
lxc exec web1 -- bash
lxc file push site.conf web1/etc/nginx/conf.d/

# Régler à chaud
lxc config set web1 limits.memory=4GiB

# Protéger
lxc snapshot web1 avant-maj
lxc restore web1 avant-maj
lxc export web1 web1.tar.gz             # sauvegarde
# Disque de données
lxc storage volume create remote donnees size=50GiB
lxc storage volume attach remote donnees db1 /srv

# Arrêter, supprimer
lxc stop web1
lxc delete web1

Projets et contrôle d'accès

# Un projet cloisonné, avec ses propres réseaux
lxc project create web \
  -c features.networks=true
lxc project set web limits.instances=20 \
  limits.cpu=64 limits.memory=128GiB

# Un groupe, opérateur du projet
lxc auth group create equipe-web
lxc auth group permission add equipe-web \
  project web operator
  • Deux façons de s'authentifier : certificat client TLS, ou fournisseur d'identité OIDC — indispensable pour l'interface web en équipe.
  • Autorisation fine : une permission est un droit sur une ressource précise (projet, instance, réseau…), accordée à un groupe.
  • Limites de projet : nombre d'instances, cœurs, mémoire, disque, réseaux — l'équivalent des quotas.
  • Restrictions : un projet peut interdire les instances privilégiées, certains périphériques, l'accès à certains réseaux.
Par défaut, quiconque atteint le socket local de LXD est administrateur de l'hôte. Ne mettre personne dans le groupe lxd sans y avoir réfléchi.
2 · Virtualisation : LXD

Placement, migration, évacuation

# Préparer une machine virtuelle à la migration à chaud
lxc config set db1 migration.stateful=true

# Déplacer une instance
lxc move db1 --target micro02

# Maintenance d'un membre
lxc cluster evacuate micro01
lxc cluster restore micro01
  • Le stockage décide de tout : sur le pool remote, une instance repart sur un autre membre sans copie ; sur local, son disque doit être transféré par le réseau.
  • Reprise automatique : LXD peut évacuer seul les instances d'un membre resté hors ligne au-delà d'un délai (cluster.healing_threshold) — réservé aux instances sur stockage distribué, et à activer explicitement.
  • Groupes de membres : réserver des machines à un usage — cartes graphiques, architecture, licence.

Les réseaux d'un MicroCloud

À retenir : deux interfaces par membre au minimum. L'une, adressée, porte tout le trafic interne du cluster ; l'autre, sans adresse, est confiée à OVN pour relier les réseaux virtuels au monde extérieur.
4 · Réseau

MicroOVN : architecture

  • MicroOVN est une enveloppe minimale autour d'OVN : il installe les services, les met en grappe et gère leurs certificats.
  • Commutation et routage distribués : chaque membre héberge son commutateur virtuel. Le trafic entre instances continue même si d'autres membres sont hors ligne.
  • DHCP et DNS des réseaux virtuels sont rendus par OVN lui-même, sur chaque membre.
  • Sécurité : les points d'accès d'OVN sont protégés par TLS 1.2 ou plus, avec des clés à courbe elliptique P-384.
  • On ne configure rien dans OVN à la main : c'est LXD qui écrit dans la base Nord.
sudo microovn status
sudo microovn.ovn-nbctl show   # vue logique
sudo microovn.ovn-sbctl show   # hôtes et tunnels
Ces deux dernières commandes servent à lire pour diagnostiquer, jamais à modifier.

Maquette

Deux interfaces : interne et sortie. Tout le reste partage le réseau interne. Une seule interface derrière un pont fonctionne pour un essai, sans support.

Production courante

Cartes double port à 10 Gbit/s au moins : un agrégat pour l'interne, des VLAN pour séparer Ceph et les tunnels, une interface pour la sortie.

Production exigeante

Liens distincts pour Ceph public, Ceph interne et tunnels ; latence faible entre membres — un MicroCloud ne s'étire pas entre sites éloignés.
Les adresses des membres sont définitives : les changer après l'installation n'est pas prévu. Fixer l'adressage, les noms et les VLAN avant de lancer microcloud init.
Taille des trames : les tunnels ajoutent un en-tête. Augmenter la taille maximale des trames sur le réseau des tunnels évite la fragmentation.

Mise en œuvre et exploitation

L'initialisation, vue de l'intérieur

Confiance : les échanges entre l'initiateur et les machines qui le rejoignent sont signés à partir d'un secret partagé qui ne circule jamais sur le réseau ; ensuite, tout passe en TLS mutuel, par certificats.
Découverte : par multidiffusion, limitée au sous-réseau de l'interface interne. Là où elle est filtrée — chez un hébergeur, par exemple — on indique l'adresse de l'initiateur à la main.

Installation pas à pas

Étape 0 — à vérifier sur chaque machine

  • Ubuntu Server LTS installé, à jour, nom de machine unique.
  • Interface interne : adresse statique, même sous-réseau partout.
  • Interface de sortie : active mais sans adresse.
  • Disques de données vierges : ni partition, ni système de fichiers.
  • Horloges synchronisées ; accès à Internet pour les snaps.
  • Sur le réseau de sortie : passerelle connue, plage d'adresses libre réservée.
# Étape 1 — sur CHAQUE machine
sudo snap install lxd microceph microovn microcloud \
  --cohort="+"
sudo snap refresh --hold lxd microceph microovn microcloud
--cohort="+" garantit la même révision partout ; --hold suspend les mises à jour automatiques, qui désaligneraient le cluster.
# Étape 2 — sur UNE machine, l'initiateur
sudo microcloud init

# Étape 3 — sur chacune des AUTRES, quand l'assistant le demande
sudo microcloud join

# Étape 4 — de retour sur l'initiateur : répondre aux questions,
#           puis laisser le cluster se former

# Étape 5 — vérifier
sudo microcloud status
lxc cluster list
lxc launch ubuntu:24.04 essai
lxc exec essai -- ping -c 3 ubuntu.com
Version viséeCanaux à préciser
3 LTScanaux par défaut ; vérifier avec snap info microcloud
2 LTSmicrocloud 2/stable, lxd 5.21/stable, microceph squid/stable, microovn 24.03/stable
Durée : la formation du cluster prend plusieurs minutes, surtout l'initialisation de MicroCeph et l'ajout des disques. Ne pas interrompre.

Vie du cluster : membres et services

sudo microcloud status

#  sur un membre existant :

#  sur la nouvelle machine (snaps déjà installés) :

Mises à jour : un ordre à respecter

# Mise à jour dans la piste courante
sudo snap refresh microceph --cohort="+"
sudo snap refresh microovn  --cohort="+"
sudo snap refresh lxd       --cohort="+"
sudo snap refresh microcloud --cohort="+"

# Montée de version : même ordre, avec le nouveau canal
sudo snap refresh microceph --channel=<canal> --cohort="+"
Vérifier l'alignement : snap list lxd doit afficher in-cohort sur chaque membre.
  • Avant : sauvegarder LXD et MicroCeph ; lire le guide de mise à niveau de chaque composant.
  • Impact : LXD laisse tourner les instances ; les mises à jour de Ceph et d'OVN peuvent perturber brièvement stockage et réseau.
  • Pour ne rien interrompre : évacuer chaque membre avant, restaurer après — les machines virtuelles migrent à chaud, les conteneurs sont arrêtés puis relancés.
  • Snaps désalignés : les instances continuent, mais on ne peut plus ajouter ni retirer de membre ou d'instance.
  • Grand parc : un mandataire de magasin d'entreprise permet de figer les révisions distribuées.

Trois membres

Tolère une panne. Pendant la panne, plus aucune marge : ni pour une seconde panne, ni pour reconstruire la troisième copie des données.

Quatre membres et plus

Recommandé pour un service critique : après une panne, Ceph retrouve trois copies et le cluster garde une marge.

Un seul site

Un MicroCloud vit sur un réseau local à faible latence. La protection contre la perte d'un site passe par un second cluster et des copies entre les deux.
Capacité à réserver : pour que les instances d'un membre perdu repartent ailleurs, garder libre l'équivalent d'un membre en mémoire et en processeurs.

Supervision et clusters multiples

Sur un cluster

  • Interface web : état des membres, occupation, instances.
  • Métriques : LXD expose un point de collecte au format Prometheus, par instance et par membre.
  • Ceph et OVN : charms d'intégration vers la pile d'observabilité, pour métriques et journaux.

Sur plusieurs clusters : Cluster Manager

  • Application web distincte, qui montre l'usage et la disponibilité de tous les clusters inscrits.
  • Se déploie par charms : Juju 3.6 ou plus, un Kubernetes, PostgreSQL, Traefik, un fournisseur OIDC, deux noms de domaine.
  • Un cluster s'inscrit avec un jeton ; il doit être en MicroCloud 3 ou plus.
  • Peut, si on l'active, déclencher certaines actions par un tunnel ouvert depuis le cluster.
Ce n'est pas une fédération : chaque cluster garde ses instances, ses projets et ses droits. Cluster Manager donne une vue d'ensemble, pas un plan de contrôle commun.

6 · Bilan

Avantages

À l'installation

  • Rapide : un cluster à haute disponibilité en quelques dizaines de minutes, par une seule personne.
  • Guidé : un assistant, une dizaine de questions ; ou un fichier pour rejouer à l'identique.
  • Tout est inclus : hyperviseur, stockage distribué, réseau virtuel, interface web — rien à assembler.
  • Démarre petit : une machine pour essayer, trois pour produire.

À l'usage

  • Simple à apprendre : une poignée d'objets, une commande, une interface.
  • Conteneurs et machines virtuelles côte à côte, sur les mêmes réseaux et volumes.
  • Cloisonnement par projets, limites et droits fins.
  • Réseau riche pour sa taille : réseaux par projet, filtrage, redirections, répartition de charge, appairage.

En exploitation

  • Peu de pièces mobiles : pas de base externe, pas de bus de messages, pas de nœud de contrôle dédié.
  • Faible empreinte : les ressources vont aux instances, pas à la plateforme.
  • Maintenance sans arrêt : évacuation et migration à chaud des machines virtuelles.
  • Réparation automatique du stockage ; bascule automatique de la sortie réseau.
  • Mises à jour par snaps : transactionnelles, avec retour arrière.

Pour l'organisation

  • Libre et gratuit, sans licence par processeur ni par instance.
  • Versions à long terme : cinq ans, dix avec Ubuntu Pro.
  • Briques standard en dessous : Ceph, OVN, QEMU/KVM — les compétences se réutilisent.
  • Mixité d'architectures de processeur possible dans un même cluster.
En une phrase : MicroCloud apporte la haute disponibilité d'un cluster de virtualisation avec stockage et réseau logiciels, pour le coût d'exploitation d'un hyperviseur.

Deux philosophies

MicroCloud répond à « où faire tourner mes machines virtuelles et mes conteneurs, de façon fiable et simple ? ».
Canonical OpenStack répond à « comment offrir à de nombreux utilisateurs un cloud complet, avec des API standard et des services à la demande ? ».

7 · Positionnement

Exploitation et compétences

  • MicroCloud : une personne formée en quelques jours tient un cluster ; le diagnostic descend rarement plus bas que LXD, Ceph et OVN.
  • Canonical OpenStack : il faut en plus lire Juju, Kubernetes et les services d'OpenStack eux-mêmes — davantage de couches entre le symptôme et la cause.
  • Coût fixe de la plateforme : quelques processus par membre pour MicroCloud ; un plan de contrôle complet — une quinzaine de gigaoctets de mémoire par nœud de contrôle — pour OpenStack.
  • Mises à jour : quatre snaps dans un ordre donné d'un côté ; snap, Kubernetes, bases, puis charms de l'autre.
Appréciation qualitative, à adapter à votre équipe : qui exploite déjà Kubernetes et Juju ne part pas de zéro sur OpenStack.
7 · Positionnement

Ce que les deux produits partagent

Ce que cela permet

  • Compétences transférables : diagnostiquer Ceph ou OVN s'apprend une fois, pour les deux.
  • Matériel réutilisable : les mêmes serveurs conviennent à l'un comme à l'autre.
  • Un seul contrat et un seul interlocuteur si les deux coexistent.

Ce que cela ne permet pas

  • Pas de conversion en place : un MicroCloud ne « devient » pas un OpenStack ; il faut redéployer et migrer les charges.
  • Pas d'API commune : l'outillage écrit pour LXD ne parle pas à OpenStack, et inversement.
  • Pas de gestion unifiée des deux dans une même console.
7 · Positionnement

Arbre de décision

Les trois premières questions éliminent MicroCloud ; la quatrième le désigne. Quand aucune ne tranche, la plateforme la plus simple que l'équipe sait exploiter est le bon choix.

7 · Positionnement

Coexistence et passage de l'un à l'autre

Faire coexister les deux

  • Répartition naturelle : OpenStack au centre, pour le libre-service ; MicroCloud sur les sites, pour la proximité.
  • Ce qui unifie : Terraform et Juju savent piloter les deux ; les images Ubuntu sont les mêmes ; supervision commune possible.
  • Autre combinaison : un MicroCloud héberge, en machines virtuelles, les services de gouvernance d'un OpenStack — MAAS, contrôleurs.

Par machine virtuelle membre

  • Deux cartes réseau : l'une sur un réseau interne avec adresse fixe ; l'autre sur le réseau de sortie, sans adresse.
  • Trois disques : système, stockage local, stockage distribué — les deux derniers vierges.
  • Virtualisation imbriquée activée, pour pouvoir lancer des machines virtuelles dans la maquette ; sinon, se limiter aux conteneurs.

Points d'attention

  • Réseau de sortie : il doit laisser passer plusieurs adresses par carte. Activer le mode « promiscuité » de la carte dans l'outil de virtualisation, sans quoi les routeurs virtuels sont injoignables.
  • Multidiffusion sur le réseau interne : nécessaire à la découverte ; sinon, indiquer l'adresse de l'initiateur.
  • Serveur DHCP de l'outil de virtualisation : à désactiver sur le réseau de sortie, ou réserver une plage qu'il ne distribue pas.
  • Adresses fixes : ne pas laisser les membres en DHCP.
  • Tutoriel officiel : il déroule exactement ce scénario à plusieurs membres virtualisés.

Scénario de démonstration en six temps

  • Initialiser · lancer un conteneur et une machine virtuelle · les joindre de l'extérieur par une redirection.
  • Déplacer la machine virtuelle à chaud · éteindre un membre et observer · le réintégrer.
Des membres virtuels conviennent à une maquette ; ils ne sont pas recommandés en production.
Synthèse

Ce qu'il faut retenir

Le produit

  • LXD + MicroCeph + MicroOVN, assemblés par le snap microcloud.
  • Conteneurs système et machines virtuelles.
  • 1 membre pour essayer, 3 pour la haute disponibilité, 50 au plus.
  • Pas de plan de contrôle séparé.

Le fonctionnement

  • Stockage : local rapide, remote répliqué trois fois.
  • Réseau : interne adressé, sortie sans adresse, réseaux virtuels OVN.
  • microcloud init et join, ou préconfiguration.
  • Au quotidien : la commande lxc et l'interface web.

Le positionnement

  • Un cluster de virtualisation, pas un cloud à services.
  • Mêmes briques basses que Canonical OpenStack.
  • API propre, pas de catalogue, taille bornée.
  • Passer à OpenStack est une migration.
