Introduction

Objectif et déroulé

Objectif : isoler réellement les locataires et les composants d'une application sur le réseau, puis être capable de répondre, après coup, à « qui a fait quoi, quand, d'où, avec quel résultat » — en centralisant et en corrélant les journaux du cloud.

À l'issue de ce module, vous saurez :

  • Expliquer ce qui isole deux projets dans Neutron et OVN.
  • Choisir entre réseau partagé, réseau privé et partage ciblé par RBAC.
  • Concevoir une micro-segmentation par groupes de sécurité et la tester.
  • Retrouver une action dans les journaux grâce aux identifiants de requête et aux événements d'audit.
  • Centraliser les journaux d'un cloud Sunbeam et écrire des règles d'alerte utiles.

1 · Le réseau

Neutron et OVN sur Sunbeam

  • Neutron décrit, OVN réalise : chaque réseau devient un commutateur logique, chaque routeur un routeur logique, chaque groupe de sécurité un ensemble de règles de filtrage (ACL).
  • Le plan de contrôle — serveur Neutron, bases nord et sud d'OVN — tourne dans Kubernetes sur les nœuds de contrôle.
  • Le plan de données est distribué : le contrôleur OVN de chaque hyperviseur programme Open vSwitch localement ; le filtrage se fait au plus près de l'instance.
  • Entre hyperviseurs, le trafic des réseaux de projet circule dans des tunnels Geneve, marqué de l'identifiant de son réseau.

Réseau superposé

Créé librement par les projets, sans toucher au réseau physique. Les adresses de deux projets peuvent se recouvrir : 10.0.0.0/24 dans chacun, sans conflit.

Réseau de fournisseur

Correspond à un réseau physique existant. Seule l'administration le déclare, car il engage l'infrastructure réelle : VLAN, routage, pare-feu de l'entreprise.

Partagé n'est pas une technologie

C'est un attribut d'accès. Un réseau superposé comme un réseau de fournisseur peut être partagé, avec tous ou quelques projets.
1 · Le réseau

Ce qui isole deux projets

Par défaut, deux projets ne se voient pas : réseaux distincts, adresses indépendantes, aucun routeur commun. Pour communiquer, ils doivent passer par le réseau externe et des adresses flottantes — comme deux entreprises sur Internet.
Chaque couche se défait par une décision explicite : un réseau partagé, un routeur commun, un groupe de sécurité trop ouvert, une sécurité de port désactivée. La suite du module passe ces décisions en revue.
1 · Le réseau

Le chemin d'un paquet entre deux projets

  • Quatre contrôles successifs : groupe de sécurité de sortie de A, traduction d'adresse par le routeur de A, routeur de B qui traduit l'adresse flottante, groupe de sécurité d'entrée de B.
  • Le groupe de sécurité de B voit l'adresse source traduite de A — l'adresse de passerelle de son routeur —, pas son adresse privée.
  • Avec OVN, routage et traduction d'adresses sont distribués : le paquet peut ne jamais quitter l'hyperviseur, et pourtant subir les mêmes contrôles.
  • Sans adresse flottante sur B, aucun chemin : B est injoignable depuis A.

Réseaux partagés et réseaux privés

Le réseau privé par projet

# Prérequis : jeton de portée projet, rôle member
export OS_PROJECT_NAME=prod-web OS_PROJECT_DOMAIN_NAME=nord

# Deux réseaux : façade et application
openstack network create prod-web-front
openstack subnet create prod-web-front-v4 \
  --network prod-web-front --subnet-range 10.10.1.0/24 \
  --dns-nameserver 10.0.0.53
openstack network create prod-web-app
openstack subnet create prod-web-app-v4 \
  --network prod-web-app --subnet-range 10.10.2.0/24 \
  --gateway none

# Routeur : façade vers l'extérieur seulement
openstack router create prod-web-rtr
openstack router set prod-web-rtr \
  --external-gateway external-network
openstack router add subnet prod-web-rtr prod-web-front-v4
  • Un réseau par zone de sécurité de l'application, pas un par machine : façade exposée, application, données.
  • Le réseau « app » n'a pas de passerelle et n'est relié à aucun routeur : ses instances n'ont aucune route vers l'extérieur. Elles joignent la façade par des instances à deux interfaces, ou un répartiteur.
  • Le routeur est le seul point de sortie : sans lui, le projet est hermétique.
  • Le nom du réseau externe — ici external-network — est celui choisi à l'installation : openstack network list --external.

2 · Partagé ou privé

Ce que partager un réseau veut dire

  • Sur un réseau partagé, les instances de plusieurs projets sont sur le même segment de niveau 2. Elles se joignent directement, sans routeur — seuls les groupes de sécurité les séparent.
  • Chaque projet ne voit que ses propres ports, mais il peut découvrir les autres adresses du segment par balayage.
  • Le groupe default d'un projet n'autorise l'entrée que depuis ce même groupe — donc pas depuis les autres projets. C'est ce qui protège le cas général ; une seule règle trop large l'annule.
  • Usage légitime : réseau d'administration ou de supervision, avec des règles d'entrée strictes du côté des instances.

# Partager le réseau d'administration avec UN projet
openstack network rbac create \
  --type network --action access_as_shared \
  --target-project prod-web --target-project-domain nord \
  admin-net

# Équivalent de --share : cible « * » (tous)
# — à éviter, et souvent réservé à l'administration
openstack network rbac create --type network \
  --action access_as_shared --target-all-projects admin-net

# Revue
openstack network rbac list --long
openstack network rbac delete <id>
  • --share à la création = cible « * » : tous les projets, présents et futurs.
  • Retrait bloqué tant que le projet cible a des ports sur le réseau : nettoyer d'abord.
  • Qui peut partager : le propriétaire, avec un projet nommé ; la cible « * » est en principe réservée à l'administration — règle create_rbac_policy à resserrer si besoin.
2 · Partagé ou privé

Le réseau externe

  • Un réseau de fournisseur marqué externe : il correspond à un réseau physique de l'entreprise ou d'Internet, et porte les passerelles des routeurs et les adresses flottantes.
  • Par défaut, visible de tous les projets : tout projet peut y raccorder un routeur et y prendre des adresses flottantes, dans la limite de ses quotas.
  • Plusieurs réseaux externes permettent des niveaux d'exposition différents : un vers Internet, un vers le réseau interne de l'entreprise.
  • Réserver un réseau externe à certains projets : le créer non partagé, puis l'ouvrir projet par projet avec access_as_external.
Sur Sunbeam, le réseau externe est déclaré par sunbeam configure ; d'autres réseaux de fournisseur s'ajoutent par l'API, sous réserve que le réseau physique correspondant soit raccordé aux hyperviseurs.
# Un second réseau externe, vers le SI interne,
# réservé aux projets qui en ont besoin (admin)
openstack network create externe-si \
  --external --no-share \
  --provider-network-type vlan \
  --provider-physical-network physnet1 \
  --provider-segment 120
openstack subnet create externe-si-v4 \
  --network externe-si --subnet-range 172.20.0.0/24 \
  --allocation-pool start=172.20.0.100,end=172.20.0.199 \
  --gateway 172.20.0.1 --no-dhcp

openstack network rbac create \
  --type network --action access_as_external \
  --target-project prod-web --target-project-domain nord \
  externe-si
Nom du réseau physique (physnet1) et identifiant de VLAN : selon le câblage et la configuration réseau de vos hyperviseurs.

Choisir

Règle par défaut : réseau privé par projet. Tout partage est une exception documentée — qui, pourquoi, depuis quand — et revue comme une affectation de rôle.

3 · Micro-segmentation

Le groupe « default »

  • Créé automatiquement dans chaque projet, et appliqué à toute instance créée sans groupe explicite.
  • Entrée : uniquement depuis les membres du même groupe. Sortie : tout.
  • Conséquence : toutes les instances d'un projet qui gardent default se parlent librement, sur tous les ports — l'inverse de la micro-segmentation.
  • Bonne pratique : ne pas y ajouter de règles ; créer des groupes par rôle et les appliquer explicitement.
  • Sur le projet de démonstration Sunbeam, il a été ouvert en SSH et ping depuis partout : ne pas s'en inspirer.
  • Il ne se supprime pas tant que le projet existe ; on peut en revanche en retirer les règles.
3 · Micro-segmentation

Écrire des règles

# Prérequis : jeton de portée projet, rôle member

# Un groupe par rôle, vide au départ
openstack security group create sg-bastion \
  --description "Bastion d'administration"

# SSH vers le bastion, depuis le réseau d'administration
openstack security group rule create sg-bastion \
  --ingress --ethertype IPv4 --protocol tcp \
  --dst-port 22 --remote-ip 192.168.50.0/24 \
  --description "SSH depuis le réseau d'admin"

# Restreindre la sortie (règles de sortie par défaut
# à retirer d'abord)
openstack security group rule list sg-bastion --egress
openstack security group rule delete <id-sortie-v4> <id-sortie-v6>
openstack security group rule create sg-bastion \
  --egress --protocol tcp --dst-port 22 \
  --remote-ip 10.10.0.0/16

# Appliquer à une instance, retirer default
openstack server add security group bastion-01 sg-bastion
openstack server remove security group bastion-01 default
  • Tout nouveau groupe contient deux règles de sortie vers tout — IPv4 et IPv6 — et aucune d'entrée.
  • Filtrer la sortie limite l'exfiltration et les rebonds depuis une instance compromise : utile pour les serveurs de données et les bastions.
  • Une description par règle : qui l'a demandée, pour quel flux. Six mois plus tard, c'est la seule documentation qui reste.
  • Éviter 0.0.0.0/0 en entrée, sauf pour un service public derrière un répartiteur.

3 · Micro-segmentation

Groupe distant ou adresse distante

  • Par groupe distant : « autoriser le port 8080 depuis les membres de sg-web ». La règle suit les instances : ajouter un serveur web au groupe lui ouvre le flux, sans toucher aux règles.
  • C'est la base de la micro-segmentation : on raisonne en rôles, pas en adresses.
  • Par adresse distante : pour ce qui n'est pas une instance du projet — réseau d'administration, sonde de supervision, partenaire.
  • Limite du groupe distant : il ne voit que les adresses fixes des ports ; un flux qui passe par une adresse flottante ou un routeur arrive avec une autre adresse source.

Un seul réseau suffit

Les quatre niveaux peuvent partager un réseau : les groupes séparent. Des réseaux distincts ajoutent une seconde barrière.

Pas à pas : les groupes de l'application

for g in sg-lb sg-web sg-app sg-db sg-bastion; do
  openstack security group create $g

$R sg-lb  --ingress --protocol tcp --dst-port 443 \
   --remote-ip 0.0.0.0/0 --description "HTTPS public"
$R sg-web --ingress --protocol tcp --dst-port 8443 \
   --remote-group sg-lb  --description "LB vers web"
$R sg-app --ingress --protocol tcp --dst-port 8080 \
   --remote-group sg-web --description "web vers app"

for g in sg-web sg-app sg-db; do

done

3 · Micro-segmentation

Groupes d'adresses

Problème : la même liste d'adresses — réseau d'administration, sondes de supervision, partenaires — revient dans des dizaines de règles. La modifier impose de toutes les retrouver.

Solution : un groupe d'adresses, nommé, référencé par les règles. On modifie le groupe ; toutes les règles suivent.

# Le groupe : les réseaux d'administration
openstack address group create ag-admin \
  --address 192.168.50.0/24 --address 192.168.51.0/24 \
  --description "Postes d'administration"

# Les règles le référencent
openstack security group rule create sg-bastion \
  --ingress --protocol tcp --dst-port 22 \
  --remote-address-group ag-admin

# Un nouveau site d'administration : une commande
openstack address group set ag-admin --address 192.168.52.0/24

Un groupe d'adresses partagé par la plateforme garantit qu'un changement d'adressage de l'administration se propage dans tous les projets, le jour même.

Règles par défaut des nouveaux groupes

Depuis 2023.2, l'administration peut définir les règles que Neutron place dans les nouveaux groupes : groupes default des projets, et groupes créés par les utilisateurs.

# Prérequis : identifiants d'administrateur
openstack default security group rule list

# Supervision autorisée dans tous les futurs groupes
openstack default security group rule create \
  --ingress --protocol tcp --dst-port 9100 \
  --remote-address-group ag-supervision \
  --for-default-sg --for-custom-sg \
  --description "Métriques, plateforme"

# Supprimer un modèle de règle
openstack default security group rule delete <id>
OptionS'applique à
--for-default-sggroupes default créés automatiquement
--for-custom-sggroupes créés par les utilisateurs
  • Seulement pour les groupes futurs : supprimer ou ajouter un modèle ne modifie pas les groupes existants.
  • Usage utile : retirer la sortie libre des nouveaux groupes, ou ajouter les flux de la plateforme — supervision, sauvegarde — partout.
  • À manier avec prudence : une règle trop large ajoutée ici se retrouve dans tous les projets.
Référencer un groupe d'adresses dans un modèle suppose qu'il soit partagé avec tous les projets ; sinon, utiliser un bloc d'adresses.

Sécurité de port et paires d'adresses autorisées

3 · Micro-segmentation

Mise en œuvre par OVN

  • Un groupe de sécurité devient un groupe de ports OVN et ses règles des ACL, inscrites dans la base nord puis traduites pour chaque hyperviseur.
  • Le filtrage se fait dans Open vSwitch sur l'hyperviseur de l'instance, avec suivi de connexion : il n'y a pas de pare-feu central à saturer.
  • Une instance compromise ne peut pas contourner ses règles : elles s'appliquent hors de l'instance, sur le port.
  • Lire ce qu'OVN a reçu : ovn-nbctl acl-list dans le conteneur de la base nord — réservé au diagnostic, jamais pour modifier.

Les identifiants de requête

  • Chaque service attribue un identifiant req-… à chaque requête reçue et le renvoie dans l'en-tête de réponse X-OpenStack-Request-ID.
  • Lorsqu'un service en appelle un autre, il transmet l'identifiant d'origine : le service appelé l'inscrit comme identifiant global à côté du sien.
  • Le client peut fournir son propre identifiant global ; un outil d'automatisation l'utilise pour relier ses actions aux journaux du cloud.
  • En pratique : on part de l'identifiant renvoyé à l'utilisateur ou affiché par openstack --debug, puis on cherche cette chaîne dans tous les journaux centralisés.

Le filtre d'audit des API

Un filtre de keystonemiddleware, placé dans la chaîne de traitement d'un service, produit un événement CADF pour chaque appel de son API : initiateur, action, cible, résultat.

Un journal resté sur la machine qui l'a produit disparaît avec elle, et peut être effacé par qui la compromet. Centraliser, c'est le mettre hors de portée, le conserver, et pouvoir enfin relier les événements de toutes les sources.

Architecture de centralisation

  • Collecte au plus près : un agent par nœud ou par modèle lit les journaux et les envoie, étiquetés par origine.
  • Stockage hors des systèmes surveillés : les journaux échappent à un administrateur ou un attaquant présent sur un nœud du cloud.
  • Exploitation à deux usages : consultation et enquête d'un côté, alertes de l'autre.
  • Le SIEM de l'entreprise, s'il existe, reçoit une copie des événements de sécurité pour les corréler avec le reste du système d'information.

  • Normaliser : le SIEM attend des champs — utilisateur, source, action, résultat — ; CADF les fournit déjà, les lignes d'accès demandent une analyse.

Ce que le SIEM apporte

  • la corrélation avec le reste du SI : poste de travail, autorité, pare-feu ;
  • la conservation longue, à part ;
  • une équipe de détection qui surveille déjà.

Ce qu'il ne remplace pas

  • les tableaux de bord d'exploitation du cloud ;
  • la connaissance des identifiants de requête et des événements d'instance pour enquêter.
Le choix de la voie dépend du SIEM en place et de son mode de collecte : à concevoir avec son équipe, en commençant par la liste des événements de la slide précédente.

Exercices de mise en pratique

#Énoncé
1Inventorier les réseaux partagés et les politiques RBAC du cloud ; justifier ou supprimer chacun.
2Déployer l'application à trois niveaux avec ses cinq groupes ; jouer le tableau de tests de cloison.
3Partager un réseau d'administration avec un seul projet ; vérifier qu'un troisième projet ne le voit pas.
4Supprimer une instance d'essai ; retrouver, à partir de son nom, l'utilisateur, l'heure et l'identifiant de requête, puis toutes les lignes associées dans Loki.
5Écrire la requête qui compte les échecs d'authentification par utilisateur sur une heure, et en faire une alerte.
6Couper la collecte d'une source ; vérifier que l'alerte « source muette » se déclenche.

Corrigé — points clés

  • 1 : network list --long et network rbac list --long ; toute cible « * » hors réseau externe est suspecte.
  • 2 : refus = délai dépassé ; vérifier aussi que default n'est plus sur les ports.
  • 3 : le projet non ciblé ne voit pas le réseau dans network list.
  • 4 : server event list → identifiant de requête → recherche dans Loki ; nom d'utilisateur par son identifiant dans Keystone.
  • 5 : filtrer « Authorization failed » puis count_over_time ; seuil et destinataire documentés.
  • 6 : sans alerte de collecte, un trou de journaux passe inaperçu — c'est l'objet de l'exercice.
Prérequis du TP : cloud Sunbeam avec admin-openrc, deux projets, observabilité activée, accès à Grafana.
Synthèse

Ce qu'il faut retenir

Réseaux

  • Réseau privé par projet par défaut : isolation de niveau 2.
  • Partage rare, ciblé par RBAC, jamais --share.
  • Exposition par adresses flottantes, sous quota.
  • Réseau externe réservable à certains projets.

Micro-segmentation

  • Groupes par rôle, règles par groupe distant.
  • default laissé intact et retiré des ports.
  • Sécurité de port toujours active.
  • Filtrage distribué par OVN sur chaque hyperviseur.

Audit et traçabilité

  • Identifiant de requête : le pivot de toute enquête.
  • Événements d'instance, notifications CADF, lignes d'accès.
  • Centralisation hors du cloud, horloges synchronisées.
  • Conservation de six mois à un an ; alertes, dont la collecte elle-même.
