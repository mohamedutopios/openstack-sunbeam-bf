Introduction

Objectif et déroulé

Objectif : donner à chaque personne et à chaque programme exactement les droits dont il a besoin, sur exactement le périmètre où il en a besoin, pour la durée où il en a besoin — avec les rôles standards d'OpenStack, sans réécrire les politiques.

  • Expliquer ce que Secure RBAC change : portées, nouvelles règles par défaut, fin de « admin partout ».
  • Lire une règle de politique et diagnostiquer un refus 403.
  • Créer des comptes de service et des identifiants d'application restreints, et les faire tourner.
  • Bâtir et auditer une matrice de rôles pour une organisation.

01

Le principe de moindre privilège

Chaque droit accordé est une porte ouverte. Le moindre privilège consiste à n'ouvrir que les portes utiles — et OpenStack fournit, depuis Secure RBAC, les outils pour le faire sans bricolage.

1 · Le moindre privilège

Le principe et ses corollaires

Moindre privilège : un acteur — personne ou programme — ne détient que les droits nécessaires à sa tâche, sur le seul périmètre de cette tâche, pendant la seule durée de cette tâche.

Besoin d'en connaître

Lire est aussi un privilège. Un auditeur n'a pas besoin d'écrire ; un développeur n'a pas besoin de voir la production d'une autre équipe.

Séparation des tâches

Celui qui accorde les droits n'est pas celui qui les utilise ; celui qui déploie n'est pas celui qui valide.

Durée limitée

Un droit temporaire porte une date de fin. Un identifiant d'automate expire et se renouvelle.

Traçabilité

Un acteur, une identité : jamais de compte partagé. Sinon, impossible de savoir qui a fait quoi.
Question à poserMauvaise réponseBonne réponse
Que doit-il faire ?« un peu de tout, on verra »une liste d'opérations : lire, créer des instances, gérer des comptes…
Où ?« sur le cloud »un projet, une branche de projets, un domaine
Combien de temps ?« jusqu'à nouvel ordre »une date, ou une revue périodique qui le reconduit
Qui l'a décidé ?« c'était plus simple »un responsable nommé, une demande tracée
1 · Le moindre privilège

Quatre leviers dans OpenStack

Le seul objet qui donne des droits est l'affectation de rôle : acteur + rôle + cible. Le moindre privilège se joue donc sur chacun de ces trois termes, plus la durée de vie de la preuve d'identité.
Ce que les leviers ne font pas : ils n'isolent pas le matériel ni le réseau. Un droit bien taillé ne remplace ni les groupes de sécurité, ni les quotas.

Le moindre privilège coûte aussi : plus d'affectations, plus de demandes. Les groupes, l'héritage et l'automatisation existent pour que ce coût reste faible.
1 · Le moindre privilège

La chaîne de décision

  • Keystone décide qui vous êtes et quels rôles vous avez, sur quelle portée. Il met tout cela dans le jeton.
  • Chaque service décide seul si ces rôles suffisent pour l'opération : Nova applique ses règles, Neutron les siennes.
  • Conséquence : un rôle n'a aucun pouvoir propre. member ne signifie quelque chose que parce que les règles des services le citent.
  • Le moindre privilège se règle à deux endroits : les affectations, côté Keystone — le quotidien ; les règles, côté services — l'exception.
1 · Le moindre privilège

Avant Secure RBAC : « admin quelque part, admin partout »

Le modèle historique ne connaissait que deux niveaux :

ProfilCe qu'il permettait
Propriétaireun rôle quelconque sur le projet : lire et modifier toutes ses ressources
Administrateuradmin sur un projet — n'importe lequel — et les services le traitaient en administrateur du cloud entier
  • Pas de lecture seule utilisable : tout membre d'un projet pouvait tout modifier.
  • Pas de délégation propre : pour gérer des comptes, il fallait admin, donc tout.
  • Des services s'appelant entre eux avec admin : un compte de service compromis valait un administrateur.
Ce comportement a fait l'objet d'un signalement de sécurité ancien et célèbre de Keystone : le rôle admin n'était pas « cantonné » à son projet.

Ce que Secure RBAC apporte

Ce qui n'a pas changé : le rôle admin reste global dans la plupart des services — un admin sur un projet administre encore le cloud. C'est le point le plus important de ce module.

2 · Les rôles standards

Cinq rôles standards

reader

Lire. Lister les instances, voir les volumes, consulter les quotas. Aucune modification.

Pour : audit, support, supervision, développeurs en production.

member

Agir sur les ressources de la cible : créer, modifier, supprimer.

Pour : les équipes qui travaillent dans un projet, les automates de déploiement.

manager

Gérer : comptes, groupes, projets et affectations dans un domaine ; certaines opérations élevées dans un projet.

Pour : responsables délégués.

admin

Tout, y compris l'infrastructure : hyperviseurs, réseaux externes, quotas, domaines.

Pour : la poignée de personnes qui exploite la plateforme.

service

Appels d'un service OpenStack à un autre : notifications d'événements, opérations internes.

Pour : les comptes des services, jamais des humains.

admininitialisation de Keystonemanager, donc tous les autresne se cantonne pas à sa cible dans la plupart des services
managerinitialisation (depuis 2023.2)member, readerne peut pas attribuer admin
memberinitialisationreaderle rôle de travail par défaut
readerinitialisation—base de la hiérarchie
servicedéploiement ; sur Sunbeam, le charm de Keystone— : hors hiérarchieadmin ne l'implique pas
2 · Les rôles standards

La hiérarchie d'implication

  • Un rôle impliqué est ajouté au jeton automatiquement : qui a member reçoit aussi reader dans son jeton, sans affectation supplémentaire.
  • Une seule affectation par personne et par cible suffit : le rôle le plus haut nécessaire.
  • service est volontairement isolé : un administrateur humain ne peut pas se faire passer pour un service, et un compte de service n'hérite pas de droits humains.
  • Les règles peuvent donc s'écrire simplement : « role:reader » suffit pour une lecture — tous les rôles supérieurs y satisfont.

Les règles de lecture vérifient aussi la cible : role:reader and project_id:%(project_id)s. Un reader sur un projet ne lit que ce projet.

Usages types

  • Audit et conformité : reader hérité sur un domaine ou une branche, porté par un groupe « audit ».
  • Support de premier niveau : voir l'état d'une ressource avant d'escalader.
  • Développeurs face à la production : diagnostiquer sans pouvoir corriger à chaud.
  • Supervision et inventaire : l'outil qui collecte l'état du cloud n'a besoin que de lire.
Lire n'est pas anodin : métadonnées d'instance, données utilisateur, noms et adresses révèlent l'architecture. Le besoin d'en connaître vaut aussi pour reader.
Dans Horizon, un reader voit les pages du projet ; les boutons d'action échouent avec un message d'autorisation.

  • Le rôle de travail par défaut pour les équipes et les automates de déploiement.
  • Pas de propriété individuelle : tous les member d'un projet peuvent modifier toutes ses ressources. Pour séparer deux équipes, il faut deux projets, pas deux rôles.
  • Les exceptions par propriétaire existent ponctuellement — paires de clés, identifiants d'application — mais rien de général.

  --project rec-web --project-domain nord

# Vérifier : ce que le groupe obtient réellement
openstack role assignment list --effective \
  --group equipe-web --group-domain nord --names
Le jeton d'un member contient member et reader : les règles de lecture lui sont acquises.

Sur un projet — avec un jeton de portée projet

  • Dans Nova, depuis 2025.2 : des opérations jusque-là réservées à admin deviennent accessibles au manager du projet — par exemple migrer à froid une instance sans choisir l'hôte.
  • Dans les autres services : l'adoption du persona est progressive. À vérifier service par service avant de s'en servir.
  • Jamais de choix d'hôte, jamais d'infrastructure : le manager reste dans son projet.

  --group gestionnaires-nord --group-domain nord \
  --domain nord

export OS_DOMAIN_NAME=nord

openstack user create --domain nord alice

2 · Les rôles standards

admin : le rôle qui déborde de sa cible

Règle typique de Nova : role:admin or (role:member and project_id:%(project_id)s). La partie admin ne vérifie pas le projet : elle vaut pour tous.
  • Dans Nova, Neutron, Cinder… admin sur n'importe quel projet donne les droits d'administration sur tout le cloud. C'est le « legacy admin », conservé volontairement pour ne pas casser les déploiements existants.
  • Dans Keystone, l'administration de l'identité tient compte de la portée : un admin de domaine n'administre que son domaine. Mais ses jetons de projet restent ceux d'un administrateur pour les autres services.
  • Conséquence pratique : admin ne se délègue jamais. Pour déléguer, manager.
Bonne pratiquePourquoi

service : le rôle des machines

Certaines API ne sont faites que pour les services entre eux. Exemple : Neutron prévient Nova qu'un port est prêt ; Cinder prévient Nova qu'un volume a changé de taille.

Avant 2023.2Avec le rôle service
le compte de Neutron avait admin pour appeler Novail a service : la règle exige ce rôle précis
un humain admin pouvait appeler ces API internesun humain admin n'a pas service : refus
compromettre un compte de service = administrateurobjectif : compte de service limité aux API internes
Règle de la documentation de Keystone : "identity:create_foo": "role:service", ou "role:service or role:admin" pendant la transition.
  • Hors hiérarchie : ni admin ne l'implique, ni il n'implique reader.
  • Ne jamais l'attribuer à une personne : il donne accès à des API dont l'appel à tort peut détruire des ressources.
  • Sur Sunbeam, le charm de Keystone crée les comptes des services avec service et admin : le second est gardé tant que tous les services ne savent pas se contenter du premier.
# Qui détient le rôle service ?
openstack role assignment list --role service --names

# Attendu : uniquement des comptes du domaine
# des services, jamais une personne
Le jour où les comptes de service n'ont plus que service, un vol de leurs identifiants ne donnera plus l'administration du cloud — c'est la cible de la phase 2 de Secure RBAC.

Rôles impliqués : lire et modifier la hiérarchie

# Prérequis : identifiants d'administrateur
source admin-openrc

# Les rôles existants
openstack role list

# Les implications : qui entraîne qui
openstack implied role list

# Ajouter une implication (exemple : rôle maison)
openstack role create facturation
openstack implied role create facturation \
  --implied-role reader

# La retirer
openstack implied role delete facturation \
  --implied-role reader
Résultat attendu de la deuxième commande : admin → manager, manager → member, member → reader. Une ligne manquante signale une installation ancienne, mise à jour sans recréer les implications.

Rôles personnalisés : à n'utiliser qu'en dernier recours

Un rôle maison ne fait rien tant qu'aucune règle ne le cite. Le créer impose de surcharger les politiques des services concernés.

CoûtDétail
Surcharges à écrireune règle par opération concernée, par service
Surcharges à maintenirà chaque montée de version, les règles par défaut évoluent ; les surcharges, non
Comportement imprévuHorizon, les clients, les autres services ignorent le rôle
Sur Sunbeamles fichiers de politique sont produits par les charms : une surcharge passe par leur configuration, pas par une édition dans le pod

Avant de créer un rôle, essayer dans l'ordre :

#Solution
1un rôle standard sur une cible plus étroite — un projet plutôt qu'un domaine
2un projet supplémentaire, pour isoler ce qui doit l'être
3un identifiant d'application avec règles d'accès, pour un automate
4un rôle maison qui n'implique qu'un rôle standard, pour nommer un usage
5en dernier : un rôle maison et des surcharges de politique
Exemple légitime : un rôle support-reseau autorisé à modifier les groupes de sécurité de tous les projets d'un domaine, sans rien d'autre. Rien de standard ne l'offre ; la surcharge est alors justifiée — et documentée.

Le contrôle d'accès par périmètre — Secure RBAC

Un rôle ne vaut que sur une cible. Secure RBAC rend cette cible explicite : chaque jeton a une portée, chaque règle dit quelles portées elle accepte et vérifie que la ressource visée en fait partie.

3 · Secure RBAC

Trois portées

Système

Ce qui n'appartient à personne : catalogue, domaines, rôles, et dans certains services l'infrastructure. Réservée à l'exploitation.

Domaine

L'identité d'une organisation : ses utilisateurs, groupes, projets, affectations. Portée de la délégation.

Projet

Les ressources : instances, réseaux, volumes, images. La portée de presque tout le travail quotidien.
3 · Secure RBAC

Personas : un rôle sur une portée

Portée systèmePortée domainePortée projet
adminadministre Keystone : catalogue, domaines, fédérationadministre l'identité du domaine« legacy admin » : administre tous les services, tous projets
manager—gère utilisateurs, groupes, projets, affectations du domaineopérations élevées dans le projet, là où le service le prévoit
memberlit l'identité de tout le cloudlit le domainecrée et gère les ressources du projet
readerlit l'identité de tout le cloud — auditlit le domainelit les ressources du projet
  • Un persona = un couple. « Lecteur système » et « lecteur de projet » sont deux profils différents, obtenus par deux affectations différentes.
  • Les cases de la colonne système concernent Keystone. Les services de ressources — Nova en tête — n'acceptent plus de jeton système : leurs règles sont de portée projet.
  • Les droits ne se transportent pas d'une portée à l'autre : un reader système ne lit pas les instances ; il lui faut un jeton de projet.
  • Exception notable : admin en portée projet, qui reste global dans les services de ressources.

3 · Secure RBAC

Les deux options d'activation

[oslo_policy] enforce_new_defaults

Vrai : seules les nouvelles règles par défaut — avec reader, member, manager — s'appliquent. Faux : les anciennes règles restent acceptées en alternative, et tout rôle sur un projet suffit souvent à y écrire.

[oslo_policy] enforce_scope

Vrai : un jeton dont la portée ne figure pas parmi celles de la règle est refusé (403). Faux : la portée n'est que signalée dans les journaux.
CombinaisonComportementQuand
faux · fauxcomportement historique : reader peut écrire, jeton système accepté partoutclouds anciens, à faire évoluer
vrai · fauxrôles respectés, portées seulement journaliséesétape de migration : observer les refus de portée à venir
faux · vraicombinaison incohérente ; à éviter—
vrai · vraiSecure RBAC completcible ; valeur par défaut depuis oslo.policy 4.4 (2024.2)
Une option par service : chaque service lit son propre fichier de configuration. Un cloud peut être en Secure RBAC complet dans Nova et en mode historique dans un autre service.

La portée système : ce qu'il en reste

L'idée de départ : un jeton système pour tout ce qui touche à l'infrastructure, dans tous les services. Le résultat : l'objectif communautaire a été recentré sur la portée projet en 2023.

La portée domaine : la délégation

  • Un jeton de portée domaine ne donne accès à aucune ressource : pas d'instance, pas de réseau. Il sert à gérer l'identité du domaine.
  • Les règles de Keystone comparent le domaine du jeton à celui de la cible : domain_id:%(target.domain_id)s. Un gestionnaire du domaine « nord » reçoit 403 sur un utilisateur de « sud ».
  • Pour agir dans les projets du domaine, le gestionnaire a besoin en plus d'un rôle sur ces projets — direct, ou hérité depuis le domaine — et d'un jeton de portée projet.

Diagnostiquer un refus 403

  • Message type de Nova : « Policy doesn't allow os_compute_api:servers:create to be performed ». Le nom de la règle est dans le message : c'est le point de départ.

4 · Comptes de service

Les comptes des services sur Sunbeam

  • Chaque charm qui se relie à Keystone reçoit un compte dans le domaine des services, avec les rôles admin et service sur le projet des services.
  • admin est conservé tant que tous les services ne savent pas se contenter de service : c'est un choix de compatibilité du charm.
  • Conséquence : les secrets de ces comptes valent un accès administrateur. Ils vivent dans les relations Juju et les fichiers de configuration des pods : protéger l'accès au nœud de contrôle et au modèle Juju.
  • Ne rien y modifier à la main — ni mot de passe, ni rôle : le charm les recrée ou se désynchronise.
4 · Comptes de service

Les jetons de service

Problème : Nova démarre une opération longue pour Alice — une migration, un attachement de volume — puis appelle Cinder avec le jeton d'Alice. Si ce jeton expire en route, l'opération échoue à mi-parcours.

Solution : Nova joint son propre jeton, en second en-tête.

En-têteContenu
X-Auth-Tokenle jeton de l'utilisateur : ses droits s'appliquent
X-Service-Tokenle jeton du service : prouve que l'appel vient de Nova
Le service appelé accepte alors un jeton utilisateur expiré depuis peu, parce qu'un service de confiance l'accompagne. Les droits restent ceux de l'utilisateur : le service ne lui prête pas les siens.
# Côté service appelant (ex. nova.conf)
[service_user]
send_service_user_token = true
auth_type = password
username = nova
user_domain_name = service_domain
project_name = services
project_domain_name = service_domain

# Côté service appelé (keystonemiddleware)
[keystone_authtoken]
service_token_roles = service
service_token_roles_required = true
  • service_token_roles : le jeton de service doit porter ce rôle — c'est l'un des usages du rôle service.
  • Sur Sunbeam, ces sections sont écrites par les charms ; on les lit pour comprendre, on ne les modifie pas.
Valeurs d'exemple ; les noms de domaine et de projet des services sont à lire dans la configuration réelle de votre cloud.

4 · Comptes de service

Identifiants d'application : principe

  • Créés par l'utilisateur lui-même, sans intervention de l'administration : la délégation est en libre-service.
  • Le secret n'est montré qu'une fois : Keystone le hache avant de le stocker. Perdu, il ne se récupère pas — on en crée un autre.
  • Ne peuvent jamais dépasser leur créateur : on ne donne pas un rôle qu'on n'a pas. Retirer un rôle au créateur invalide ses identifiants sur ce projet.
  • Restreints par défaut : ils ne peuvent pas créer ni supprimer d'autres identifiants d'application — sauf option --unrestricted, à éviter.

4 · Comptes de service

Rotation et révocation

  • Rotation sans coupure : le nouvel identifiant existe avant que l'ancien disparaisse ; deux noms différents.
  • Fréquence : à chaque trimestre, ou plus court pour la production.
  • Révocation d'urgence : application credential delete — effet immédiat pour les nouveaux jetons ; les jetons déjà émis vivent jusqu'à leur expiration.
  • Pour tout couper : retirer le rôle du titulaire sur le projet, ce qui invalide ses identifiants.
  • Départ du titulaire : recréer les identifiants sous un autre titulaire avant de désactiver le compte.
  • Fuite suspectée : révoquer d'abord, enquêter ensuite.
4 · Comptes de service

Délégations (trusts)

Une délégation permet à un utilisateur — le délégant — d'autoriser un autre utilisateur — le délégataire — à agir en son nom, sur un projet, avec certains de ses rôles, pour une durée donnée.

Qui s'en sertPour quoi
Heatagir plus tard au nom de l'utilisateur : mise à l'échelle automatique, mise à jour d'une pile
Magnumpermettre au cluster de gérer ses ressources dans le projet
Automates internesrarement : on préfère les identifiants d'application
Différence clé : un identifiant d'application est un secret pour un programme ; une délégation est un lien entre deux comptes existants, que le délégataire utilise avec ses propres secrets.
# Alice délègue member sur prod-web au compte
# technique « exploitation-bot », pour trois mois
openstack trust create \
  --project prod-web --project-domain nord \
  --role member \
  --expiration 2027-01-13T00:00:00 \
  --trustor-domain nord --trustee-domain nord \
  alice exploitation-bot

openstack trust list
openstack trust show <id>
openstack trust delete <id>
  • --impersonate : le jeton obtenu porte l'identité du délégant. Plus transparent pour les services, moins lisible dans les journaux — à éviter sauf besoin.
  • Délégations créées par les services — Heat, Magnum — : les lister à la revue ; un délégant parti les rend inopérantes.

Interdits

  • Le fichier admin-openrc de Sunbeam dans un pipeline, un dépôt, un poste de développeur.

Le meilleur secret est celui qui n'existe pas : lorsque l'outil le permet, préférer une authentification fédérée de courte durée à un secret statique.

Cette matrice suppose l'arbre de projets « par environnement » du module précédent : nœuds prod et horsprod, feuilles par application.

Pas à pas (1) : groupes et affectations

# Étape 0 — prérequis : cloud Sunbeam déployé, client
# openstack installé, domaine nord et projets créés
sunbeam openrc > admin-openrc
source admin-openrc
openstack role list      # reader member manager admin service

# Étape 1 — les groupes
for g in gestionnaires-nord exploitation-prod \
         developpeurs audit; do
  openstack group create $g --domain nord
done

# Étape 2 — délégation du domaine
openstack role add manager --domain nord \
  --group gestionnaires-nord --group-domain nord

# Étape 3 — audit : lecture du domaine et des projets
openstack role add reader --domain nord \
  --group audit --group-domain nord
openstack role add reader --domain nord --inherited \
  --group audit --group-domain nord
# Étape 4 — production : exploitation et développeurs
openstack role add member --inherited \
  --project prod --project-domain nord \
  --group exploitation-prod --group-domain nord
openstack role add reader --inherited \
  --project prod --project-domain nord \
  --group developpeurs --group-domain nord

# Étape 5 — hors production : affectations directes
for p in rec-web dev-web; do
  openstack role add member \
    --project $p --project-domain nord \
    --group developpeurs --group-domain nord
done

# Étape 6 — les personnes, dans les groupes
openstack group add user --group-domain nord \
  --user-domain nord developpeurs alice

# Contrôle
openstack role assignment list --names \
  --effective --user alice --user-domain nord
Domaine raccordé à un annuaire (sunbeam ldap add-domain) : les groupes viennent de l'annuaire ; on saute les étapes 1 et 6.

Corrigé — points clés

  • 1 : console refusée — règle de type member ; attention si la création réussit : nouvelles règles inactives.
  • 2 : 403 sur admin : il ne figure pas dans la liste des rôles attribuables par un manager.
  • 3 : un jeton de domaine n'ouvre aucune ressource. Il faut un rôle sur le projet — reader suffit — et un jeton de portée projet.
  • 4 : après suppression, une nouvelle authentification échoue (401) ; un jeton déjà obtenu fonctionne jusqu'à son expiration.
  • 5 : Neutron répond 401 : en validant le jeton, Keystone constate que cet appel ne figure pas dans les règles d'accès.
  • 6 : attendu — l'équipe plateforme pour admin ; les comptes des services, et eux seuls, pour service.
Prérequis du TP : cloud Sunbeam opérationnel, admin-openrc, domaine nord et un projet contenant au moins une instance.
Synthèse

Ce qu'il faut retenir

Les rôles standards

  • reader lit, member agit, manager gère, admin administre.
  • service est réservé aux services, hors hiérarchie.
  • Implications : une affectation suffit.
  • Rôle maison = surcharge de politique ; en dernier recours.

Secure RBAC

  • Trois portées : système, domaine, projet ; un jeton, une portée.
  • Règle = portée acceptée + rôle + cible dans la portée.
  • Deux options par service, à vrai par défaut depuis 2024.2.
  • admin de projet reste global : ne jamais le déléguer.

Les comptes de service

  • Comptes des services : gérés par les charms, sensibles, intouchables.
  • Automates : identifiant d'application, rôle minimal, un projet, une date de fin.
  • Règles d'accès pour restreindre aux appels utiles.
  • Rotation sans coupure, révocation immédiate.
