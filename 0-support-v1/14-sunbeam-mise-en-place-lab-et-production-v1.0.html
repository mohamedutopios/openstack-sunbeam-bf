Introduction

Objectif et déroulé

Objectif : savoir dérouler, dans le bon ordre et avec les bonnes commandes, la mise en place d'un cloud Sunbeam — en comprenant à chaque étape ce qui est créé, et en distinguant ce qui est propre au lab de ce qu'exige une production.

À l'issue de ce module, vous saurez :

  • Nommer les briques qu'installe Sunbeam et les rôles d'un nœud.
  • Préparer le réseau (gestion, externe, stockage), le DNS et les disques avant d'installer.
  • Écrire un manifeste et lancer bootstrap, join, resize, configure.
  • Expliquer, commande par commande, comment le lab a été construit et ce qu'il a fallu corriger.
  • Dérouler un déploiement 3 contrôle + 2 calcul + 1 stockage et en juger les limites.

Minimum officiel multi-nœuds (2024.1) : par nœud, 16 cœurs amd64, 32 GiB de RAM, 500 GiB SSD libres pour le système, un SSD de 500 GiB pour Ceph, deux réseaux 1 Gbps. « Trois nœuds sont nécessaires pour un fonctionnement multi-nœuds. »

Trois adresses à nommer avant d'installer

Le manifeste fixe les VIP et leurs noms (endpoints). Le DNS doit les résoudre avant le bootstrap : les services valident les jetons sur le nom interne. Lab : cloud.lab.test, internal.lab.test, rgw.lab.test.

La carte externe n'a pas d'adresse

Elle appartient à Open vSwitch. Lui mettre une IP casse le pont. Sur le lab, provider0 de Lab-Sunbeam est UP sans adresse ; c'est Lab-Services qui porte .2 et fait passerelle.

MTU

Les réseaux des projets sont encapsulés (Geneve) : MTU 1442 au lieu de 1500. Tout ce qui est passerelle du réseau externe doit l'accepter — la cause du correctif MTU sur Lab-Services.
1 · Ce qu'est un déploiement Sunbeam

Les étapes, dans l'ordre

  1. Dessiner les réseaux et le plan d'adressage : gestion, externe, stockage ; VIP des API ; passerelle du réseau externe.
  2. DNS et noms : chaque nœud a un FQDN ; les trois noms des API résolvent vers les VIP. NTP en place.
  3. Ubuntu Server 24.04 sur chaque nœud, netplan écrit, disques Ceph vides et non partitionnés.
  4. Installer le snap : sudo snap install openstack --channel 2024.1/stable, même version partout.
  5. Préparer le nœud : sunbeam prepare-node-script | bash -x (dépendances, sudo sans mot de passe, groupe snap_daemon).
  6. Écrire le manifeste : CIDR de gestion, plage MetalLB, noms des API, base single ou multi, réseau externe, disques Ceph.
  7. Bootstrap sur le premier nœud : sunbeam cluster bootstrap --role … --manifest … — crée Juju, Kubernetes, puis déploie tout.
  8. Joindre les autres nœuds : cluster add (jeton) puis cluster join --role … ; resize quand il y a 3 nœuds de contrôle.
  9. Configurer : sunbeam configure — réseau externe, utilisateur de démonstration, règles de sécurité.
  10. Vérifier, puis durcir : cluster list, juju status, une première VM ; puis TLS, observabilité, sauvegardes.
Pourquoi cet ordre : le bootstrap grave dans le cluster ce que le manifeste et le réseau lui donnent — CIDR, base single/multi, région, noms des API. Ces choix ne se changent plus ensuite sans tout refaire. Tout ce qui précède l'étape 7 est donc à vérifier deux fois.

Les choix qui comptent

  • MAC fixes (08:00:27:56:…, 08:00:27:57:…) : netplan nomme les cartes par leur MAC. C'est ce qui rend les OVA transportables.
  • auto_config: false : Vagrant ne touche pas aux adresses ; c'est netplan, dans le script, qui les fixe.
  • Disque Ceph séparé, 100 Go, vide : MicroCeph exige un disque entier, sans partition.
  • VT-x imbriqué : sans lui, pas de KVM dans la VM, donc pas d'instances.
  • Promiscuité « Tout autoriser » sur les cartes 2 et 3 : les VIP MetalLB et les instances répondent avec d'autres MAC que celle de la carte ; VirtualBox les filtrerait.
Fait : réseaux hôte 192.168.56.1/24 et 192.168.57.1/24 créés dans VirtualBox, DHCP désactivé. Hôte Linux : /etc/vbox/networks.conf doit autoriser ces plages.

Étape 2 · Lab-Services : passerelle NAT et MTU

# /etc/sysctl.d/70-lab-router.conf
net.ipv4.ip_forward=1

# scripts/router.sh, installé en /usr/local/sbin/lab-router,
# relancé après Docker (drop-in docker.service.d/lab-router.conf : ExecStartPost=)
UPLINK=$(ip -4 route show default | awk 'NR==1 {print $5}')
iptables -N DOCKER-USER 2>/dev/null || true
iptables -C FORWARD -j DOCKER-USER 2>/dev/null || iptables -I FORWARD 1 -j DOCKER-USER
for item in mgmt0:192.168.56.0/24 provider0:192.168.57.0/24; do
  LAN=${item%%:*}; CIDR=${item#*:}
  # chaque règle : testée (-C), ajoutée seulement si absente
  iptables -t nat -C POSTROUTING -s "$CIDR" -o "$UPLINK" -j MASQUERADE 2>/dev/null \
    || iptables -t nat -A POSTROUTING -s "$CIDR" -o "$UPLINK" -j MASQUERADE
  iptables -C DOCKER-USER -i "$LAN" -o "$UPLINK" -s "$CIDR" -j ACCEPT 2>/dev/null \
    || iptables -I DOCKER-USER 1 -i "$LAN" -o "$UPLINK" -s "$CIDR" -j ACCEPT
  iptables -C DOCKER-USER -i "$UPLINK" -o "$LAN" -d "$CIDR" \
      -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT 2>/dev/null \
    || iptables -I DOCKER-USER 1 -i "$UPLINK" -o "$LAN" -d "$CIDR" \
      -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
done

Ce que fait ce routeur

  • Les instances Nova ont pour passerelle 192.168.57.2 : leurs paquets sortent par Lab-Services, masqués derrière la carte NAT.
  • Docker réécrit la chaîne FORWARD au démarrage : d'où la chaîne DOCKER-USER, que Docker respecte, et le relancement après Docker.
  • Chaque règle est testée (-C) avant d'être ajoutée : le script est rejouable.

Le correctif MTU (15 octobre)

  • Symptôme : depuis une instance, ping et DNS passent, apt et HTTPS restent bloqués.
  • Cause : le réseau des projets est à 1442 (Geneve). Le NAT de VirtualBox renvoie des segments de 1480 octets, qu'OVN jette.
  • Correctif : mtu: 1442 sur provider0, puis sudo netplan apply. Contrôle : ip link show provider0 doit afficher mtu 1442.

held : Sunbeam bloque la mise à jour automatique des snaps qu'il pilote (openstack, k8s, microceph, openstack-hypervisor, cinder-volume). Une mise à jour se fait par Sunbeam, pas par snap refresh.

Ce que fait prepare-node-script

  • Installe openssh-server et les dépendances système.
  • Donne au compte courant sudo sans mot de passe : Juju s'en servira pour installer les snaps de machine.
  • Ajoute le compte au groupe snap_daemon, pour parler au démon de cluster.
  • Vérifie la virtualisation, la mémoire, le disque libre.
  • Avec --bootstrap : prépare aussi ce qu'il faut au premier nœud (LXD n'est plus requis en 2024.1 ; le contrôleur Juju va sur Kubernetes).
Pourquoi un script et pas un paquet : ces réglages touchent au compte de l'exploitant et à sudoers. Les générer et les lire avant de les exécuter, c'est garder la main sur ce qui est changé sur la machine.

Durée sur le lab : de l'ordre de l'heure, dépendante du téléchargement des charms et des images. Le cloud n'est utilisable qu'une fois les 25 applications du modèle openstack en active.

Ce que le bootstrap fait, dans l'ordre

  1. Démarre le démon de cluster sunbeamd et crée le déploiement star-heron, type local.
  2. Installe le snap k8s et crée le cluster Kubernetes, avec MetalLB sur la plage donnée.
  3. Amorce le contrôleur Juju (sunbeam-controller) sur Kubernetes ; VIP 192.168.56.200:17070.
  4. Ajoute la machine au modèle admin/openstack-machines (cloud manual) et y déploie sunbeam-machine, microceph (OSD sur /dev/sdb), openstack-hypervisor, cinder-volume.
  5. Déploie le plan openstack-plan (Terraform) : les 25 charms *-k8s dans le modèle openstack, trois Traefik sur les trois VIP.

Ce qu'il a fallu corriger après l'import des OVA

1 · Noyau des instances en panique

Symptôme : instance ACTIVE, mais Kernel panic, NULL pointer dereference dans sa console. Cause : KVM imbriqué dans VirtualBox sur les Intel 12ᵉ à 14ᵉ génération corrompt la mémoire de l'invité avec EPT.
echo "options kvm_intel ept=0" | \
  sudo tee /etc/modprobe.d/kvm-intel-ept.conf
sudo modprobe -r kvm_intel && sudo modprobe kvm_intel
cat /sys/module/kvm_intel/parameters/ept   # N

2 · L'OSD Ceph ne démarre plus

Symptôme : 0 osds up, lancement d'instance en ERROR, HTTP 502 Glance. Cause : à l'import, VirtualBox donne au disque un nouvel identifiant ; le lien /dev/disk/by-id/… de l'OSD est cassé.
OSD=/var/snap/microceph/common/data/osd/ceph-1
sudo ls -l $OSD/block
sudo ln -sfn \
  /dev/disk/by-path/pci-0000:00:1f.2-ata-2 \
  $OSD/block
sudo systemctl reset-failed \
  snap.microceph.osd.service
sudo snap restart microceph.osd
sudo ceph -s   # 1 osds: 1 up

Ce que le rôle compute installe sur le nœud

  • Le nœud entre dans admin/openstack-machines (machines 3 et 4) ; Juju y déploie sunbeam-machine et openstack-hypervisor.
  • Le snap openstack-hypervisor apporte nova-compute, libvirt/KVM, Open vSwitch et l'agent OVN (chassis) ; le nœud s'enregistre auprès de Nova et d'OVN central.
  • La carte bond0.20, trouvée dans external_network.nics, devient un port du pont br-ex : c'est par là que sortent les IP flottantes des VM de ce nœud.
  • Le nœud monte les pools Ceph (nova, cinder, glance) par le VLAN 30 : sans sto1, aucune VM ne démarre.
Deux nœuds de calcul, c'est le minimum utile : on peut vider l'un (openstack compute service set --disable, migration à chaud) pour le mettre à jour. Avec un seul, chaque maintenance arrête les VM.

Pourquoi HEALTH_WARN est honnête

  • Ceph place 3 copies de chaque objet sur 3 hôtes différents (règle CRUSH par défaut). Avec un seul hôte, il ne peut en placer qu'une : les groupes de placement restent undersized, les écritures sont acceptées mais rien n'est répliqué.
  • La vraie réponse est sto2 et sto3 (même manifeste, cluster add, join --role storage) : Ceph rééquilibre seul.

Si l'on doit vivre avec un seul nœud (préproduction, démarrage) : changer le domaine de défaillance d'hôte à OSD. On garde 3 copies, sur 3 disques du même serveur : protège d'une panne de disque, pas d'une panne de serveur.

# sur sto1, avant de créer des volumes
sudo ceph config set global osd_crush_chooseleaf_type 0
sudo ceph osd crush rule create-replicated replicated_osd default osd
for p in $(sudo ceph osd pool ls); do
  sudo ceph osd pool set "$p" crush_rule replicated_osd; done
sudo ceph -s   # HEALTH_OK, pgs active+clean
À dire au client : « 3 + 2 + 1 » est un cloud à haute disponibilité du plan de contrôle et du calcul, avec un point unique de défaillance sur les données. Le devis suivant, c'est sto2 et sto3.

# sur la machine « Sunbeam Client » (une VM d'administration)

sunbeam deployment space map internal-space:internal
sunbeam deployment space map public-space:public
sunbeam deployment space map data-space:data
sunbeam deployment space map storage-space:storage

sunbeam cluster bootstrap --manifest ~/prod.yaml
sunbeam cluster deploy

Ce que MAAS apporte, que le mode manuel n'a pas

  • Les réseaux par rôle deviennent explicites : six espaces (spaces) — management, internal, public, data, storage, storage-cluster — et chaque étiquette de machine dit lesquels elle exige. En mode manuel, Ceph et les API partagent le réseau de gestion.
  • Les machines par étiquette : control, compute, storage, network, juju-controller, sunbeam, plus openstack-acme-prod pour les rattacher au déploiement. La carte externe se marque neutron:physnet1, sous-réseau non configuré.
  • L'installation du système et le netplan sont faits par MAAS, identiques sur toutes les machines : plus de fichier à recopier sur six nœuds.
  • Le remplacement d'une machine : on l'étiquette, cluster deploy la prend.

Ce qu'il faut retenir

Avant d'installer

  • Dessiner les réseaux : gestion (VIP), externe (sans IP sur la carte), stockage.
  • Les trois noms des API dans le DNS avant le bootstrap.

Les commandes, dans l'ordre

  • snap install openstack --channel 2024.1/stable
  • sunbeam prepare-node-script | bash -x
  • cluster bootstrap --role … --manifest …
  • cluster add → cluster join --role … → cluster resize (à 3 control)
  • configure --manifest …, openrc, une VM de preuve.

Lab contre production

  • Le lab : 1 nœud, base single, HTTP, DNS et passerelle dans une VM — fait pour être cassé et refait.
  • La production : 3 control pour le quorum, 2 compute pour la maintenance, 3 storage pour la réplication.
  • « 3 + 2 + 1 » marche, avec un point unique de défaillance sur les données : le dire, le chiffrer, le planifier.
