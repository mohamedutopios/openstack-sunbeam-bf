Introduction

Objectif et déroulé

Objectif : comprendre comment Keystone répond aux quatre questions que pose toute requête dans OpenStack — qui es-tu, sur quoi agis-tu, où est le service, en as-tu le droit — et savoir le configurer et le diagnostiquer sur un cloud Sunbeam.

À l'issue de ce module, vous saurez :

  • Décrire les entités de Keystone et leurs relations.
  • Lire et exploiter le catalogue de services.
  • Expliquer le cycle de vie d'un jeton : émission, contenu, validation, expiration, rotation des clés.
  • Raccorder une source d'identité externe : annuaire LDAP ou fournisseur OIDC / SAML.
  • Lire une règle de politique et prévoir qui peut faire quoi.
  • Diagnostiquer un refus : 401, 403, service introuvable.

1 · Keystone dans le cloud

Quatre questions, un service

Ce que Keystone ne fait pas : il ne décide pas si l'on peut créer une instance ou supprimer un volume. Cette décision appartient à Nova ou à Cinder, à partir de ce que Keystone a certifié.
Version de l'API : une seule, la v3. Les notions de domaine, de groupe et de portée système n'existent que dans celle-ci.
1 · Keystone dans le cloud

Une requête de bout en bout

Deux appels à Keystone par opération : l'un par l'utilisateur, pour obtenir le jeton ; l'autre par le service, pour le valider. Le second est mis en cache par le service pour ne pas être répété à chaque requête.
Conséquence d'exploitation : si Keystone est lent, tout le cloud est lent ; s'il est indisponible, les jetons déjà validés et encore en cache fonctionnent quelques minutes, puis tout s'arrête.

Architecture interne

1 · Keystone dans le cloud

Keystone sur Sunbeam : où il tourne

  • Un pod par unité, trois unités en haute disponibilité : n'importe laquelle traite n'importe quelle requête, car l'état est dans la base et les clés sont identiques partout.
  • Deux entrées : les points d'accès public et interne passent par deux Traefik distincts, sous un préfixe de chemin.
  • Aucun fichier édité à la main : keystone.conf est produit par le charm à partir de ses options et de ses relations.
  • Les autres services n'ont pas de compte créé à la main : la relation avec Keystone crée leur utilisateur de service et inscrit leurs points d'accès.
juju status -m openstack keystone
juju config -m openstack keystone
juju actions -m openstack keystone
sudo k8s kubectl -n openstack get pods \
  -l app.kubernetes.io/name=keystone
Options, actions et noms exacts varient selon la révision du charm : ces quatre commandes les montrent pour votre cloud.

Domaines : la frontière d'administration

Ce qu'est un domaine

  • Un espace de noms : les noms d'utilisateur, de groupe et de projet ne sont uniques qu'à l'intérieur d'un domaine. Deux domaines peuvent chacun avoir un projet « web ».
  • Une frontière de délégation : on peut confier à quelqu'un l'administration d'un domaine — créer ses utilisateurs, ses projets, attribuer des rôles — sans lui donner la main sur le reste du cloud.
  • Un point de raccordement : chaque domaine peut avoir sa propre source d'identité — la base locale pour l'un, l'annuaire de l'entreprise pour un autre.
  • La racine d'une hiérarchie de projets : techniquement, un domaine est lui-même un projet particulier, sommet de son arbre.
Un domaine ne se supprime pas d'un geste : il faut d'abord le désactiver, et la suppression emporte tout ce qu'il contient.
UsageUn domaine par…
Hébergeurclient : chacun gère ses utilisateurs et ses projets
Grand groupefiliale ou direction
Source d'identitéannuaire raccordé : un domaine LDAP, un domaine fédéré
Séparation techniqueles comptes des services d'un côté, les humains de l'autre
openstack domain list
openstack domain create --description "Filiale Nord" nord
openstack domain show nord

# Désactiver puis supprimer
openstack domain set --disable nord
openstack domain delete nord
Désactiver un domaine coupe immédiatement l'authentification de tous ses utilisateurs et invalide leurs jetons : c'est l'interrupteur d'urgence pour un locataire.
2 · Les entités

Projets : le conteneur des ressources

  • C'est l'unité de propriété : quotas, facturation et isolation réseau se raisonnent par projet.
  • C'est la portée la plus courante d'un jeton : on travaille « dans » un projet.
  • Hiérarchie : un projet peut avoir des sous-projets ; un rôle peut être hérité vers le bas de l'arbre. L'isolation des ressources, elle, reste par projet.
  • Étiquettes libres pour classer : environnement, centre de coût.
  • Désactivé, un projet refuse toute nouvelle authentification vers lui, sans que ses ressources soient détruites.
openstack project create --domain nord production
openstack project create --domain nord \
  --parent production web
openstack project list --domain nord --long
openstack project set --tag prod web
Hiérarchie et quotas font l'objet du module suivant ; on en retient ici le principe.
2 · Les entités

Utilisateurs et groupes

Utilisateur

  • Identifiant unique dans tout le cloud ; nom unique dans son domaine seulement.
  • Trois origines possibles : créé dans la base locale, lu dans un annuaire LDAP, ou créé à la volée lors d'une connexion fédérée.
  • Projet par défaut : facultatif ; sert quand une authentification ne précise pas de portée.
  • Options par utilisateur : dispense de changement de mot de passe, exemption de verrouillage, règles d'authentification multifacteur.

Groupe

  • Contient des utilisateurs du même domaine.
  • Un rôle attribué au groupe vaut pour tous ses membres, présents et futurs.
  • Avec un annuaire ou une fédération, les groupes viennent de la source externe : on attribue les rôles aux groupes, jamais aux personnes.
openstack user create --domain nord \
  --password-prompt --email alice@exemple.fr alice
openstack group create --domain nord developpeurs
openstack group add user \
  --group-domain nord --user-domain nord \
  developpeurs alice
openstack user set --disable alice    # coupe l'accès
Type de compteParticularité
Humainmot de passe ou connexion fédérée ; à rattacher à des groupes
Service du cloudun compte par service (nova, neutron…), créé par le charm, rôle service ou admin
Automatisationplutôt un identifiant d'application qu'un utilisateur dédié
Désactiver plutôt que supprimer : la suppression d'un utilisateur efface aussi ses attributions et ses identifiants d'application ; la désactivation est réversible.
2 · Les entités

Rôles et rôles impliqués

  • Un rôle est une étiquette. Keystone ne sait pas ce que « member » permet dans Nova : ce sont les règles de politique de Nova qui lui donnent un sens.
  • Cinq rôles fournis d'office : admin, member, reader depuis longtemps ; manager et service depuis la version 2023.2.
  • Rôle impliqué : une règle « tel rôle entraîne tel autre », résolue par Keystone à l'émission du jeton. Le jeton d'un administrateur contient donc aussi les rôles inférieurs.
  • Rôles supplémentaires : certains services en définissent — par exemple pour l'équilibrage de charge ou l'orchestration.
  • Rôle propre à un domaine : un alias local qui implique des rôles globaux ; rarement nécessaire.
openstack role list
openstack implied role list
openstack role create auditeur
openstack implied role create auditeur \
  --implied-role reader
Créer un rôle ne donne aucun droit tant qu'aucune règle de politique ne le mentionne : préférer les rôles par défaut, compris par tous les services.

Les trois portées

PortéeDemandée avecSert à
projet--os-project-namele travail courant sur les ressources
domaine--os-domain-namegérer identités et projets d'un domaine
système--os-system-scope alladministrer le cloud
aucune—prouver son identité, lister ses projets
  • Un jeton n'a qu'une portée. Pour agir dans un autre projet, on demande un autre jeton — le client le fait seul, à partir des identifiants.
  • Les droits ne débordent pas : être admin d'un domaine ne donne rien sur le domaine voisin.
  • La portée fait partie de la décision : une règle de politique peut exiger « rôle reader et portée système ».
Tous les services n'exploitent pas encore la portée système de la même façon : dans la pratique, beaucoup d'opérations d'administration passent par un jeton de portée projet avec le rôle admin.

Mettre en place un locataire : la séquence complète

  --user-domain nord web-dev alice

openstack user create --domain nord --password-prompt bob

  --domain nord manager

Ce que fait le client, à chaque commande

3 · Le catalogue

Le catalogue sur Sunbeam

  • Le catalogue se remplit seul : chaque charm de service déclare ses points d'accès à Keystone par une relation ; l'ajout d'une fonctionnalité Sunbeam ajoute ses entrées.
  • Adresses de service : prises dans les plages réservées aux API, l'une sur le réseau public, l'autre sur le réseau interne.
  • Un seul port, des chemins : tous les services partagent l'adresse de Traefik et se distinguent par leur préfixe.
  • TLS : en activant la fonctionnalité correspondante, les URL publiques passent en https et le catalogue est mis à jour par les charms.
  • Nom d'hôte : on peut publier un nom plutôt qu'une adresse IP ; le manifeste prévoit ce réglage pour chaque entrée.
Ne pas corriger le catalogue à la main : une URL modifiée par openstack endpoint set sera réécrite par le charm au prochain événement. Le bon levier est la configuration de Sunbeam.
Le nom exact de la relation et des préfixes se lit dans juju status --relations et openstack endpoint list.

Jetons et portées

Type de jetonContientSert àS'obtient en demandant
Sans portéel'identité seule : ni rôles, ni catalogueprouver qui l'on est ; lister ses projets ; obtenir ensuite des jetons à portée sans redonner son mot de passeaucune portée

Un jeton est un « porteur »

Quiconque le détient peut s'en servir jusqu'à son expiration. Il se protège comme un mot de passe : jamais dans un journal, un ticket ou un dépôt.

Un jeton ne se modifie pas

Si les rôles changent, le jeton déjà émis garde l'ancienne liste jusqu'à ce que le service le revalide ; un retrait de rôle provoque sa révocation.

Un jeton est court

Une heure par défaut dans Keystone. Les clients en redemandent un automatiquement à partir des identifiants.
Changer de projet = changer de jeton. C'est ce que fait Horizon quand on sélectionne un autre projet dans son menu : il échange son jeton contre un jeton de l'autre portée.

4 · Les jetons

Anatomie d'un jeton Fernet

Rien n'est stocké : Keystone ne garde aucune trace des jetons émis. Il lui suffit de la clé pour déchiffrer et vérifier celui qu'on lui présente — d'où l'absence de table de jetons à purger.
Chiffré, donc opaque : impossible de lire ou de modifier un jeton sans les clés. Qui détient les clés, en revanche, peut fabriquer des jetons pour n'importe qui.

4 · Les jetons

La validation par les services

  • Chaque service embarque le même composant — keystonemiddleware — placé devant son API. C'est lui qui parle à Keystone ; le code du service ne voit que des en-têtes.
  • Le service a son propre compte dans Keystone : il s'authentifie pour avoir le droit de valider les jetons des autres.
  • Cache : le résultat d'une validation est gardé quelques minutes. C'est aussi le délai pendant lequel un jeton révoqué peut encore passer.
  • Section à connaître dans la configuration de tout service : [keystone_authtoken] — adresse de Keystone, compte de service, cache.
4 · Les jetons

Opérations longues et jetons de service

Le problème

  • Un jeton dure une heure ; une migration à chaud ou la création d'une grosse image peut durer plus.
  • En cours de route, Nova doit encore appeler Cinder, Neutron ou Glance au nom de l'utilisateur.

La solution : deux jetons dans la requête

  • Le jeton de l'utilisateur, dans X-Auth-Token : il dit pour qui l'on agit.
  • Le jeton du service appelant, dans X-Service-Token : il prouve que la requête vient bien d'un service du cloud.
  • Si le second est valide et porte le rôle service, le service appelé accepte le premier même expiré, dans la limite de allow_expired_window.
C'est pour cela que le rôle service existe, à part de la chaîne des autres : il ne donne aucun droit sur les ressources, seulement cette confiance entre services.
Symptôme d'une mauvaise configuration : des opérations longues qui échouent en 401 au bout d'une heure pile.

Trois familles de sources

Point commun : seule l'identité change de source. Projets, rôles et attributions restent toujours dans la base de Keystone — l'annuaire ne sait rien d'OpenStack.
Elles se combinent, par domaine : un domaine local pour les services et le secours, un domaine LDAP pour les employés, un domaine fédéré pour les partenaires.
5 · Les sources d'identité

La base locale et sa politique de sécurité

Comment sont gardés les mots de passe

  • Jamais en clair : une empreinte calculée par un algorithme volontairement lent — bcrypt par défaut — avec un sel propre à chaque compte.
  • L'historique des empreintes est conservé, pour interdire la réutilisation.

Ce que la base locale sait faire

  • Créer, modifier, désactiver des comptes et des groupes par l'API.
  • Laisser l'utilisateur changer lui-même son mot de passe.
  • Appliquer une politique de sécurité : verrouillage, expiration, complexité.
  • Exiger un second facteur, compte par compte.
Ces règles ne valent que pour la base locale. Pour LDAP ou la fédération, c'est la source externe qui applique sa propre politique.

5 · Les sources d'identité

LDAP : un annuaire par domaine

  • Une configuration par domaine : chaque domaine peut pointer vers un annuaire différent, ou vers une branche différente du même.
  • Authentification : Keystone cherche l'entrée de l'utilisateur, puis tente de s'y connecter avec le mot de passe fourni. C'est l'annuaire qui dit oui ou non.
  • Lecture seule : on ne crée ni ne modifie de compte LDAP par l'API d'OpenStack.
  • Identifiants : Keystone attribue à chaque entrée LDAP un identifiant stable, gardé dans une table de correspondance.
  • Groupes : ceux de l'annuaire sont visibles ; on leur attribue des rôles comme à des groupes locaux.

LDAP sur Sunbeam

Prérequis : l'annuaire joignable depuis les nœuds de contrôle ; un compte de recherche en lecture ; le certificat de l'autorité si la liaison est en TLS.

# entreprise.yaml — les quatre clés obligatoires
url: ldaps://ldap.exemple.fr:636
user: cn=keystone,ou=services,dc=exemple,dc=fr
password: "••••••••"
suffix: dc=exemple,dc=fr
# puis, selon l'annuaire :
user_tree_dn: ou=personnes,dc=exemple,dc=fr
user_objectclass: inetOrgPerson
user_id_attribute: uid
user_name_attribute: uid
group_tree_dn: ou=groupes,dc=exemple,dc=fr
group_objectclass: groupOfNames
Le compte de recherche n'a besoin que de lire utilisateurs et groupes. Son mot de passe est dans ce fichier : le traiter comme un secret et le supprimer après usage.
# 1 · Activer la fonctionnalité, une fois
sunbeam enable ldap

# 2 · Raccorder un domaine à l'annuaire
sunbeam ldap add-domain \
  --domain-config-file ./entreprise.yaml \
  --ca-cert-file ./ca-entreprise.pem entreprise

# 3 · Vérifier
sunbeam ldap list-domains
openstack user list --domain entreprise
openstack group list --domain entreprise

# 4 · Donner des droits — aux groupes de l'annuaire
openstack role add --group dev --group-domain entreprise \
  --project web --project-domain nord member

# Modifier, retirer
sunbeam ldap update-domain \
  --domain-config-file ./entreprise.yaml entreprise
sunbeam ldap remove-domain entreprise
Retirer ne supprime que la liaison avec l'annuaire : le domaine, ses projets et ses attributions restent. Pour tout enlever, openstack domain delete.

openstack domain create partenaires

  --remote-id $REMOTE_ID --domain partenaires entra-groupe

openstack mapping create --rules regles.json entra_openid

  --identity-provider entra-groupe \

Les règles de correspondance

# regles.json — règle simple : tout utilisateur authentifié
[
  {
    "local": [
      { "user":  { "name": "{0}" } },
      { "group": { "name": "federes",
                   "domain": { "name": "partenaires" } } }
    ],
    "remote": [
      { "type": "REMOTE_USER" }
    ]
  }
]
# Règle conditionnelle : seulement un groupe du fournisseur
"remote": [
  { "type": "OIDC-preferred_username" },
  { "type": "OIDC-groups", "any_one_of": ["cloud-dev"] }
]
ÉlémentSignification
remoteconditions sur les attributs transmis par le fournisseur ; toutes doivent être satisfaites
localce que l'on en fait : nom de l'utilisateur local, groupes d'affectation
{0}, {1}…valeur du premier, du deuxième attribut de remote
any_one_ofla valeur doit figurer dans la liste
not_any_ofla valeur ne doit pas y figurer
  • Les règles sont évaluées dans l'ordre ; un utilisateur peut cumuler les groupes de plusieurs règles satisfaites.
  • Aucune règle satisfaite : connexion refusée, même si l'authentification chez le fournisseur a réussi.
  • Une seule correspondance par couple fournisseur + protocole ; une même correspondance peut servir à plusieurs fournisseurs.
  • Noms des attributs : ils dépendent du module et du fournisseur ; les journaux de Keystone en mode détaillé montrent ceux qui arrivent réellement.
Piège classique : une règle trop large donne un rôle à tout compte du fournisseur. Toujours conditionner à un groupe dédié au cloud.

6 · Politiques d'accès

De la requête à la décision

  • La décision est locale : Nova applique les règles de Nova, Cinder celles de Cinder. Keystone n'est pas consulté pour décider, seulement pour valider le jeton.
  • Une règle par opération d'API : plusieurs centaines dans un cloud complet.
  • 401 ou 403 ? 401 : le jeton est absent, expiré ou invalide — on ne sait pas qui vous êtes. 403 : on le sait, et la règle dit non.
  • Le rôle seul ne suffit pas : la plupart des règles vérifient aussi que la cible appartient à la portée du jeton.

Anatomie d'une règle

"admin_required":         "role:admin or is_admin:1"
"service_role":           "role:service"

"identity:list_users":    "(rule:admin_required)
                           or (role:reader and system_scope:all)
                           or (role:reader and domain_id:%(target.domain_id)s)"

"identity:get_user":      "(rule:admin_required) or (role:reader and system_scope:all)
                           or (role:reader and token.domain.id:%(target.user.domain_id)s)

"identity:create_project": "(rule:admin_required)
                            or (role:manager and domain_id:%(target.project.domain_id)s …)"
ÉlémentSignification
role:readerle jeton porte ce rôle
rule:admin_requiredrenvoi à une autre règle, réutilisable
system_scope:allle jeton est de portée système
domain_id:%(target.domain_id)sle domaine du jeton est celui de la cible
user_id:%(target.user.id)sl'appelant est l'utilisateur visé

Lecture de identity:get_user

  • un administrateur ; ou
  • un lecteur de portée système ; ou
  • un lecteur du domaine de l'utilisateur consulté ; ou
  • l'utilisateur lui-même, quel que soit son rôle.
À remarquer : admin_required ne mentionne aucune portée. Dans Keystone, le rôle admin reste très puissant quelle que soit la cible sur laquelle il est détenu : ne jamais l'attribuer « sur un projet » en pensant le cantonner.
6 · Politiques d'accès

Règles par défaut et surcharges

  • Pas de fichier, pas de problème : un service sans policy.yaml applique les règles de sa version. C'est l'état recommandé.
  • Format : YAML ; l'ancien format JSON est déprécié depuis Wallaby.
  • Rechargement : le fichier est relu à chaud, sans redémarrage.
  • Chaque surcharge est une dette : à chaque montée de version, il faut vérifier qu'elle a encore un sens face aux nouveaux défauts.
# Voir les règles par défaut d'un service
oslopolicy-sample-generator --namespace keystone

# Voir les règles effectives, surcharges comprises
oslopolicy-policy-generator --namespace keystone

# Repérer les surcharges devenues inutiles
oslopolicy-list-redundant --namespace keystone
# policy.yaml — exemple de surcharge
# autoriser le rôle « auditeur » à lister les utilisateurs
"identity:list_users": "(rule:admin_required)
   or (role:reader and system_scope:all)
   or role:auditeur"

Sur Sunbeam

  • Les fichiers de configuration sont dans les pods et réécrits par les charms : un policy.yaml déposé à la main ne survit pas.
  • Une surcharge passe par ce que le charm expose ; à défaut, s'en tenir aux rôles et règles par défaut.
  • Les outils oslopolicy-* s'exécutent dans le conteneur du service, par kubectl exec.
6 · Politiques d'accès

Portées et nouveaux rôles par défaut

D'où l'on vient

  • Longtemps, les règles se résumaient à « admin ou propriétaire ». Le rôle admin, attribué sur n'importe quel projet, valait administrateur du cloud entier.
  • Pas de lecture seule : pour voir, il fallait pouvoir modifier.

Ce qui a changé — le « RBAC sécurisé »

  • Des rôles gradués partout : reader, member, manager, admin.
  • Des portées déclarées : chaque règle annonce les portées de jeton qu'elle accepte (scope_types) — système, domaine, projet.
  • Deux interrupteurs, dans la section [oslo_policy] de chaque service :
OptionQuand elle est active
enforce_new_defaultsseules les nouvelles règles s'appliquent ; les anciennes, plus permissives, ne sont plus acceptées en parallèle
enforce_scopeun jeton de la mauvaise portée est refusé, même avec le bon rôle
  • État des lieux : ces options sont actives par défaut dans les versions récentes de la bibliothèque, mais chaque service a avancé à son rythme. Vérifier la valeur service par service.
  • Conséquence pratique : selon le service, une opération d'administration attend un jeton de portée système ou un jeton de projet avec admin.
  • En cas de 403 inattendu pour un administrateur : regarder d'abord la portée du jeton, pas le rôle.
sudo k8s kubectl -n openstack exec nova-0 -c nova-api -- \
  grep -A3 '^\[oslo_policy\]' /etc/nova/nova.conf
Noms de pod et de conteneur à adapter : kubectl get pods -n openstack les donne.

6 · Politiques d'accès

Bonnes pratiques

Des groupes, pas des personnes

Toute attribution vise un groupe. Les arrivées et départs se règlent dans l'annuaire, pas dans OpenStack.

Le moindre privilège

reader par défaut, member pour ceux qui déploient, manager pour déléguer. admin reste l'exception.

Très peu d'administrateurs

Le rôle admin déborde encore de sa portée dans plusieurs services : le traiter comme un accès au cloud entier.

Les rôles par défaut

Éviter les rôles maison : aucun service ne les comprend sans surcharge de politique.

Pas de surcharge sans nécessité

Chaque règle modifiée est à revalider à chaque montée de version, service par service.

Des identifiants d'application

Pour tout ce qui n'est pas humain : limités à un projet, à un rôle, à une durée, révocables un par un.

Un compte de secours

Local, hors annuaire et hors fédération, mot de passe au coffre, usage tracé.

Une revue périodique

Extraire les attributions effectives et les faire valider par les responsables de projets.

Synthèse

Ce qu'il faut retenir

Entités et catalogue

  • Acteur + rôle + cible : la seule source de droits.
  • Le domaine délimite noms et délégation.
  • Trois portées : projet, domaine, système.
  • Le catalogue donne l'adresse de chaque service, par interface et par région.

Jetons

  • Une preuve datée : identité et portée.
  • Fernet : chiffré, non stocké, validé par Keystone.
  • Trois sortes de clés ; rotation et distribution indissociables.
  • Le jeton de service couvre les opérations longues.

Sources et politiques

  • Local, LDAP, fédération — par domaine.
  • Rôles et projets restent toujours dans Keystone.
  • Chaque service décide, avec ses propres règles.
  • 401 : qui êtes-vous ? 403 : pas le droit.
